`MatchingEngine`이 가상 스레드를 쓴 이유를 실제 코드 근거로 정리.

## 1. 플랫폼 스레드(스레드풀의 스레드)

**개념**: JVM 스레드 하나가 **OS 스레드 하나에 1:1로 그대로 매핑**된다. `new Thread()`나
`Thread.ofPlatform()`으로 만들면 커널이 실제 스레드를 하나 만들어준다.

**특징**:
- 생성 비용이 크다 — 고정 크기 네이티브 스택을 예약한다(이 프로젝트는 `-Xss512k`로 튜닝, 기본은
  1MB). 스레드 수가 늘수록 이 비용이 그대로 쌓인다(예: 스레드 246개 × 1MB = 246MB — 실제로 이
  프로젝트가 겪은 메모리 예산 문제).
- 블로킹되면(DB 응답 대기, 네트워크 I/O 대기 등) **그 OS 스레드/코어 슬롯을 그대로 점유한 채
  잠든다.** 다른 작업이 그 스레드를 대신 쓸 방법이 없다.
- 그래서 보통 **스레드풀**(`ExecutorService`, 톰캣의 워커 풀)로 미리 만들어두고 재사용한다 —
  매번 생성/폐기하는 비용을 상쇄하기 위해서다.

**언제/왜 쓰나**:
- **요청-응답형 짧은 작업**을 대량으로 처리할 때(웹 서버의 요청 처리). 이 프로젝트의 톰캣이
  `server.tomcat.threads.max=100`으로 API 요청을 처리하는 게 이 경우다.
- **정확한 동시성 "개수" 자체를 통제해야 하는 CPU 바운드 작업**. `LoginQueue`의 PBKDF2 해싱
  워커(`Thread.ofPlatform()`)가 이 경우 — "CPU 코어 수만큼만 정확히 동시에 돌아야 한다"는 요구사항
  자체가 스레드 개수를 엄격히 고정해야 성립하므로, 가상 스레드를 쓰면 오히려 이 통제가 깨진다.

## 2. 가상 스레드

**개념**: JVM이 자체적으로 관리하는 경량 스레드. 실제로 코드를 실행할 때만 **캐리어(carrier)라는
소수의 OS 스레드 풀**에 잠깐 "올라타서" 실행되고, **블로킹 I/O를 만나면 캐리어에서 스스로
내려온다(언마운트).** 그 순간 비어난 캐리어는 다른 가상 스레드가 가져다 쓴다.

**특징**:
- 생성 비용이 매우 작다 — 고정 네이티브 스택을 예약하지 않고, 자바 힙 위에서 필요한 만큼만 자란다.
  그래서 수십만 개를 만들어도 부담이 적다.
- **CPU 연산에는 아무 이점이 없다.** 블로킹 구간이 없으면 그냥 캐리어에 계속 마운트된 채로
  실행되므로, 플랫폼 스레드와 성능 차이가 없다.
- **블로킹 I/O(DB 호출, HTTP 호출, 소켓 쓰기 등)를 만났을 때만 진가를 발휘**한다 — 캐리어를
  비워줘서 다른 가상 스레드가 그 자원을 쓸 수 있게 한다.
- 한계(pinning): `synchronized` 블록 안이나 네이티브(JNI) 블로킹 호출 중에는 언마운트가 안 되고
  캐리어에 그대로 고정된다.

**언제/왜 쓰나**: 스레드가 하는 일의 대부분이 CPU 연산이 아니라 **블로킹 대기**일 때. 동시에 몇
개나 띄우는지(수십만 개든 딱 1개든)와 무관하게, "이 스레드가 자주 블로킹된다"는 성질만으로 쓸
이유가 생긴다.

## 3. 이 프로젝트의 실제 스레드 배정 구조

| 작업 | 스레드 종류 | 왜 |
|---|---|---|
| 클라이언트의 일반 API 요청 | 톰캣 플랫폼 스레드 풀(100개) | 요청-응답형, Spring Boot 기본값 |
| SSE 이벤트 전송(`SseService`) | 전용 가상 스레드 1개 | 소켓 쓰기가 블로킹될 수 있고, 순서 보장을 위해 단일 스레드가 필요 |
| 매칭 엔진(`MatchingEngine`) | 전용 가상 스레드 1개 | 아래 4절 |
| 웹푸시 전송(`NotificationService`) | 가상 스레드 풀 4개 | 외부 HTTP 호출이 블로킹됨 |
| 로그인 해싱(`LoginQueue`) | 플랫폼 스레드 N개(permits) | PBKDF2가 CPU 바운드라 정확한 동시성 개수 통제가 필요 |

SSE는 최초 `GET /subscribe` 요청만 톰캣 스레드가 받고, `SseEmitter`를 반환하는 순간(Servlet 3.0
비동기 처리) 그 톰캣 스레드는 즉시 반납된다 — 이후 실제 이벤트 전송은 전용 가상 스레드가 전담하므로
SSE 연결이 오래(최대 1시간) 유지돼도 톰캣 스레드 풀은 묶이지 않는다.

## 4. 매칭 엔진의 가상 스레드 — 사례 정리

**구조**: `DelayQueue` + 단일 워커 스레드로 모든 매칭 상태 변경을 직렬화한다(락 없이 동시성 문제를
없애는 설계). 이 워커가 처리하는 액션 종류는 여러 개다(오퍼 수락/거절, 만료, 배치 할당 등).

**어디서 DB에 접근하는지**:
- `applyAcceptByDreami`(드리미가 오퍼 수락) — **순수 인메모리 + SSE 알림뿐, DB 접근 없음.**
  ```java
  void applyAcceptByDreami(UUID offerId) {
      ...
      offer.acceptByDreami(now);                          // 인메모리
      matchingEngine.schedule(new ExpireBoormiOffer(...));  // 인메모리 큐 적재
      notificationService.notify(group.boormiId(), ...);    // SSE 알림(논블로킹 제출)
      ...
  }
  ```
- `applyAcceptByBoormi`(부르미가 드리미를 최종 확정) — `proceedToDelivery` →
  `DeliveryService.startDelivery`(`@Transactional`, 실제 JDBC INSERT)로 이어져서 **여기서만
  실제 블로킹 DB 호출이 발생**한다.
  ```java
  void applyAcceptByBoormi(UUID offerId) {
      ...
      matchOffer.confirmByBoormi(...);                 // 인메모리
      group.confirmMatch();                              // 인메모리
      proceedToDelivery(matchOffer, group.boormiId());   // ← 여기서 DB 접근
      cleanUpAfterMatched(matchOffer, group);
  }

  private void proceedToDelivery(MatchOffer matchOffer, UUID boormiId) {
      deliveryService.startDelivery(...);  // @Transactional — 실제 JDBC INSERT
  }
  ```

**왜 이 워커에 가상 스레드를 썼는가**:
- 워커 스레드 자체는 하나의 `run()` 루프를 계속 도는데, 그 루프가 처리하는 여러 액션 중
  일부(`applyAcceptByBoormi`)만 DB I/O를 포함한다. 스레드 타입은 액션 단위가 아니라 **루프
  전체**에 붙는 속성이라, "가끔이라도 블로킹 I/O가 섞이면 그 루프를 도는 스레드는 가상으로
  한다"는 게 실제 선택 기준이다.
- 이 프로젝트는 `SseService`·`NotificationService`도 전부 가상 스레드를 쓰고, 이들은 전부
  vCPU 2개짜리 인스턴스(t3.micro)의 **같은 캐리어 풀**을 공유한다. 매칭 엔진이 `startDelivery`로
  블로킹되는 순간, 그 캐리어를 SSE 전송이나 웹푸시 전송이 잠깐 빌려 쓸 수 있다는 게 이론적 이점이다.
- **다만 이 이득의 실제 크기는 작다** — `startDelivery`는 같은 VPC의 로컬 MySQL에 INSERT 한 번
  날리는 정도라 블로킹 시간이 짧고 빈도도 낮다. "결정적인 성능 개선"이라기보다 "손해가 없어서 고른
  기본값"에 가깝다.

**`LoginQueue`와의 대조로 본 원칙**:
- `LoginQueue`는 가상 스레드를 쓰면 **기능이 망가진다**(정확히 permits개만 동시에 돌아야 하는
  CPU 바운드 요구사항이 깨짐) — 그래서 플랫폼 스레드가 **필수**다.
  ```java
  // LoginQueue.java
  // 가상 스레드를 쓰지 않는 이유는 이 작업이 CPU 바운드라서다. 가상 스레드는
  // 블로킹 I/O를 겹치는 데 쓰는 것이고, 여기서는 "정확히 permits개만 동시에 돈다"가 요점이다.
  Thread.ofPlatform().name("login-hasher-" + i).daemon(true).start(this::run);
  ```
- `MatchingEngine`은 플랫폼 스레드로 바꿔도 **기능은 완전히 동일하게 동작한다**(실제로
  `Thread.ofPlatform()`으로 그대로 대체 가능 — `LoginQueue`가 이미 그 패턴을 쓰고 있다). 가상
  스레드는 "필수"가 아니라 "달리 손해 볼 게 없어서 고른 선택"이라는 게 최종 결론이다.

**한 줄 요약**: 플랫폼 스레드는 "OS 스레드를 그대로 예약해두고 재사용하는" 무거운 자원이라 정확한
동시성 통제가 필요할 때 쓰고, 가상 스레드는 "블로킹 순간에만 자원을 반납하는" 가벼운 자원이라
블로킹 I/O가 섞인 작업에 기본으로 쓰기 좋다 — 매칭 엔진은 후자에 해당하지만, 그 이점이 필수적이라기보다
비용 없는 합리적 기본값이라는 점까지가 정확한 이해다.
