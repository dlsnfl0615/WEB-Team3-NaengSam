**동작 원리**

*Q. presigned URL이 인증 없이도 접근을 허용하는 원리는?*

Presigned URL은 HTTP 메서드, 리소스 경로, 만료 시간, 필요한 헤더 같은 요청 조건을 서버가 가진 IAM 자격증명(Access Key/Secret Key)으로 HMAC-SHA256 서명해서 쿼리 파라미터(X-Amz-Signature 등)에 담아둔 URL입니다. S3는 요청이 들어오면 동일한 방식으로 서명을 재계산해 비교하고, 값이 일치하고 만료 시간(X-Amz-Expires) 이내이면 요청을 처리합니다. Access Key/Secret Key 자체가 아니라 "이 조건으로 서명된 증명서"만 전달되는 구조라서 자격증명이 클라이언트에 노출되지 않는다는 점이 핵심입니다.

*Q. generatePresignedUrl이 내부적으로 하는 일은?*

버킷, 키, HTTP 메서드, 만료 시간, 추가 헤더(Content-Type 등)를 받아 Canonical Request를 구성하고, SDK가 가진 자격증명으로 이를 서명한 뒤 서명값을 쿼리 스트링에 붙여 최종 URL을 만듭니다. 이 과정은 로컬에서 계산만 이루어지고 실제 네트워크 요청은 발생하지 않습니다.

**보안 관련**

*Q. 만료 시간을 어떻게, 왜 그렇게 설정했는지?*

업로드/다운로드에 걸리는 예상 시간에 약간의 여유를 더해 최소한으로 설정하는 게 원칙입니다. 예를 들어 업로드는 수 분(5~15분), 조회용 다운로드 링크는 목적에 따라 초 단위에서 길게는 1시간 정도로 다르게 잡습니다. 너무 길게 잡으면 URL 탈취 시 위험 노출 시간이 늘어나고, 너무 짧으면 네트워크 지연으로 실패율이 올라가는 트레이드오프가 있다는 점을 함께 설명하면 좋습니다.

*Q. URL이 유출되면 어떤 위험이 있고, 어떻게 완화했는지?*

만료 전까지는 URL을 아는 누구든 해당 동작을 수행할 수 있습니다. 다운로드용이면 정보 유출, 업로드용이면 임의 파일 덮어쓰기나 스토리지 오남용으로 이어질 수 있습니다. 완화책으로는 짧은 만료 시간, HTTPS 강제, 예측 불가능한 고유 키(UUID 기반 경로)로 다른 리소스까지 유추되지 않게 하는 것, 업로드 후 즉시 폐기하는 사실상 1회성 사용 등이 있습니다.

*Q. 업로드 파일 타입/크기 제한은 어떻게 걸었는지?*

PUT 방식은 서명할 때 Content-Type을 조건에 포함시켜, 실제 요청의 Content-Type이 다르면 S3가 거부하게 할 수 있지만 크기 제한은 세밀하게 걸기 어렵습니다. 더 정교한 제어가 필요하면 POST 방식을 써서 Policy document에 `content-length-range`, `starts-with $Content-Type` 같은 조건을 명시하는 방법이 있습니다. 실제 프로젝트에서 어떤 방식을 썼고 어떤 조건을 걸었는지 구체적으로 답하면 좋습니다.

*Q. 업로드 완료 확인 및 악성 파일 검증은 어떻게 했는지?*

클라이언트의 "업로드 완료" 콜백만 신뢰하기보다는, S3 이벤트 알림을 SQS/SNS/Lambda로 연결해서 실제 객체가 생성된 시점에 서버가 후처리(DB 반영, 스캔, 썸네일 생성 등)를 트리거하는 패턴이 일반적입니다. 악성 파일 검증은 Lambda 등에서 별도 스캐너를 돌려 비동기로 확인하고, 문제가 있으면 격리하거나 삭제하는 흐름으로 설명하면 됩니다.

*Q. 여기서 나오는 SQS/SNS가 정확히 뭔가? (인스타 같은 그 "SNS"는 아닌지)*

아니다, 소셜 미디어(SNS)와는 전혀 무관한 AWS 인프라 서비스다. 이름이 우연히 "SNS"로 겹쳐서 헷갈리기 쉽다.

- **SNS = Simple Notification Service**: **발행-구독(pub/sub) 알림 서비스**. "토픽(topic)"에 메시지를 발행(publish)하면, 그 토픽을 구독(subscribe) 중인 여러 대상(SQS 큐, Lambda, HTTPS 엔드포인트, 이메일 등)에게 동시에 팬아웃(fan-out)해준다.
- **SQS = Simple Queue Service**: **메시지 큐**. 생산자가 큐에 메시지를 쌓아두면, 소비자가 그 큐를 계속 폴링(polling)하며 메시지를 하나씩 꺼내 처리한다.

S3 업로드 완료를 서버(WAS)에 알리는 방법은 실제로 아래 네 가지 중 하나를 고르는 문제다.

| 방식 | 흐름 | 백엔드가 해야 할 일 | 인증 |
|---|---|---|---|
| **A. 웹훅(직접 HTTP 호출)** | `Lambda → (HTTP POST) → 백엔드 공개 API` | 공개 엔드포인트를 열고 위조 요청 방지용 서명 검증 로직을 직접 구현 | 직접 구현 필요(가장 번거로움) |
| **B. SQS 폴링** | `Lambda → SQS 큐에 적재 → 백엔드가 큐를 계속 조회해서 꺼내감` | 백엔드가 능동적으로 큐를 조회하는 컨슈머 로직만 추가하면 됨. 인바운드 포트를 열 필요 없음 | IAM 자격증명으로 처리(추가 구현 불필요) |
| **C. SNS→SQS 팬아웃** | `Lambda → SNS 토픽 발행 → 구독 중인 SQS 큐로 전달 → 백엔드가 그 큐를 폴링` | B와 사실상 동일. 소비자가 백엔드 하나뿐이면 SNS를 끼울 이유가 없고, 백엔드 외에 다른 시스템(분석 파이프라인 등)도 같은 이벤트를 받아야 할 때만 의미가 있음 | IAM |
| **D. 검증완료 버킷으로 이동** | `Lambda가 검증 통과 파일을 별도 버킷으로 복사/이동` | 알림 자체가 필요 없음. 기존처럼 HEAD로 존재 확인하되, 대상 버킷만 "검증완료" 버킷으로 바꿈 | 불필요 |

즉 "SQS/SNS로 알림"은 **말씀하신 "웹훅으로 백엔드 API를 직접 호출"과는 다른 방식**이다. 웹훅은 Lambda가 백엔드 주소를 알고 직접 찔러야 하지만(방식 A), SQS 방식은 **백엔드가 스스로 AWS 쪽에 계속 물어보러 가는(pull) 구조**라 백엔드에 별도 공개 엔드포인트·서명 검증이 필요 없다는 게 핵심 차이다.

*Q. 인증/인가는 어느 시점에 이루어지는지?*

presigned URL 자체는 발급된 이후 S3 단에서 별도의 사용자 인증을 하지 않기 때문에, 인가 검증은 URL을 발급하는 시점에 끝나야 합니다. 발급 API는 반드시 인증된 사용자만 호출 가능해야 하고, 서버는 그 시점에 해당 사용자가 해당 리소스에 접근할 권한이 있는지 확인한 뒤 서명을 생성해야 한다는 점이 핵심 포인트입니다.

**실무 디테일**

*Q. PUT과 POST(정책 기반) 방식의 차이는?*

PUT은 단일 파일을 하나의 URL로 업로드하는 방식으로 사용이 간단하지만 조건 설정이 제한적입니다. POST는 HTML form 업로드에 최적화되어 있고, base64 인코딩된 Policy document에 파일 크기 범위, 키 접두사, Content-Type 패턴 같은 여러 조건을 세밀하게 걸 수 있어 브라우저 form 업로드에 많이 쓰입니다.

*Q. 멀티파트 업로드와 presigned URL을 어떻게 함께 쓰는지?*

대용량 파일(보통 100MB 이상)은 CreateMultipartUpload로 업로드 세션을 열고, 각 파트마다 별도의 presigned URL을 발급해 클라이언트가 병렬로 업로드하게 한 뒤, CompleteMultipartUpload로 조립을 마무리하는 흐름입니다. 이렇게 하면 특정 파트만 실패해도 전체를 재업로드할 필요가 없습니다.

*Q. presigned URL 발급 API는 어떻게 설계했는지?*

클라이언트 요청 → 인증(JWT/세션) 확인 → 업로드 경로는 서버가 결정(클라이언트가 임의 경로를 지정하지 못하게) → 파일 메타데이터 검증 → presigned URL 생성 → 클라이언트에 URL과 만료 시간 반환의 흐름입니다. 발급 API 자체는 반드시 인증이 필요한 엔드포인트로 설계해야 하고, 남발되지 않도록 Rate limiting도 고려 대상이라고 언급하면 좋습니다.

**트레이드오프**

*Q. presigned URL이 항상 나은 방식인지?*

대용량 파일이나 트래픽이 많아 서버 부하를 줄여야 하는 경우, 서버가 파일 내용 자체를 처리할 필요가 없는 경우에는 presigned URL이 유리합니다. 반대로 업로드 전에 서버가 반드시 파일을 동기적으로 검사·변환해야 하거나, 클라이언트를 신뢰할 수 없어 세밀한 통제와 감사 로그가 필요한 경우에는 서버 경유 방식이 더 적합할 수 있습니다.

*Q. 장애 발생 시(URL 만료, 업로드 중 실패) 어떻게 처리했는지?*

URL 만료로 실패하면 클라이언트가 이를 감지해 새 presigned URL을 재요청하도록 처리합니다. 멀티파트 업로드 중 특정 파트만 실패했다면 해당 파트만 재업로드하면 됩니다. 그리고 클라이언트의 "완료했다"는 콜백만으로 최종 상태를 확정하지 않고, S3 이벤트 기반으로 서버가 실제 상태를 다시 확인하는 방식이 더 안전하다는 점을 언급하면 좋은 답변이 됩니다.
