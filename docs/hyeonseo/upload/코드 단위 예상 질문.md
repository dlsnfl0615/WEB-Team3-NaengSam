# upload 도메인 — 코드 단위 예상 질문

"바이브 코딩이었더라도 코드 한 줄 한 줄에 대해 깊게 답할 수 있어야 한다"는 전제로 준비하는 문서.
질문 유형: ① 이 코드에 문제가 생길 수 있는 지점, ② 애노테이션을 왜 그렇게 썼는지, ③ 주석에 대한
꼬리질문, ④ 동시성을 처리한 다른 클래스(`OrderRepository`)가 있는데 왜 여긴 다른 방식을 썼는지,
⑤ 대체 가능한 방법이 있는데 왜 지금 방식을 골랐는지.

> 대상 파일: `DevStorageController`, `DevUploader`, `InMemoryFileStore`, `Uploader`, `S3Uploader`,
> `S3Config`, `UploadProperties`, `S3PresignService`, `UploadController`, `UploadSessionService`,
> `UploadSession`, `UploadSessionRepository`, `UploadPurpose`, `UploadSessionCd`, `UploadErrorCode`.

---

## 1. 이 코드에 문제가 생길 수 있는 지점

**Q1. `UploadSession`에 `consume()` 인스턴스 메서드가 있는데, 실제 소비 처리는 이 메서드를 안 쓰고
`UploadSessionRepository.markConsumedIfIssued()`라는 별도의 JPQL 벌크 UPDATE로 합니다. 왜 두 개가
있고, `consume()`은 어디서 쓰이나요? 죽은 코드 아닌가요?**

죽은 코드는 아니고, **역할이 다릅니다.**

- `UploadSession.consume()`(엔티티 메서드)은 실제 운영 흐름에서 전혀 호출되지 않습니다. 대신
  **테스트 코드에서 "이미 CONSUMED 상태인 세션"을 픽스처로 만들 때**만 씁니다
  (`UploadSessionServiceTest.java:129, 195` — `session.consume()`으로 상태를 미리 CONSUMED로
  세팅해두고, 그 상태에서 서비스가 어떻게 동작하는지 검증). `ReflectionTestUtils` 대신 엔티티가 이미
  제공하는 상태 전이 메서드를 그대로 재사용한 것입니다.
- 실제 운영 흐름(`UploadSessionService.consume(String key)`)은 엔티티를 조회해서 `session.consume()`을
  부르고 `save()`하는 방식(더티 체킹)을 **의도적으로 쓰지 않습니다.** 대신
  `uploadSessionRepository.markConsumedIfIssued(key)`라는 **조건부 UPDATE 쿼리 한 방**으로 처리합니다.
  이유는 4절(동시성)에서 자세히 다룹니다 — 요약하면, 엔티티를 조회해서 상태를 바꾸고 커밋하는 방식은
  두 트랜잭션이 동시에 같은 세션을 읽어 들어오는 경합에 안전하지 않기 때문입니다.

즉 "같은 상태 전이 로직이 두 곳에 있다"는 지적은 맞지만, 하나는 **테스트 픽스처 전용**, 하나는
**운영 경로 전용**으로 용도가 갈립니다. 다만 이렇게 두 군데 있으면 나중에 누군가 실수로 서비스 코드에서
`session.consume()` 경로를 쓰게 될 위험은 있습니다 — 리뷰에서 "이거 프로덕션에서 쓰면 안 되는 메서드"
라는 걸 표시(`@VisibleForTesting`류 주석 등)해두면 더 안전했을 겁니다.

**Q2. `s3_key` 컬럼이 `length = 500`으로 제한돼 있는데, `fileName`의 길이 검증이 없습니다. 아주 긴
파일명이 들어오면 어떻게 되나요?**

```java
// UploadController.validateFileName
if (fileName == null || fileName.isBlank()) { ... }
if (fileName.contains("/") || fileName.contains("\\") || fileName.contains("..")) { ... }
// 길이 검증 없음

// UploadSessionService.buildKey
return "uploads/" + purpose.name() + "/" + UUID.randomUUID() + "-" + fileName;
```

`buildKey`가 만드는 key는 `"uploads/" + purpose + "/" + UUID(36자) + "-" + fileName`인데, `fileName`
자체의 길이를 막는 코드가 없습니다. 파일명이 충분히 길면(대략 450자 이상) 합쳐진 key가
`s3_key varchar(500)`을 넘어서고, `uploadSessionRepository.save(...)` 시점에 DB 드라이버가 데이터
길이 초과 예외를 던집니다. 이건 `BusinessException`으로 깔끔하게 잡히는 게 아니라
`GlobalExceptionHandler`의 최종 캐치올(`Exception.class`)로 떨어져서 사용자에게는 그냥 500(내부 오류)
로 보이게 됩니다 — 원인이 "파일명이 너무 길다"는 걸 사용자도 로그도 바로 알기 어렵습니다.
**실무라면 `fileName` 길이 상한을 `validateFileName`에 추가하고, 초과 시 `INVALID_FILE_NAME`처럼
명확한 에러코드로 막는 게 맞습니다.**

**Q3. `S3PresignService`에 이런 TODO가 남아있습니다 — `// todo: presigned url에 저장된 파일이
안전한지 체크해주는 aws 서비스 호출해야 함. 지금은 권한이 없는데 댕글님께 나중에 여쭤보기...`.
이게 왜 문제이고, 지금 상태에서 실제로 뚫릴 수 있는 시나리오가 뭔가요?**

이 TODO는 "업로드된 파일이 실제로 악성 파일인지"를 검증하는 로직이 아직 없다는 뜻입니다.
`presigned-url-strategies.md`에도 이미 정리된 한계인데, 이 프로젝트가 채택한 "업로드 세션 방식"은
**key 재사용/타인 도용/중복 소비는 막지만, 파일 내용 자체는 전혀 검사하지 않습니다.** 예를 들어
신분증 사진 업로드(`DREAMI_ID_CARD`)에 실행 파일이나 악성 스크립트를 이미지 확장자로 위장해서 올려도
현재 코드는 막지 못합니다(`resolveContentType`이 확장자 기반으로 Content-Type만 강제할 뿐, 실제
바이트 내용을 열어보지 않기 때문). 이 팀이 이걸 "지금 요구사항엔 없다"고 판단해 의도적으로 미룬
것(문서의 "이 프로젝트가 업로드 세션 방식을 선택한 이유" 참고)이지, 놓친 게 아니라는 걸 구분해서
답해야 합니다 — 다만 이런 TODO가 코드에 남아있다는 건 "인지하고 있는 리스크"라는 뜻이라 면접에서
숨기지 말고 그대로 인정하는 게 낫습니다.

**Q4. `InMemoryFileStore`는 삭제 경로가 아예 없다고 주석에 적혀 있습니다. 이게 왜 로컬 개발에서는
문제가 안 되나요?**

이 저장소는 `upload.s3-enabled=false`일 때만(로컬 개발 전용) 활성화됩니다. 개발 서버는 코드를
수정할 때마다, 또는 하루에도 여러 번 재시작되기 때문에 힙에 쌓인 데이터가 주기적으로 초기화됩니다.
운영 환경에서는 이 빈 자체가 등록되지 않으므로(`@ConditionalOnProperty`) 이 문제가 아예 발생할 수
없는 구조입니다. `inMemoryStructures()`가 총 바이트를 관리자 화면에 노출해두는 것도, "혹시 로컬에서도
오래 켜두면 위험할 수 있으니 눈에 보이게는 해두자"는 안전장치입니다.

## 2. 동시성 처리 — 왜 이 방식을 골랐는지 (`OrderRepository`와 비교)

**Q5. 이 프로젝트에서 동시성 문제를 다룬 다른 클래스로 `OrderRepository.findByOrderId`가
`@Lock(LockModeType.PESSIMISTIC_WRITE)`(비관적 락)를 쓰는 걸 봤습니다. `UploadSessionRepository`는
왜 락을 안 걸고 조건부 UPDATE(`markConsumedIfIssued`)를 썼나요?**

두 코드 모두 "동시에 같은 행을 여러 트랜잭션이 건드리는 경합"을 막는다는 목적은 같지만, **경합의
모양이 다르기 때문에 해법도 다릅니다.**

```java
// OrderRepository — 비관적 락
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Orders> findByOrderId(UUID orderId);
```
드리미의 제안 수락 흐름은 **"행을 읽고 → 여러 조건(아직 MATCHING 상태인지, 이 드리미가 자격이 있는지
등)을 애플리케이션 코드로 판단한 뒤 → 여러 필드를 갱신"**하는, SQL의 `WHERE` 절 하나로 표현하기
어려운 복잡한 read-check-write입니다. 그래서 아예 행을 락으로 잠가 다른 트랜잭션이 못 끼어들게 만든
뒤, 그 안에서 자바 코드로 판단하고 갱신합니다.

```java
// UploadSessionRepository — 조건부 UPDATE (락 없음)
@Modifying
@Query("""
    UPDATE UploadSession s SET s.status = CONSUMED, s.consumedDtm = CURRENT_TIMESTAMP
    WHERE s.s3Key = :s3Key AND s.status = ISSUED
    """)
int markConsumedIfIssued(@Param("s3Key") String s3Key);
```
반면 세션 소비는 **"ISSUED일 때만 CONSUMED로 바꾼다"는 조건 자체가 `WHERE` 절 하나로 완전히 표현
가능**합니다. 별도의 복잡한 비즈니스 판단이 끼어들 필요가 없습니다. 이런 경우엔 SQL의 `UPDATE ...
WHERE 조건` 자체가 DB 엔진 레벨에서 원자적으로 실행되므로, 애플리케이션이 락을 따로 잡을 필요가
없습니다 — 동시에 같은 key로 두 요청이 들어와도, DB가 그 UPDATE 문 실행 자체를 순차적으로 처리하며
**딱 하나만 영향받은 row 수 1을 받고 나머지는 0을 받습니다.**

**정리하면**: "읽고 판단해서 여러 필드를 조건부로 바꿔야 하는 복잡한 전이"엔 비관적 락(Order),
"조건 하나로 상태만 원자적으로 뒤집으면 되는 단순 전이"엔 조건부 UPDATE(UploadSession)를 쓴 것입니다.
후자가 **락을 아예 안 잡으므로 다른 트랜잭션을 블로킹하지 않아 처리량 면에서 더 유리**하다는 것도
같이 언급하면 좋습니다.

**Q6. 락 대신 `@Version`을 이용한 낙관적 락(Optimistic Lock)을 쓰는 방법도 있는데, 왜 그것도 안
썼나요?**

낙관적 락을 썼다면 흐름이 이랬을 겁니다: 세션을 조회(SELECT) → 애플리케이션에서 `status`를 확인 →
`session.setStatus(CONSUMED)` → 저장 시 버전이 그 사이 바뀌었으면 `OptimisticLockingFailureException`
발생 → 그걸 잡아서 "이미 소비됨"으로 재해석하는 코드를 추가로 짜야 합니다. 이건 **SELECT 한 번 +
UPDATE 한 번, 총 두 번의 왕복**이 필요하고, 예외를 잡아 성공/실패를 구분하는 우회 로직도 필요합니다.

반면 조건부 UPDATE는 **한 번의 왕복**으로 끝나고, "영향받은 row 수(0 또는 1)"라는 정수값 하나로
바로 성공 여부를 알 수 있어 예외 처리도 필요 없습니다. 애초에 "동시에 두 요청이 왔을 때 정확히
하나만 성공해야 한다"는 요구사항 자체가 `@Version` 없이도 `WHERE status = ISSUED` 조건 하나로 완전히
표현되므로, 낙관적 락이 주는 추가 기능(버전 충돌 감지)이 여기선 불필요한 오버엔지니어링입니다.

## 3. 애노테이션 관련 질문

**Q7. `DevStorageController`, `DevUploader`, `InMemoryFileStore` 세 클래스 모두
`@ConditionalOnProperty(name = "upload.s3-enabled", havingValue = "false", matchIfMissing = true)`가
문자열로 반복돼 있습니다. 이렇게 세 군데에 흩어놓은 게 문제가 될 수 있지 않나요?**

네, 실제로 취약한 지점입니다. 이 세 빈은 반드시 "다 같이 켜지거나 다 같이 꺼져야" 앱이 정상 동작하는
**세트**입니다(`InMemoryFileStore` 없이 `DevUploader`만 켜지면 `DevUploader`의 생성자 주입이 실패해
기동 자체가 안 됩니다). 그런데 이 조건을 하나의 상수나 커스텀 애노테이션(`@ConditionalOnDevStorage`
같은)으로 묶지 않고 **문자열 리터럴을 세 번 복붙**해뒀습니다. 만약 리팩터링 중 한 곳만 프로퍼티
이름을 오타 내거나 다른 값으로 바꾸면:
- `DevUploader`/`InMemoryFileStore`는 켜지는데 `DevStorageController`만 안 켜지면 → 로컬에서
  presigned URL은 발급되는데 실제 PUT/GET을 받을 엔드포인트가 없어 404
- 반대로 S3 관련 조건과 어긋나면 → `Uploader` 인터페이스 구현체가 0개 또는 2개가 되어 스프링 기동
  자체가 실패(`NoSuchBeanDefinitionException` 또는 `NoUniqueBeanDefinitionException`)

**개선하면**: `upload.s3-enabled` 프로퍼티 키를 상수 하나로 빼거나, `@ConditionalOnProperty`를 감싼
커스텀 메타 애노테이션(`@ConditionalOnDevStorage`)을 만들어 세 곳에 재사용했으면 이 위험이 원천적으로
사라졌을 것입니다.

**Q8. `matchIfMissing = true`는 왜 넣었나요? 빼면 어떻게 되나요?**

`upload.s3-enabled` 프로퍼티가 **아예 설정 파일에 없을 때**의 기본 동작을 정하는 옵션입니다.
`matchIfMissing = true`가 없으면, 프로퍼티가 없는 환경(신규 개발자가 로컬에 `.env`를 아직 안 채운
경우 등)에서는 조건이 "만족 안 됨"으로 취급돼 `DevUploader` 등이 **아무것도 등록되지 않고**,
동시에 `S3Uploader`(`havingValue = "true"`만 요구, `matchIfMissing` 없음 → 기본값 false)도 등록
안 됩니다. 결과적으로 `Uploader` 구현체가 하나도 없어서 `S3PresignService` 생성자 주입이 실패하고
**앱 기동 자체가 실패**합니다. `matchIfMissing = true`를 넣어둔 덕분에, "설정을 안 건드린 순수
로컬 환경"이 안전하게 기본값(Dev 모드, AWS 자격증명 불필요)으로 떨어지게 만든 것입니다.

**Q9. `UploadSessionRepository.markConsumedIfIssued`에 `@Modifying`을 빼면 어떻게 되나요?**

Spring Data JPA는 `@Query`가 붙은 메서드를 기본적으로 **조회(SELECT)**로 간주합니다. 이 메서드는
실제로는 `UPDATE` 문인데 `@Modifying`을 빼면, 실행 시점에
`InvalidDataAccessApiUsageException`(또는 유사한 예외)이 발생합니다 — JPA가 "이 쿼리는 결과 엔티티를
매핑해야 하는데 UPDATE 문이라 매핑할 게 없다"고 판단하기 때문입니다. `@Modifying`은 "이건 DML이니
결과를 엔티티로 매핑하지 말고 영향받은 row 수(int)를 그대로 반환하라"고 알려주는 표시입니다.

**Q10. `S3PresignService.validateScope`에는 `@Transactional(readOnly = true)`가 붙어 있는데, 왜
읽기 전용으로 표시했나요? 그냥 두면 뭐가 다른가요?**

`readOnly = true`는 Hibernate의 flush 모드를 사실상 MANUAL로 바꿔서, 트랜잭션 커밋 시점에 자동으로
도는 dirty checking(변경 감지)용 스냅샷 비교 작업을 생략시킵니다. 이 메서드는 세션을 조회해서 비교만
할 뿐 아무것도 쓰지 않으므로, 이 최적화를 켜도 안전하고 약간의 성능 이득이 있습니다(`jpa-interview.md`
4절 참고). 안 붙여도 기능은 똑같이 동작하지만, "이 메서드는 절대 쓰기를 하지 않는다"는 의도가
코드에서 드러나지 않게 됩니다.

## 4. 주석에 대한 꼬리질문

**Q11. `S3PresignService.resolveDownloadUrl`의 주석에 "실패해도 예외를 던지지 않고 null로
degrade한다"고 적혀 있습니다. 왜 이 메서드만 예외 대신 null을 반환하나요? 호출부에서 NPE 나는 거
아닌가요?**

이 메서드는 **모든 곳에서 쓰라고 만든 게 아니라, "다운로드 URL이 없어도 화면이 정상적으로 그려져야
하는 곳"에서만 쓰라고 의도적으로 분리한 메서드**입니다. 예를 들어 완료된 주문 요약 화면이나 관리자
심사 목록처럼, 사진 하나가 이미 삭제됐거나 스토리지 장애로 잠깐 조회가 안 되더라도 **그 화면 전체를
실패시키면 안 되는 곳**에서는 "사진 없음" 자리표시자를 보여주면 그만입니다. 반대로 실제로 업로드
여부를 검증해서 통과/거부를 갈라야 하는 곳(`UploadSessionService.checkUpload`)은 이 메서드가 아니라
`generateDownloadUrl`(예외를 던지는 원래 버전)을 그대로 씁니다. 즉 NPE 위험이 아니라, **"조회
실패를 허용해도 되는 화면인가"를 개발자가 메서드 선택으로 명시하게 만든 설계**입니다. 호출부가
`resolveDownloadUrl`을 쓴다면 그 화면은 `null`을 받았을 때 "사진 없음" UI를 그리도록 이미 대비돼
있어야 하는 게 이 API의 계약입니다.

**Q12. `UploadPurpose`의 `resourceScopeRequired`는 왜 어떤 용도(`PICKUP_CERTIFICATION_IMAGE`,
`DELIVERY_CERTIFICATION_IMAGE`)만 `true`이고 나머지는 `false`인가요?**

이 값은 "presigned URL을 발급할 때 `resourceId`(예: 주문 ID)가 필수인가"를 결정합니다.
`ORDER_ITEM_IMAGE`(주문 생성 중 물건 사진)는 **아직 주문 자체가 안 만들어진 시점**에 사진을 먼저
올리므로 연결할 `orderId`가 아직 없습니다 — 그래서 `false`. `DREAMI_ID_CARD`/`DREAMI_CRIMINAL_RECORD`도
"이 사람"에게 귀속될 뿐 특정 건(주문 등)에 속하지 않아서 `false`. 반면
`PICKUP_CERTIFICATION_IMAGE`/`DELIVERY_CERTIFICATION_IMAGE`(픽업/배달 인증 사진)는 **반드시 특정
주문 건에 종속**돼야 의미가 있는 사진이라 `resourceId`(주문 ID)가 없으면 아예 발급 요청 자체를
막습니다(`UploadSessionService.issue`의 `MISSING_RESOURCE_ID` 검사). 이 값이 `false`인 용도에
`resourceId`를 안 넘겨도 되고, `true`인 용도인데 `resourceId`를 안 넘기면 그 자리에서 즉시 예외입니다.

## 5. 대체 가능한 방법이 있는데 왜 지금 방식을 골랐는지

**Q13. `S3Uploader`는 `@Service`가 아니라 `@Component`를 씁니다. 기능적으로 차이가 있나요? 왜
`@Service`를 안 썼나요?**

**Spring 빈으로 등록되는 동작 자체는 완전히 동일**합니다. `@Component`/`@Service`/`@Repository`는
전부 `@Component`의 특수화(메타 애노테이션)일 뿐이고, 셋 다 컴포넌트 스캔 대상이 됩니다. 차이는
의미론적 구분과 부가 기능뿐입니다 — `@Repository`는 예외 변환(persistence 예외 → Spring
DataAccessException)이 자동으로 붙고, `@Service`는 관례상 "도메인 비즈니스 로직"을 담당하는 빈에
붙입니다. `S3Uploader`는 비즈니스 규칙을 담고 있는 게 아니라 **외부 스토리지(S3)에 대한 순수
어댑터/인프라 코드**라, 이 프로젝트는 "인프라 구현체는 `@Component`, 비즈니스 로직은 `@Service`"로
구분해서 씁니다(`S3PresignService`는 실제 검증 로직이 있어 `@Service`인 것과 대조). 코드 동작은 같지만
읽는 사람에게 "이 클래스가 어떤 계층인지"를 알려주는 역할입니다.

**Q14. `InMemoryFileStore`는 왜 `HashMap` 대신 `ConcurrentHashMap`을 썼나요? 어차피 로컬 개발
전용이고 부하도 없을 텐데, 굳이 동시성 안전한 자료구조를 쓸 필요가 있었나요?**

"로컬 전용이라 트래픽이 적다"는 건 맞지만, **동시 요청 자체가 없는 건 아닙니다.** 톰캣은 로컬에서도
요청마다 별도 스레드로 처리하므로, 개발자가 브라우저 탭 두 개에서 동시에 업로드 테스트를 하거나,
프론트가 여러 이미지를 병렬로 업로드하는 것만으로도 `filesByKey` 맵에 동시 쓰기가 발생할 수 있습니다.
일반 `HashMap`은 동시 쓰기에 대해 스레드 안전을 보장하지 않아 최악의 경우 내부 버킷 구조가 깨지거나
값이 유실될 수 있습니다. `ConcurrentHashMap`은 `HashMap`과 API가 거의 동일하면서 스레드 안전을
공짜로 얻을 수 있으므로, 굳이 안 쓸 이유가 없어서 기본으로 택한 것입니다 — "로컬 전용이니 대충
짜도 된다"가 아니라 "안전한 선택의 비용이 0에 가까우면 항상 안전한 걸 쓴다"는 원칙입니다.

**Q15. 파일 검증을 강화하려면 `presigned-url-strategies.md`에 나온 대로 S3 이벤트 + Lambda 방식으로
갈 수도 있는데, 지금 왜 업로드 세션(DB row) 방식을 택했나요?**

`presigned-url-strategies.md`에 이미 정리해둔 근거를 요약하면: 이 서비스에서 업로드되는 파일은
드라이버 신분증·픽업 인증 사진처럼 **소량이고 신뢰도가 이미 어느 정도 있는(로그인된 사용자가 올리는)
파일**이라, 악성 파일 스캔까지 필요한 요구사항이 아직 없었습니다. Lambda 방식은 인프라(Lambda 배포,
S3 이벤트 설정, SQS/SNS 연결, IAM 권한)가 추가로 필요하고 비동기 처리라 클라이언트가 "검증 완료"를
확인하려면 폴링/SSE까지 얹어야 합니다. 반면 업로드 세션 방식은 **순수 Spring Boot + MySQL만으로**
"key 재사용 공격 차단"이라는 이 프로젝트의 핵심 요구사항을 충분히 만족시킵니다. 요구사항이 더
엄격해지면(악성 파일 차단 등) 그때 Lambda 방식으로 전환하거나 두 방식을 결합하는 게 자연스러운
다음 단계라고 문서에도 명시돼 있습니다 — 즉 "몰라서 안 한 게" 아니라 **지금 요구사항 대비
오버엔지니어링을 피한 선택**이라는 걸 근거로 답하면 됩니다.
