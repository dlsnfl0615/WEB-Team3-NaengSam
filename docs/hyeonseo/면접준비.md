## 3. 코드 공부 전략

### 핵심 원칙
> **코드를 외우지 말고, "왜 이렇게 짰는지"를 설명할 수 있어야 한다.**

면접관은 코드 암기를 원하는 게 아니라 **기술적 판단력**을 본다.

### 내 담당 도메인 공부법
1. **코드를 읽으면서 "WHY" 메모 작성**
   - 왜 이 메서드에 `@Transactional(readOnly = true)`를 붙였나?
   - 왜 이 조회를 JPQL이 아닌 파생 쿼리로 썼나?
   - 왜 이 예외는 `BusinessException`으로 처리했나?
2. **기능 흐름을 말로 설명하는 연습**
   - 화면에서 버튼을 누르면 → 어떤 HTTP 요청이 → 어떤 컨트롤러로 → 어떤 서비스 로직을 거쳐 → DB에 어떻게 저장되는지
3. **내가 만든 ERD/API 설계 결정에 대해 이유 설명 준비**

### 팀원 도메인 공부법 (효율적으로)
- 코드를 깊게 읽지 말고 **서비스 레이어의 public 메서드 시그니처와 주석**만 읽기
- 각 도메인의 `ErrorCode` enum을 읽으면 그 도메인에서 어떤 예외 상황을 다루는지 빠르게 파악됨
- **핵심 질문**: "이 도메인이 왜 필요하고, 어떤 데이터를 다루는가?"

## 4. 팀원 담당 부분도 알아야 하나?

### 결론: **알면 압도적으로 유리하다. 단, 깊이보다 넓이로.**

### 왜 알아야 하는가
- 면접관은 "팀 프로젝트에서 본인이 전체 흐름을 이해하고 있느냐"를 본다
- "우리 팀은 이런 기술적 이슈가 있었고, 저는 이렇게 기여했습니다"라고 말할 수 있어야 함
- 자기 도메인만 알면 "팀워크 능력이 없다"는 인상을 줄 수 있음

### 어느 수준까지 알아야 하는가
| 수준 | 내용 | 필요 여부 |
|------|------|----------|
| ★★★ 필수 | 서비스 전체 흐름 (부르미가 배송 요청하면 어떻게 드리미한테 가는가) | 반드시 |
| ★★★ 필수 | 기술적 결정 이유 (왜 세션? 왜 SSE? 왜 Redis?) | 반드시 |
| ★★☆ 권장 | 각 도메인의 핵심 로직 개요 | 할 수 있으면 |
| ★☆☆ 여유 | 팀원이 짠 코드의 세부 구현 | 시간 되면 |

### 실제로 준비해야 할 "전체 흐름" 시나리오
1. **회원가입 → 로그인** 흐름 (Redis 대기열 포함)
2. **배송 요청 → 매칭 → 수락 → 배송 완료** 전체 플로우
3. **파일 업로드** 흐름 (S3 Presigned URL)
4. **실시간 위치 추적** 흐름 (SSE)
5. **알림** 흐름 (WebPush + SMS 폴백)

## 5. AWS 인프라 공부법

### 이 프로젝트에서 실제로 쓴 AWS 서비스

#### EC2 (Elastic Compute Cloud)
- **용도**: Spring Boot 백엔드 서버 실행
- **이 프로젝트에서**: t3 인스턴스, Docker로 배포, 메모리 제약으로 JVM 옵션 튜닝
- **공부할 것**:
  - 인스턴스 타입 (t3 = 버스트 가능형, 왜 선택했는지)
  - 보안 그룹 (포트 8080, 8081 열기)
  - SSH 접속, 파일 전송

#### S3 (Simple Storage Service)
- **용도 1**: 프론트엔드 정적 파일 호스팅
- **용도 2**: 사용자 업로드 파일 저장 (Presigned URL 방식)
- **공부할 것**:
  - 버킷 정책, ACL
  - **Presigned URL**: 클라이언트가 서버를 거치지 않고 직접 S3에 업로드하는 방식. 왜 씀? → 서버 부하 감소, 보안 (직접 노출 없음)
  - 정적 웹 호스팅 설정

#### CloudFront
- **용도**: CDN + HTTPS 처리 (S3 앞단)
- **공부할 것**:
  - CDN이 왜 필요한가 (캐싱, 글로벌 엣지)
  - CloudFront 무효화 (Invalidation) — CI/CD에서 배포 후 캐시 갱신

#### 전체 아키텍처 그림 (말로 설명 연습)
```
사용자 브라우저
    ↓ HTTPS
CloudFront (CDN, 엣지 캐싱)
    ↓
S3 (React 빌드 산출물)
    ↓ /api/v1/* 요청은 백엔드 직접 호출
    ↓ HTTPS + CORS
EC2 t3 (Docker → Spring Boot :8080)
    ├── MySQL (같은 VPC)
    └── Redis (주소 캐싱, 로그인 대기열)

EC2 모니터링 인스턴스 (별도)
    ├── Prometheus (백엔드 :8081/actuator/prometheus 수집)
    └── Grafana (시각화)
```

### 공부 방법 (시간이 없을 때)

**D-4(9/6) 하루만 집중할 내용**

1. `.github/workflows/*.yml` 파일 전부 읽기
   - `backend-docker-publish.yml`: 백엔드 빌드 → 도커 이미지 → DockerHub
   - `frontend-deploy.yml`: 프론트엔드 빌드 → EC2 경유 → S3 업로드 → CloudFront 무효화
   - 각 step의 `name`과 `run`만 읽어도 흐름 파악 가능

2. `docker-compose.yml` 읽기
   - 환경변수, 포트, 메모리 제한, JVM 옵션이 왜 그렇게 설정됐는지

3. 면접 예상 질문 답변 준비
   - "CI/CD 어떻게 구성했나요?" → 위 파이프라인 설명
   - "배포 과정을 설명해보세요" → Docker 이미지 빌드 → DockerHub → EC2 pull 흐름
   - "S3를 파일 업로드에 쓴 이유?" → Presigned URL 방식 + 서버 부하 감소

## 6. 예상 면접 질문 & 모범 답변 키워드

### 프로젝트 전반

**Q. 이 프로젝트가 뭔지 설명해보세요.**
> P2P 근거리 배송 플랫폼. 배송을 요청하는 부르미와 동선 중 배송을 수행하는 드리미를 연결. 한 계정이 두 역할 전환 가능. 핵심 기술 챌린지는 실시간 매칭, 배송 추적.

**Q. 팀에서 본인이 담당한 부분은?**
> 구체적으로 본인이 담당한 도메인/기능을 말하고, 그 과정에서 내린 기술적 판단을 언급.

**Q. 가장 어려웠던 기술적 문제는?**
> STAR 기법: Situation(상황) → Task(과제) → Action(행동) → Result(결과)

---

### Spring / 백엔드

**Q. 세션과 JWT 중 왜 세션을 선택했나요?**
> 키워드: 서버 측 무효화 가능, Redis로 확장성 확보, 토큰 탈취 시 즉시 강제 로그아웃 가능, 모바일 쿠키 보안(SameSite=None)

**Q. JPA를 사용하면서 N+1 문제를 경험했나요?**
> N+1이 뭔지, fetch join / @BatchSize로 해결하는 방법 설명

**Q. @Transactional을 왜 쓰나요?**
> ACID 보장, 특히 원자성. readOnly=true는 스냅샷 모드로 플러시 생략 → 성능 향상

**Q. Redis를 왜 썼나요?**
> 로그인 대기열: 비밀번호 해싱(PBKDF2 210,000회) CPU 바운드 작업을 직렬화해 서버 과부하 방지. 주소 캐싱: 카카오 API 호출 비용 절감 (TTL 7일)

**Q. SSE vs WebSocket 선택 이유?**
> SSE: 서버→클라이언트 단방향, HTTP 표준, 별도 프로토콜 없음, 프록시 친화적. 배송 추적은 클라이언트 업로드(위치 전송)가 있지만 단방향 이벤트 스트림이 주된 패턴이라 SSE 채택.

**Q. Presigned URL이 뭔가요?**
> S3에 직접 업로드할 수 있는 시간 제한 서명된 URL. 서버를 거치지 않아 서버 부하 없고, URL 만료되면 더 이상 업로드 불가해 보안적.

**Q. 모니터링은 어떻게 했나요?**
> Spring Actuator로 /actuator/prometheus 엔드포인트 노출 → 별도 EC2의 Prometheus가 주기적으로 긁어감 → Grafana로 시각화. 메트릭: JVM 힙, HTTP 요청 수, 응답시간 등.

### CI/CD / 인프라

**Q. CI/CD 파이프라인 설명해보세요.**
> 백엔드: main에 PR merge → GitHub Actions가 Java 21 빌드 + 테스트 → Docker 이미지 생성 → DockerHub push → EC2에서 pull → 재시작  
> 프론트엔드: main/develop push → pnpm 빌드 → S3 업로드 → CloudFront 캐시 무효화

**Q. Docker를 왜 썼나요?**
> 환경 일관성 (개발 환경 ≠ 운영 환경 문제 해결), 배포 단순화, 롤백 용이성 (이미지 태그로)

**Q. JVM 메모리를 어떻게 튜닝했나요?**
> t3 EC2(RAM 1GB 수준)에서 Spring Boot가 동작하도록 힙 192MB, 메타스페이스 256MB로 제한. 스택도 512KB로 줄여 스레드당 메모리 절약. MALLOC_ARENA_MAX=2로 glibc 메모리 풀 제한.

---

### 코드 설계

**Q. 공통 응답 포맷은 어떻게 관리했나요?**
> `ResponseBodyAdvice`를 구현한 `CommonResponseAdvice`가 모든 컨트롤러 응답을 자동으로 `{isSuccess, code, message, result}` 형태로 래핑. 컨트롤러는 순수 DTO만 반환.

**Q. 예외 처리는 어떻게 했나요?**
> 도메인별 `ErrorCode` enum이 `BaseErrorCode`를 구현 → `BusinessException(errorCode)` 발생 → `@RestControllerAdvice`의 `GlobalExceptionHandler`가 중앙에서 처리 → 공통 응답 포맷으로 변환.

**Q. 테스트는 어떻게 작성했나요?**
> JUnit 5 + Mockito(BDD 스타일: given/when/then). 서비스 단위 테스트에서 Repository는 Mock. 비즈니스 예외는 `catchThrowable`로 잡아 `errorCode` 비교. 메서드명은 한글 서술형.

### 협업 / 팀워크

**Q. 팀에서 기술적 의견 충돌이 있었나요?**

**Q. 코드 리뷰는 어떻게 했나요?**

**Q. 혼자 개발한 게 아닌데, 전체를 얼마나 이해하나요?**

## 8. [신규] 현대기아 ICT본부 특화 보강 (2026-09-03 리서치 반영)

> 잡플래닛/블라인드/링커리어/자소설닷컴 최신 후기와 2026년 백엔드 채용 트렌드 검색을 반영해 추가한 섹션. 출처는 섹션 끝 참고.

### 8-1. 면접 진행 방식 — PT 발표형이라는 점이 핵심

- 다수 후기 공통: **1차 = PT 발표(직전 배부, 10~15분 준비) + 질의응답**, 다대일(인사 1 + 실무진 2 구성이 흔함) 형식.
- 링커리어 후기(IT 플랫폼 개발직무): PT 발표 15분 + 질의응답 25분(총 40분), 질문의 **98%가 기술 질문**, 인성 질문은 1개 정도.
- 최종면접도 "개발자면 기술 질문이 계속될 가능성 높음" — 1차와 최종을 별개로 준비하지 말 것.
- **시사점**: 현재 계획은 답변 "연습"은 있지만 **발표 형식 리허설**이 없음 → D-3에 타이머 켜고 실제 PT처럼 말하는 연습 추가함(위 참고). 자기소개/프로젝트 소개를 **PT 슬라이드 없이 구두로 15분** 채울 수 있게 스토리 분량을 늘려둘 것 (기존 계획의 "1~2분 버전"은 질의응답 대비용으로만 쓰고, 별도로 15분 풀버전도 준비).

### 8-2. 자료구조 심화 — 현재 계획의 가장 큰 공백

여러 후기에서 "지원 부서에 자주 쓰이는 개념의 자료구조를 깊이 있게" 묻는다고 언급. Spring/JPA 지식만으로는 안 커버되는 **순수 CS 영역**이므로 D-2에 아래를 스피드 리뷰:

- [ ] HashMap 내부 구현 (버킷, 해시 충돌 처리 — 체이닝, 로드팩터, 리사이징), Java 8+에서 트리화(레드블랙트리) 조건
- [ ] ArrayList vs LinkedList — 삽입/삭제/조회 시간복잡도와 실제 사용 시점 차이
- [ ] HashMap vs TreeMap vs LinkedHashMap — 언제 어떤 걸 쓰는가
- [ ] Set 계열(HashSet/TreeSet) 내부적으로 뭘 쓰는지 (HashMap 기반)
- [ ] Stack/Queue를 Java에서 어떻게 구현하는지, Deque를 Stack 대신 쓰는 이유
- [ ] **내 프로젝트 코드에 실제로 등장하는 자료구조**(Redis List/ZSet/Hash, Map, List 등)를 골라 "왜 이 자료구조인가"로 연결 — 순수 이론보다 "내 코드 사례 + 이유" 조합으로 답하는 게 실전에서 강함

### 8-3. 2026년 백엔드 채용 트렌드 — 알고 있다는 티만 내도 되는 것들

검색 결과, 2026년 기술면접에서 출제율이 급상승 중인 토픽:

- **AI/LLM 리터러시**: RAG, AI Agent 개념 이해, 생성형 AI를 실무에 어떻게 통합할 수 있는지에 대한 견해. 프로젝트에 직접 안 썼어도 "이런 식으로 도입해볼 수 있을 것 같다"는 의견 한두 개는 준비
- **대규모 트래픽 대응 아키텍처**: 쿠버네티스, Kafka, Elasticsearch가 "핵심 기술"로 언급됨. 우리 프로젝트는 EC2 단일 인스턴스 + Docker 수준이므로, **"지금 규모에서 트래픽이 늘어나면 어떻게 확장하겠는가"** 질문에 대비한 답 (예: 로드밸런서 + 오토스케일링, DB 읽기 복제본, 캐시 레이어 확대, 메시지 큐 도입 등)을 미리 정리해두면 좋음 — "단순 CRUD 개발자"가 아니라는 인상을 주는 포인트
- 채용 시장 전반이 "CRUD를 넘어 트래픽/장애 대응/확장 가능한 구조를 이해하는 사람" 선호로 이동 중 → 프로젝트 설명 시 이 프레이밍(현재 구조의 한계를 알고, 다음 단계를 그릴 수 있음)을 자연스럽게 섞을 것

### 8-4. 코딩테스트 관련 (참고)

- 현대차그룹 코딩테스트는 자체 플랫폼 **Softeer**에서 진행되며, 난이도는 "네카라보다 쉽고 다른 SI대기업보다 어려운" 수준, **백준 골드2 수준**까지 준비하라는 후기가 일반적.
- (이번 전형에 코딩테스트가 포함되는지는 채용 공고 기준으로 재확인 필요 — 별도 사전과제/코딩테스트 여부에 따라 시간 배분 조정)
