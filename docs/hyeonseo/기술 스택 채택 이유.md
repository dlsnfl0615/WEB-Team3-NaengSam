# 기술 스택 채택 이유 (Infra·DevOps / Backend / Test)

스크린샷 기술 스택 표에서 **프론트엔드 카테고리는 제외**하고, Infra·DevOps / Backend / Test 세
영역을 정리. Test 영역 중 `Vitest`/`Testing Library`는 프론트엔드(React 컴포넌트) 전용 테스트
도구라 이 문서에서도 제외했고, `k6`/`Node.js`/`Playwright`/`JUnit5`/`Mockito`/`AssertJ`는 백엔드를
대상으로 하는 테스트/부하테스트 도구라 포함했다.

각 기술마다 **개념 → 왜 채택했는지(이점) → 대안과 미채택 이유 → 코드상 위치** 순으로 정리.

---

## 1. Infra · DevOps

### Docker / Docker Hub

**개념**: 애플리케이션과 실행 환경(JRE 버전, OS 라이브러리)을 하나의 이미지로 묶어, 어디서
실행하든 동일하게 동작하게 하는 컨테이너 기술. Docker Hub는 그 이미지를 저장·배포하는 레지스트리.

**왜 채택했는지**: "내 로컬에선 되는데 서버에선 안 됨" 문제를 원천 차단한다. 실행 환경이 이미지
안에 고정되므로, CI가 만든 이미지를 어떤 서버에서 pull해도 같게 동작한다. 이미지 태그(`main`,
`main-<PR번호>`)를 분리해 두면 특정 버전으로 즉시 롤백도 가능하다.

**대안과 미채택 이유**: 서버에 바이너리(jar)를 직접 배포하고 JRE를 서버마다 수동 설치하는 방식도
가능했지만, 서버 환경이 조금이라도 다르면 재현 안 되는 버그가 생긴다. 프라이빗 레지스트리로는 AWS
ECR(Elastic Container Registry)도 고려할 수 있었으나, IAM 정책 설정과 리전별 요금이 추가로 필요해
소규모 프로젝트에는 과했다. Docker Hub는 무료이고 GitHub Actions와의 로그인/push 연동이 표준
액션으로 바로 되어 설정이 훨씬 단순했다.

**코드상 위치**: `backend/Dockerfile`(`eclipse-temurin:21-jre` 베이스에 jar만 얹는 얇은 이미지),
`.github/workflows/backend-docker-publish.yml`(이미지 빌드·push), `backend/docker-compose.yml`
(`seoki/symboorm:${IMAGE_TAG:-main}` pull).

### GitHub Actions

**개념**: 깃허브 저장소에 내장된 CI/CD 자동화 도구. 이벤트(PR, push 등)에 반응해 정해진 워크플로우
(YAML)를 실행한다.

**왜 채택했는지**: 코드와 CI 설정이 **같은 저장소**에 있어 별도 CI 서버를 구축·운영할 필요가 없다.
Public 저장소/오픈소스 규모에서는 무료 티어로 충분하다.

**대안과 미채택 이유**: Jenkins는 직접 서버를 띄우고 유지보수해야 해서 관리 부담이 크고, CircleCI/
GitLab CI는 저장소가 GitHub인데 굳이 외부 서비스를 하나 더 붙이는 셈이라 이점이 없었다.

**코드상 위치**: `.github/workflows/backend-test.yml`, `backend-docker-publish.yml`,
`frontend-build.yml`, `frontend-deploy.yml`, `protect_branch.yml`.

### AWS EC2

**개념**: AWS의 가상 서버(VM) 임대 서비스. OS부터 직접 다루는 IaaS.

**왜 채택했는지**: 백엔드·DB·NAT·모니터링을 각각 별도 인스턴스로 나눠서, 보안그룹으로 인스턴스
간 접근을 세밀하게 통제할 수 있었다(예: 액츄에이터 8081을 모니터링 인스턴스 SG에서만 허용). 비용도
직접 조절 가능해서, NAT Gateway(관리형, 시간당+트래픽 과금) 대신 t2.nano 인스턴스에 NAT 기능을
직접 구성해 비용을 낮췄다.

**대안과 미채택 이유**: ECS Fargate나 Elastic Beanstalk 같은 관리형 컨테이너 서비스는 서버 관리
부담이 줄어드는 대신 요금이 더 나오고, 세밀한 네트워크 제어(보안그룹 단위 인스턴스 분리 등)의
자유도가 낮다. 이 프로젝트는 비용에 민감한 사이드 프로젝트라 인스턴스를 직접 운용하며 비용을
낮추는 쪽을 택했다.

**코드상 위치**: `docs/hyeonseo/cicd.md`에 정리된 인스턴스 목록(`symboorm-web`, `symboorm-db`,
`symboorm-nat`, `symboorm-load`), `backend/docker-compose.yml`(메모리 예산에 맞춘 JVM 옵션).

### AWS S3

**개념**: 객체 스토리지(파일을 "버킷"이라는 논리적 공간에 저장). 이 프로젝트는 두 가지 용도로 쓴다
— ① 프론트엔드 정적 파일(`symboorm-s3-front`), ② 사용자 업로드 파일(`symboorm-s3`, 신분증·인증
사진 등).

**왜 채택했는지**: 서버가 파일 바이트를 직접 받지 않고, presigned URL로 클라이언트가 S3에 직접
PUT/GET하게 해서 서버 부하·대역폭을 아낀다. 두 버킷 다 **비공개**로 두고 CloudFront/presigned URL을
통해서만 접근 가능하게 만들어 접근 통제도 확보했다.

**대안과 미채택 이유**: 업로드 파일을 EC2 로컬 디스크에 저장하는 방식은 인스턴스가 재생성되면
데이터가 통째로 사라지고, 여러 인스턴스로 확장할 때 파일을 공유할 방법이 없다. S3는 내구성·가용성이
AWS가 관리해주는 관리형 스토리지라 이런 걱정이 없다.

**코드상 위치**: `domain/upload/config/S3Config.java`, `domain/upload/service/S3Uploader.java`,
`domain/upload/service/S3PresignService.java` (자세한 설계는
`docs/hyeonseo/upload/presigned-url-strategies.md` 참고).

### CloudFront

**개념**: AWS의 CDN(콘텐츠 전송 네트워크). 엣지 서버에 콘텐츠를 캐싱해 가까운 곳에서 응답한다.

**왜 채택했는지**: S3를 퍼블릭으로 열지 않고도(CloudFront 서비스 프린시펄에만 접근 허용) HTTPS·
캐싱·접근 통제를 한 곳에서 관리할 수 있다. `/api/*` 경로는 캐싱을 끄고 백엔드(nginx)로 프록시해서,
프론트·백엔드가 브라우저 입장에서 동일 출처처럼 동작하게 만들어 CORS 이슈도 회피했다.

**대안과 미채택 이유**: S3 정적 웹호스팅을 그대로 퍼블릭으로 여는 방식도 가능했지만, 버킷을
비공개로 유지할 수 없고 HTTPS도 별도로 구성해야 한다. nginx만으로 정적 파일까지 서빙하는 방식도
가능했지만, 전 세계 엣지 캐싱 같은 이점이 없고 정적 자산과 API 트래픽의 캐싱 정책을 한 서버에서
같이 관리해야 해서 더 복잡해진다.

**코드상 위치**: `docs/hyeonseo/CloudFront S3 배포와 API 요청 흐름.md`에 전체 흐름 정리. 코드
자체보다는 AWS 콘솔 설정(behavior 2개)과 `frontend-deploy.yml`의 `aws cloudfront
create-invalidation` 호출이 실체다.

### Prometheus 3.1 / Grafana 11.5

**개념/왜/대안/코드 위치**: 방금 정리한 `docs/hyeonseo/모니터링 스택.md`에 상세히 있음. 요약하면
— Actuator가 노출한 지표를 Prometheus가 15초마다 pull로 긁어가고, Grafana가 시각화한다. AWS
CloudWatch(관리형)도 대안이었지만, 이 프로젝트가 만든 커스텀 메트릭(SSE 연결 수, 카카오 캐시
히트율)을 자유롭게 정의하고 무료로 운용하기엔 Micrometer + Prometheus 조합이 더 유연했다.

## 2. Backend

### Java 21

**개념**: LTS(장기 지원) 버전인 17보다 최신인 논-LTS 릴리스. 가상 스레드(virtual thread), record
패턴, 패턴 매칭 switch 등 최신 문법을 포함한다.

**왜 채택했는지**: **가상 스레드**를 실제로 세 곳에서 활용한다 — SSE 이벤트 전송을 순서 보장하며
처리하는 단일 스레드(`SseService`), 매칭 상태 변경을 직렬화하는 단일 워커(`MatchingEngine`), 웹푸시
전송을 오프로드하는 스레드 풀(`NotificationService`). 가상 스레드는 블로킹 I/O 중에도 OS 스레드를
점유하지 않아 적은 자원으로 많은 동시 작업을 처리할 수 있다. **패턴 매칭 switch**는
`GlobalExceptionHandler.resolve(...)`에서 예외 타입별 분기를 간결하게 표현하는 데 쓰인다.

**대안과 미채택 이유**: LTS인 17을 썼다면 더 오랜 지원 기간을 보장받지만, 가상 스레드(21에서 정식
기능화)를 못 쓴다. 사이드 프로젝트라 장기 지원보다 최신 기능 실습이 더 가치 있다고 판단한 것으로
보인다. Kotlin도 대안이었지만 팀 전체가 Java에 익숙해 학습 비용 없이 바로 생산성을 낼 수 있는
Java를 택했다.

**코드상 위치**: `SseService.java`(`Executors.newSingleThreadExecutor(Thread.ofVirtual()...)`),
`MatchingEngine.java`(`Thread.ofVirtual().start(...)`), `NotificationService.java`(가상 스레드 기반
`ThreadPoolExecutor`), `GlobalExceptionHandler.java`(`switch (e) { case ... }`).

### Spring Boot 4.1

**개념**: 자바 웹 애플리케이션을 빠르게 구성해주는 프레임워크. 자동 설정, 내장 톰캣, 의존성 관리를
제공한다.

**왜 채택했는지**: Spring Data JPA·Security·Actuator·springdoc 같은 생태계 전체가 통합돼 있어
개발 속도가 빠르다. 팀 전원이 학습 곡선 없이 바로 활용 가능한 프레임워크였다.

**대안과 미채택 이유**: Quarkus/Micronaut는 기동 속도·메모리 사용량이 더 적어 컨테이너 환경에
유리하지만, 생태계가 Spring보다 작고 팀 숙련도가 없어 오히려 개발 속도가 떨어질 위험이 있었다.

**코드상 위치**: 프로젝트 전체. `backend/build.gradle`의 `org.springframework.boot` 플러그인
버전.

### Spring Data JPA

**개념**: JPA(ORM 표준)의 구현체(Hibernate)를 감싸, 리포지토리 인터페이스 선언만으로 CRUD·쿼리를
자동 생성해주는 라이브러리.

**왜 채택했는지**: 반복적인 CRUD 코드를 줄여준다. 다만 이 프로젝트는 `@ManyToOne`/`@OneToMany`
같은 연관관계 매핑을 **의도적으로 안 쓰고**, 엔티티 간 관계를 원시 UUID 필드로만 표현한다(자세한
이유는 이전 대화 및 `jpa-interview.md` 참고) — JPA의 객체 그래프 탐색 기능보다는 "선언만으로 파생
쿼리를 만들어주는" 편의만 취하고, 실제 조회는 JPQL/네이티브 쿼리로 명시적으로 짜는, MyBatis에
가까운 방식으로 JPA를 활용한다.

**대안과 미채택 이유**: MyBatis/JOOQ는 SQL을 직접 제어할 수 있어 이 프로젝트의 "관계는 ID로만"
스타일과 오히려 더 잘 맞았을 수 있지만, 단순 CRUD(파생 쿼리)는 JPA가 훨씬 적은 코드로 해결해준다.
"단순 조회는 파생 쿼리, 복잡한 조회는 JPQL/네이티브"로 절충한 것.

**코드상 위치**: 모든 `*Repository extends JpaRepository<T, UUID>` 인터페이스.
`OrderRepository.findByOrderId`(`@Lock`), `UploadSessionRepository.markConsumedIfIssued`
(`@Modifying` + JPQL)처럼 동시성이 필요한 곳은 직접 쿼리를 짠다.

### MySQL

**개념**: 오픈소스 관계형 DBMS.

**왜 채택했는지**: 팀 숙련도가 가장 높은 RDBMS였고, EC2에 직접 설치해 RDS(관리형) 대비 비용을
낮췄다.

**대안과 미채택 이유**: PostgreSQL은 더 엄격한 표준 준수·풍부한 타입을 제공하지만 팀이 MySQL에
더 익숙했다. RDS는 백업·장애조치가 자동화되지만 요금이 EC2 직접 운용보다 비싸 사이드 프로젝트
예산에 안 맞았다. 다만 EC2에 직접 설치한 대가로 "리눅스 MySQL은 테이블명 대소문자를 구분한다"는
운영 환경 특유의 문제를 실제로 겪었다(`backend/CLAUDE.md`의 네이티브 쿼리 규칙 — DDL과 똑같은
대문자로 테이블명을 써야 하는 이유).

**코드상 위치**: `backend/sql/sym-boorm-ddl.sql`(대문자 테이블명 DDL),
`application.properties`(`DATABASE_URL` 등 환경변수 주입).

### 세션 기반 인증

**개념**: 로그인 상태를 서버(톰캣)의 `HttpSession`에 저장하고, 클라이언트는 세션 ID만 쿠키
(JSESSIONID)로 들고 다니는 인증 방식.

**왜 채택했는지**: 서버가 세션을 직접 들고 있어 **강제 로그아웃**(다른 기기 로그인 시 이전 세션
즉시 무효화)이 쉽다. JWT처럼 클라이언트가 토큰을 들고 있는 방식은 서버가 발급한 토큰을 회수할
방법이 없어(만료 전까지는 계속 유효) 이런 즉시 무효화가 어렵다.

**대안과 미채택 이유**: JWT(토큰 기반)는 서버가 상태를 안 들고 있어(stateless) 여러 서버로 수평
확장하기 쉽다는 장점이 있지만, 이 프로젝트는 지금 단일 인스턴스 전제라 그 장점이 필요 없었고,
반대로 "즉시 강제 로그아웃"이라는 이 서비스의 요구사항(계정당 세션 1개 강제, 다른 기기 로그인 시
이전 기기 즉시 로그아웃)에는 세션 방식이 훨씬 자연스러웠다. (다만 세션이 톰캣 인메모리에만 있어
다중 인스턴스로 확장하려면 Redis 기반 세션 저장소 도입이 필요하다는 한계는 이전에 정리한 그대로다.)

**코드상 위치**: `global/session/LoginSession.java`, `ActiveSessionRegistry.java`,
`LoginCheckInterceptor.java`, `@LoginUser`/`@AdminUser` 커스텀 애노테이션.

### SSE

**개념**: 서버가 HTTP 응답을 끝내지 않고 계속 이어서 써서, 클라이언트에 실시간 이벤트를 단방향으로
흘려보내는 표준 기술.

**왜 채택했는지**: 매칭 오퍼·배달 위치처럼 "서버→클라이언트 단방향" 이벤트가 이 서비스의 핵심
실시간 요구사항이고, 클라이언트가 서버로 실시간으로 보낼 데이터(양방향)는 필요 없었다. HTTP
표준이라 별도 프로토콜 업그레이드가 필요 없고 프록시(nginx, CloudFront)와도 잘 맞는다.

**대안과 미채택 이유**: WebSocket은 양방향 통신을 지원하지만, 이 프로젝트엔 양방향이 필요한
지점이 없어 오히려 프로토콜이 더 무겁고 프록시/로드밸런서 설정이 더 까다롭다(관련 위키:
"실시간 배달 상태 전달에 SSE를 선택한 이유"). Long polling도 대안이었지만 매 응답마다 새 연결을
맺어야 해 지연이 크고 서버 부하도 더 든다.

**코드상 위치**: `global/sse/*`(`SseConnectionManager`, `SseService`, `SseController`),
프론트엔드 `shared/lib/sse/*`.

### Swagger (springdoc-openapi)

**개념**: 컨트롤러 코드의 애노테이션을 스캔해 OpenAPI 스펙을 자동 생성하고, Swagger UI로 문서를
보여주는 라이브러리.

**왜 채택했는지**: 코드와 문서가 항상 동기화된다(`@ApiErrorCodes` 같은 커스텀 애노테이션이 실제
에러코드 enum 값을 그대로 읽어 문서화). 이게 특히 이득이 컸던 이유는, 프론트가 **Orval**로 이
OpenAPI 스펙을 그대로 읽어 TypeScript API 클라이언트를 자동 생성하기 때문이다 — 백엔드가 API를
바꾸면 프론트 타입까지 한 번에 갱신되는 파이프라인이 만들어진다.

**대안과 미채택 이유**: Notion이나 Postman Collection으로 API 문서를 수동 관리하는 방법도
있었지만, 코드가 바뀔 때마다 사람이 문서를 따라 고쳐야 해서 금방 어긋난다. 자동 생성 방식은 그럴
위험이 없다.

**코드상 위치**: `global/swagger/*`(`SwaggerConfig`, `ApiErrorCodes`, 커스터마이저들),
`frontend/orval.config.ts`.

### Kakao Local API (좌표 변환·도보 길찾기)

**개념**: 카카오가 제공하는 지도/위치 기반 API. 주소→좌표 변환(지오코딩), 도보 경로 탐색을
제공한다.

**왜 채택했는지**: 국내 서비스 특성상 한국 도로명주소 체계를 가장 정확히 처리하고, 개인/소규모
프로젝트가 접근하기 쉬운 무료 쿼터를 제공한다.

**대안과 미채택 이유**: Google Maps API는 전 세계 커버리지가 넓지만 한국 상세 주소 인식이 카카오
대비 약하고 과금 체계가 더 복잡하다. 네이버 지도 API도 대안이었지만 팀이 카카오 개발자 문서/커뮤니티
자료에 더 익숙했다.

**코드상 위치**: `domain/address/service/KakaoCoordinatesService.java`,
`KakaoDirectionsService.java`(+ 캐싱 데코레이터 `Cached*Service`, Redis 캐시 설계는
`docs/hyeonseo/모니터링 스택.md`의 카카오 캐시 메트릭 절 참고).

### Solapi

**개념**: 국내 SMS/알림톡 발송 대행 서비스(API로 문자를 보내주는 SaaS).

**왜 채택했는지**: 국내 통신사 규제(발신번호 사전 등록 등)에 맞춰진 국내 특화 서비스라 인증문자·
드리미 무소식 알림처럼 실제 한국 휴대폰으로 문자를 보내는 요구사항에 바로 맞았다.

**대안과 미채택 이유**: AWS SNS(SMS 기능)나 Twilio 같은 해외 서비스도 국내 발송이 가능하지만,
국내 스팸 규제·발신번호 사전등록 절차 대응이 국내 서비스보다 복잡하고 비용도 더 든다.

**코드상 위치**: `domain/user/sms/SolapiSmsSender.java`, `SolapiProperties.java`,
`domain/user/service/SmsVerificationService.java`. `solapi.enabled=false`인 로컬에서는
`DevSmsSender`가 대신 로그만 남긴다.

### Web Push (VAPID)

**개념**: 브라우저 표준 Push API를 이용해, 앱을 안 켜놔도 서버가 알림을 보낼 수 있게 하는 기술.
VAPID는 발신자를 식별하는 서명 키 쌍.

**왜 채택했는지**: PWA 기반인 이 서비스가 네이티브 앱처럼 잠금화면 알림을 보내면서도, 특정
플랫폼(iOS/Android)에 종속되지 않는다 — 표준 브라우저 API라 어떤 브라우저든 동작한다.

**대안과 미채택 이유**: Firebase Cloud Messaging(FCM)은 안드로이드/구글 생태계에 강하지만, 결국
구글 계정·프로젝트에 종속되고 iOS Safari PWA 지원이 상대적으로 늦었다. 표준 Web Push(VAPID)를
직접 구현하면 특정 벤더에 안 종속되고, 이 프로젝트처럼 자체 서버가 이미 있는 경우 별도 중개
서비스 없이 바로 서명·전송할 수 있다.

**코드상 위치**: `global/notification/WebPushSender.java`, `WebPushProperties.java`,
`PushSubscriptionService.java`(구독 관리).

## 3. Test (백엔드 대상)

### JUnit 5 / Mockito / AssertJ

**개념**: 자바 표준 테스트 프레임워크(JUnit5) + Mock 객체 생성 도구(Mockito) + 가독성 좋은 검증
문법을 제공하는 라이브러리(AssertJ).

**왜 채택했는지**: Spring Boot가 기본으로 통합 지원하는 조합이라 별도 설정이 거의 필요 없다.
Mockito의 BDD 스타일(`given/when/then`)이 `backend/CLAUDE.md`의 테스트 컨벤션과 잘 맞는다.

**대안과 미채택 이유**: TestNG나 Spock(Groovy 기반)도 대안이었지만, Spock은 Groovy 문법을 새로
배워야 하고 TestNG는 Spring Boot 생태계에서 JUnit5보다 지원이 약하다.

**코드상 위치**: `backend/src/test/java/**` 전체.

### k6

**개념**: JavaScript로 시나리오를 작성하는 오픈소스 부하테스트 도구. 순수 HTTP 요청 위주의 대량
부하를 만드는 데 특화돼 있다.

**왜 채택했는지**: N+1 쿼리 같은 순수 API 성능 문제를 검증할 때, 브라우저를 띄우지 않고 가볍게
대량의 HTTP 요청만 만들면 되므로 k6가 적합했다.

**대안과 미채택 이유**: JMeter는 GUI 기반이라 스크립트를 코드로 관리(버전 관리, 리뷰)하기
불편하고, Gatling(Scala)은 팀이 익숙하지 않은 언어였다. k6는 JS라 프론트/백엔드 개발자 모두 바로
읽고 짤 수 있었다.

**코드상 위치**: `index-test/n-plus-1-nearby-test/k6/nearby-calls.js`.

### Node.js

**개념**: 브라우저 밖에서 자바스크립트를 실행하는 런타임.

**왜 채택했는지**: 부하테스트 스크립트(계정 세팅, 지도 핀 시뮬레이션 등)를 짤 때 프론트와 같은
언어(JS/TS)를 써서 팀 전체가 진입장벽 없이 스크립트를 이해·수정할 수 있게 했다.

**대안과 미채택 이유**: 같은 스크립트를 Python으로 짤 수도 있었지만, 프론트엔드 팀원들이 이미
익숙한 JS/npm 생태계를 그대로 쓰는 게 협업에 더 유리했다.

**코드상 위치**: `matchingtest/`, `matchingtest-cell/`의 `*.mjs` 스크립트, `package.json`.

### Playwright

**개념**: 여러 브라우저(Chromium/Firefox/WebKit)를 자동화해 실제 사용자처럼 웹앱을 조작하는
E2E 테스트/자동화 도구.

**왜 채택했는지**: 매칭 부하테스트가 "디버그 API가 아니라 로그인·SSE·주문 생성·수락·확정을 전부
운영과 같은 경로로" 태우는 걸 목표로 했기 때문에(`matchingtest/README.md`), 실제 브라우저를 여러
개 동시에 띄워 각각 독립된 사용자처럼 동작시킬 수 있는 도구가 필요했다. Playwright는 여러 브라우저
컨텍스트를 병렬로 가볍게 띄우는 데 강점이 있다.

**대안과 미채택 이유**: Selenium은 역사가 길지만 병렬 컨텍스트 처리와 최신 웹 API(SSE 등) 지원이
Playwright보다 번거롭고, Cypress는 기본적으로 한 브라우저 탭에서 단일 테스트 흐름 위주라 "동시
접속자 다수 시뮬레이션"에는 Playwright의 멀티 컨텍스트 모델이 더 적합했다.

**코드상 위치**: `matchingtest/`(실행 단계 4/5 "클라이언트 기동"이 Playwright로 매칭 대기 화면까지
브라우저를 올리는 단계).
