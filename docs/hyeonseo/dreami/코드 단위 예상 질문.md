# dreami 도메인 — 코드 단위 예상 질문

`upload/코드 단위 예상 질문.md`, `address/코드 단위 예상 질문.md`와 같은 목적·형식. 카테고리:
① 동시성 처리(다른 도메인과 비교), ② 이 코드에 문제가 생길 수 있는 지점, ③ 애노테이션·구조,
④ 대체 가능한 방법이 있는데 왜 지금 방식을 골랐는지.

> 대상 파일: `Dreami`, `DreamiCd`, `DreamiRequestDeniedDetails`, `DreamiRepository`, `DreamiService`,
> `DreamiActivationChecker`, `DreamiAuthController`, `DreamiApproveController`, `DreamiErrorCode`.

## 1. 동시성 처리 — 왜 이렇게 했는지 (다른 도메인과 비교)

**Q1. `DreamiService.acceptOffer`(드리미의 제안 수락)에서 동시성을 어떻게 처리했는지 설명해
주세요.**

두 겹으로 확인합니다.

```java
@Transactional
public void acceptOffer(UUID offerId, UUID dreamiId) {
    if (!matchingService.isDreamiOfferOwner(offerId, dreamiId)) {
        throw new BusinessException(MatchingErrorCode.NOT_OFFER_OWNER);
    }
    if (!matchingService.isDreamiOfferAcceptable(offerId, dreamiId)) {  // ① 인메모리 매칭 엔진 상태 확인
        throw new BusinessException(MatchingErrorCode.OFFER_EXPIRED);
    }
    ...
    Orders order = orderRepository.findByOrderId(orderId)  // ② DB 비관적 락으로 재확인 — OrderRepository
            .orElseThrow(...);

    if (order.getOrderCd() == OrderCd.PENDING_BOORMI_CONFIRMATION) {
        if (dreamiId.equals(order.getDreamiId()) && offerId.equals(order.getPendingOfferId())) {
            return; // 본인의 재시도 — 멱등하게 통과
        }
        throw new BusinessException(MatchingErrorCode.ALREADY_ACCEPTED_BY_OTHER);
    }
    if (order.getOrderCd() != OrderCd.MATCHING) {
        throw new BusinessException(MatchingErrorCode.NOT_ACCEPTABLE_STATUS);
    }
    order.markPendingBoormiConfirmation(dreamiId, offerId);
    ...
}
```

- **①은 매칭 엔진(인메모리, 단일 스레드) 쪽 상태**를 봅니다 — 이 오퍼가 지금 이 드리미에게 유효한
  상태(OFFERED)인지, TTL이 지나지 않았는지.
- **②는 DB 쪽 진실**을 봅니다 — `OrderRepository.findByOrderId`는 `@Lock(PESSIMISTIC_WRITE)`가
  걸려 있어서, 이 트랜잭션이 끝날 때까지 다른 트랜잭션이 같은 주문 행을 못 건드립니다. 락을 잡은
  뒤에 주문 상태를 **다시 한번** 확인하는 이유가 주석에 명확합니다 — *"락을 잡은 뒤 재확인 — 다른
  드리미가 먼저 커밋해 이미 MATCHING이 아니게 됐을 수 있다."*

**왜 둘 다 필요한가**: ①만 있으면, 엔진에서 "가능"으로 확인한 순간과 DB 트랜잭션이 실제로 실행되는
순간 사이에 다른 드리미가 먼저 커밋해버릴 수 있습니다(엔진 확인은 락이 없는 스냅샷 조회이기
때문). ②만 있으면, TTL이 지나 엔진이 이미 내부적으로 만료 처리한 오퍼인데도 DB 상 주문 상태만
보고는 구분이 안 될 수 있습니다. 그래서 "엔진에서 먼저 걸러내고, DB 락으로 최종 확정한다"는 이중
방어가 필요합니다.

**Q2. 멱등성 판단에서 `dreamiId`만 비교하지 않고 `offerId`(`order.getPendingOfferId()`)까지 같이
비교합니다. 왜 `dreamiId`만으로는 부족한가요?**

같은 드리미라도 "지금 재시도로 들어온 요청"과 "그 사이에 새로 발급된 다른 오퍼"를 구분해야 하기
때문입니다. 시나리오: 드리미 A가 오퍼 1을 수락 → 네트워크 문제로 응답을 못 받고 클라이언트가 재시도
→ 그 사이 서버에서는 오퍼 1 처리가 타임아웃돼 실패하고 오퍼 2가 다시 A에게 발급됨 → A가 오퍼 2를
수락해 `PENDING_BOORMI_CONFIRMATION`으로 이미 전이됨 → 이때 **오퍼 1에 대한 원래의 재시도 요청**이
뒤늦게 도착합니다. `dreamiId`만 봤다면 "같은 드리미의 재시도"로 착각해 조용히 통과(return)시켰을
텐데, 실제로는 **다른 오퍼(오퍼 1)**에 대한 낡은 요청입니다. `offerId`까지 같이 비교해야 "정확히
이 오퍼에 대한 재시도"만 멱등하게 통과시키고, 그 외의 경우는 `ALREADY_ACCEPTED_BY_OTHER`로 정확히
거절할 수 있습니다.

**Q3. `acceptOffer` 마지막에 `matchingService`를 직접 호출하지 않고
`eventPublisher.publishEvent(new DreamiAcceptedEvent(offerId))`로 이벤트만 발행합니다. 왜
동기적으로 바로 안 부르나요?**

이건 이전에 정리한 "매칭 확정 후 Delivery가 생성되지 않는 고아 Order 문제"(`ce8f1cbd` 커밋)와
**정확히 같은 클래스의 문제를 예방하는 패턴**입니다. 매칭 엔진은 이 트랜잭션과 다른 스레드에서
동작하므로, 만약 여기서 엔진에 즉시 제출했다면 `order.markPendingBoormiConfirmation(...)`이 아직
커밋되지 않은 상태에서 엔진이 그 주문을 다시 조회할 수 있고, 커밋 전이라 상태 변경을 못 본 채
잘못 판단할 위험이 있습니다. 그래서 `@TransactionalEventListener(phase = AFTER_COMMIT)`(주석에
언급된 대로, `MatchingService`의 리스너가 이 역할)로 **이 트랜잭션이 실제로 커밋된 뒤에만** 엔진에
제출되도록 순서를 강제합니다. 즉 upload 도메인처럼 새로운 패턴이 아니라, 이 프로젝트가 "DB 트랜잭션
→ 비동기 인메모리 엔진"으로 넘어가는 모든 지점에 일관되게 적용하는 원칙입니다.

## 2. 이 코드에 문제가 생길 수 있는 지점

**Q4. `DreamiCd` enum에 `REVIEWING`이라는 값이 있는데, 실제로 이 상태로 전이시키는 코드가 어디
있나요?**

**없습니다.** `Dreami` 엔티티를 보면 상태 전이는 `create()`(→`REQUESTED`), `approve()`(→`APPROVED`),
`reject()`(→`REJECTED`) 세 메서드뿐이고, `REVIEWING`으로 바꾸는 코드는 프로젝트 전체에 없습니다
(`grep`으로 확인해도 `UserDto`의 주석 — *"REQUESTED/REVIEWING/APPROVED/REJECTED"* — 에만 문서상
언급될 뿐 실제로 세팅되는 곳이 없습니다). 즉 **선언은 돼 있지만 도달 불가능한 상태**입니다. 아마
"관리자가 검토를 시작하면 REVIEWING으로 바꾸는" 기능이 기획엔 있었는데 구현이 안 됐거나, 나중을
위해 미리 만들어둔 자리로 보입니다. 면접에서 이 지점을 짚히면 "구현이 안 된 걸 인지하고 있다"고
정직하게 답하는 게 낫습니다 — `listPendingReviews()`가 `REQUESTED` 상태만 조회하는 것도, 지금
구조에서는 `REVIEWING`을 거칠 일이 없으니 자연스럽게 들어맞는 우연의 일치에 가깝습니다.

**Q5. `DreamiAuthController.verifyUploadedDocuments`는 `assertNotAlreadyApproved` →
`checkUpload`(신분증) → `checkUpload`(범죄경력) → `saveVerificationFileKeys` 순서로 **서로 다른
4개의 `@Transactional` 메서드**를 순차 호출합니다. 중간에 실패하면 어떻게 되나요?**

이건 실제로 눈여겨볼 지점입니다. 각 호출이 독립된 트랜잭션이라, 예를 들어 두 `checkUpload`가 모두
성공(업로드 세션을 CONSUMED로 소비)한 **직후**, `saveVerificationFileKeys` 호출에서 DB 커넥션
장애 같은 게 발생하면 — 업로드 세션은 이미 "소비 완료"로 확정됐는데 `Dreami` row는 갱신되지 않은
채로 끝날 수 있습니다. 이건 앞서 다룬 "매칭 확정 후 Delivery 미생성" 버그와 같은 계열의 문제
(DB 트랜잭션 여러 개를 순서대로 실행하는데 원자성이 보장되지 않는 것)입니다.

다만 심각도는 다릅니다 — Delivery 미생성은 **자동화된 매칭 흐름**이라 사용자가 손쓸 방법이 없는
반면, 여기는 **사람이 능동적으로 재시도할 수 있는 흐름**입니다. `checkUpload`가 이미 소비한
키라도, 클라이언트가 다시 presigned URL을 발급받아 파일을 재업로드하면 새 key로 다시
`verifyUploadedDocuments`를 호출할 수 있습니다(`UploadSessionService.issue`가 매번 새 key를
만들어주므로). 즉 "완전히 막히는" 실패는 아니고 "사용자가 한 번 더 시도해야 하는" 실패입니다. 다만
이걸 하나의 트랜잭션으로 묶거나, 실패 시 보상 이벤트를 발행하는 방식으로 더 견고하게 만들 여지는
분명히 있습니다.

**Q6. 재제출 시 `idCardNewlyConsumed`와 `criminalRecordNewlyConsumed` 중 하나만 `true`여도
`saveVerificationFileKeys`를 호출합니다. 이때 왜 클라이언트가 이전에 이미 통과한 파일의 key까지
다시 보내야 하나요?**

`saveVerificationFileKeys`는 **요청으로 받은 두 key로 통째로 덮어쓰는 방식**이기 때문입니다.
서버는 "이전에 어떤 idCardKey를 썼는지"를 별도로 기억하고 있다가 부분 갱신을 하는 게 아니라,
매번 요청에 실린 두 값 그대로 새 `Dreami` row(사실상 upsert)를 만듭니다. 그래서 범죄경력조회서만
반려돼서 그 파일만 다시 올렸다면, 클라이언트는 **이미 통과했던 신분증 사진의 key도 그대로
다시 실어서** 요청해야 서버가 "이전 값을 잃어버리지" 않습니다. 주석에도 이 상황이 명시돼 있습니다
— *"범죄 이력 조회서는 통과되지 않아서 이 파일만 다시 제출해야 할 때 신분증 사진은
newlyConsumed = false"*. 서버가 상태를 기억 안 해도 되니 구현은 단순해지지만, **클라이언트가 이전
제출값을 계속 들고 있어야 하는 책임**을 진다는 트레이드오프입니다.

## 3. 애노테이션·구조 관련 질문

**Q7. `DreamiActivationChecker`는 `@Service`가 아니라 `@Component`이고, `DreamiService`를 안 쓰고
리포지토리 2개(`BoormiRepository`, `DreamiRepository`)만 직접 의존합니다. 왜 서비스 계층을 안
거치고 이렇게 따로 뺐나요?**

클래스 javadoc에 이유가 명확합니다 — *"리포지토리에만 의존하는 잎 컴포넌트로 둔다. 서비스를
참조하면 매칭↔배달↔유저 사이에 순환 참조가 생긴다."* "이 계정이 드리미로 활동 가능한 상태인가"
(활성화 + 승인)라는 판정은 배달 시작 검증처럼 **여러 도메인에서 공통으로 필요한 조회**입니다. 만약
이 로직을 `DreamiService`(또는 다른 도메인의 서비스) 안에 두고 다른 도메인이 그 서비스를
참조하게 만들면, `backend/CLAUDE.md`가 원칙으로 삼는 "도메인 간 독립성"이 깨지고 A→B→A 같은
순환 의존이 생길 위험이 커집니다. 그래서 **가장 아래 계층(리포지토리)만 아는 얇은 컴포넌트**로
격리해, 어느 도메인에서 호출하든 순환 걱정 없이 재사용할 수 있게 만든 것입니다. `@Component`를
쓴 것도 upload 도메인의 `S3Uploader`처럼 "비즈니스 로직 서비스"가 아니라 "여러 곳에서 재사용하는
판정 유틸"이라는 성격을 드러내는 선택입니다.

**Q8. `DreamiService.assertNotAlreadyApproved`는 `dreamiRepository.findById`(락 없음)를 쓰고,
`saveVerificationFileKeys`는 `dreamiRepository.findByDreamiId`(`@Lock(PESSIMISTIC_WRITE)`)를
씁니다. 왜 앞단은 락을 안 걸었나요? 처음부터 락을 걸면 안 되나요?**

주석에 설계 의도가 그대로 적혀 있습니다 — *"락 없이 빠르게 걷어내는 사전 체크용이고, 실제
안전장치는 `saveVerificationFileKeys` 내부의 락 걸린 재확인이다."* `assertNotAlreadyApproved`는
컨트롤러 흐름 초입에서 "이미 승인된 사람이 굳이 여기까지 올 필요가 있나"를 빠르게 걸러내는
용도입니다. 이 시점에 락을 걸면, 대부분 통과할 케이스(재신청이 아닌 정상 흐름)에서도 매번 DB
행 락을 잡았다가 푸는 불필요한 비용이 듭니다. 반면 실제로 데이터를 쓰는(`save`) 시점의
`saveVerificationFileKeys`는 "그 사이 관리자가 승인을 확정했을 수도 있는" 진짜 경합 구간이라
반드시 락으로 보호해야 합니다. **"자주 실행되고 대부분 그냥 통과하는 사전 체크는 가볍게, 실제
쓰기가 일어나는 마지막 순간만 무겁게 보호한다"**는 원칙입니다.

**Q9. `DreamiService.getOfferItemPhoto`는 왜 물품 사진 URL 조회를 오퍼 수락/거절과 합치지 않고
별도 API로 뗐나요?**

메서드 주석에 이유가 있습니다 — *"매칭 엔진의 SSE 발송 경로(단일 스레드로 직렬화됨)에 S3 조회를
얹지 않기 위해."* 매칭 오퍼가 여러 드리미에게 SSE로 팝업 알림을 뿌리는 경로는 `MatchingEngine`의
**단일 워커 스레드**를 씁니다(이전에 정리한 그 구조). 만약 오퍼 알림 payload 자체에 "물품 사진
URL"까지 포함시키려 했다면, 그 URL을 만들기 위한 S3 presigned URL 발급(약간의 계산/조회 비용)이
매번 이 단일 스레드 안에서 일어나게 됩니다. 오퍼가 몰리는 상황에서 이 병목 하나가 전체 매칭 처리
속도를 늦출 수 있습니다. 그래서 사진 URL은 알림 payload에 안 담고, **드리미가 실제로 사진 버튼을
눌렀을 때만** 별도 API로 그때그때 조회하도록 떼어놨습니다 — "무거운 I/O는 절대 단일 스레드 핫패스에
얹지 않는다"는 원칙이 여기서도 반복됩니다.

## 4. 대체 가능한 방법이 있는데 왜 지금 방식을 골랐는지

**Q10. `DreamiService.goOnline`은 "이미 온라인 상태"인 걸 막지 않습니다. 중복 온라인 전환 요청을
그냥 거부하면 더 간단하지 않았나요?**

메서드 주석에 이유가 있습니다 — *"클라이언트의 온라인 상태는 메모리에만 있어 새로고침하면
사라지는데, 여기서 거절해버리면 화면이 오프라인으로 굳은 채 되돌릴 방법이 없어진다."* 드리미
클라이언트는 "나 지금 온라인인가"를 서버에 물어보지 않고 자체 메모리 상태로 관리합니다. 만약
서버가 "이미 온라인이니 거부"를 하면, 새로고침으로 클라이언트 상태가 초기화된 드리미가 다시
온라인 전환을 시도할 때마다 거부당해서 **영원히 오프라인 화면에 갇히는** 상황이 생깁니다. 그래서
"이미 온라인"이어도 그냥 다시 등록을 허용하고, 실제 중복 처리(같은 드리미를 매칭 후보 목록에
두 번 넣는 것 등)는 더 아래 계층인 `matchingService.registerDreami`가 멱등하게 처리하도록
책임을 넘겼습니다. **"거부해서 막는 것"보다 "받아주고 아래에서 멱등하게 흡수하는 것"이 클라이언트
상태 유실 시나리오에 더 안전하다**는 판단입니다.

**Q11. `Dreami.approve()`/`reject()`가 왜 `DreamiService`에서 필드를 직접 바꾸지 않고 엔티티
메서드로 감싸져 있나요? Setter를 열어두면 더 간단하지 않았나요?**

`backend/CLAUDE.md`의 엔티티 규칙(정적 팩토리로만 생성, setter 없음)을 그대로 따른 것입니다.
`approve()`/`reject()`는 단순히 필드 하나를 바꾸는 게 아니라 **관련된 여러 필드를 함께, 항상 같은
규칙으로** 바꿉니다 — `approve()`는 `requestCd`뿐 아니라 `reviewDtm`도 같이 채우고, `reject()`는
`requestCd` + `reviewDtm` + `rejectDetail` 세 개를 한 번에 바꿉니다. 만약 setter를 열어뒀다면
호출부(`DreamiService`)가 이 세 필드를 매번 순서대로, 빠짐없이 챙겨야 하고 실수로 하나를 빠뜨릴
위험이 생깁니다. 엔티티가 "상태 전이 하나 = 메서드 하나"로 캡슐화하면, **호출부는 의도(승인한다/
반려한다)만 표현하고 "그 상태에서 정확히 뭘 바꿔야 하는지"는 엔티티 자신이 책임진다**는 게 이
패턴의 핵심입니다.

**Q12. 드리미 인증 반려 사유(`rejectDetail`)를 `Dreami` 엔티티 필드로도 갖고 있는데, 왜
`DreamiRequestDeniedDetails`라는 별도 테이블에도 똑같이 저장하나요? 중복 아닌가요?**

의미가 다릅니다. `Dreami.rejectDetail`은 **가장 최근 반려 사유 하나**만 담는, 현재 상태의 일부입니다
(재신청하면 `Dreami` row 자체가 새로 만들어지므로 이전 반려 사유는 사라집니다 — Q6에서 다룬
"매번 새 row로 덮어쓰는" 설계와 같은 맥락). 반면 `DreamiRequestDeniedDetails`는 `rejectReview`가
호출될 때마다 **새 행을 계속 추가**하는 이력 테이블입니다. `DreamiService.getDreamiProfile`이
`dreamiRequestDeniedDetailsRepository.countByDreamiId(dreamiId)`로 **반려 누적 횟수**를 세는 데
씁니다 — "이 드리미가 몇 번 반려당했는가"라는 이력은 `Dreami` 엔티티 하나만으로는 표현할 수 없는
정보(계속 초기화되는 현재 상태 vs 누적되는 이력)라서, 굳이 두 곳에 나눠 저장한 게 중복이 아니라
**"현재 상태"와 "이력"의 책임 분리**입니다.
