# 로그인 경로

로그인 버튼 클릭부터 홈 화면 진입까지, 실제로 이 코드베이스는 **일반 로그인 경로**와 **동시 접속이 몰릴 때의 대기열 경로** 두 갈래가 있습니다(부하테스트 이슈로 Redis 기반 로그인 대기열이 도입돼 있음). 순서대로 따라가겠습니다.

## 전체 그림

```
[LoginScreen] 버튼 클릭
    │
    ▼
sessionStore.login({email, password})
    │
    ▼
api.login(...)  ──HTTP POST /api/v1/user/login──▶  UserController.login(...)
    │                                                      │
    │                                                      ▼
    │                                           loginQueue.submit(request)
    │                                                 ├─ [한산할 때] userService.login(request) 즉시 실행 → boormiId
    │                                                 └─ [몰릴 때]   Redis 대기열에 등록 → QUEUED 응답
    │                                                      │
    │                                                      ▼
    │                                  establishSessionIfReady(progress, httpRequest)
    │                                       boormiId 있으면 → LoginSession 생성 + ActiveSessionRegistry.replace
    │                                       없으면        → QUEUED 응답 그대로 반환
    ▼
(QUEUED면) waitInQueue 루프: api.pollLoginQueue(ticketId) 반복 호출
    │           └─ HTTP POST /api/v1/user/login/queue/{ticketId} ──▶ UserController.pollLoginQueue(...)
    │                                                                       │
    │                                                                       ▼
    │                                                              loginQueue.poll(ticketId)
    │                                                              (백그라운드 워커 스레드가 그 사이 해싱 완료해둠)
    ▼
세션 쿠키(JSESSIONID) 발급됨 → api.me() 호출 ──▶ UserController.me(@LoginUser boormiId)
    │                                                   │
    │                                                   ▼
    │                                        userService.getUserInfo(boormiId) → UserDto
    ▼
toAuthUser(UserDto) → zustand 스토어에 user 저장 → resolveLandingRoute(user) → navigate("/home" 등)
```

---

## 1. 버튼 클릭 → `LoginScreen.onLogin`

`LoginScreen.tsx:61`의 `onLogin`이 실행되며 `useSessionStore((s) => s.login)`으로 가져온 스토어 액션 `login({ email, password })`을 호출합니다(`sessionStore.ts:187`). 이 시점에 넘어가는 값은 화면의 `email`/`password` state 문자열 그대로입니다.

## 2. `sessionStore.login` → `api.login`

`sessionStore.ts:190`에서 `api.login({ email, password })`을 호출합니다. `api`는 orval이 OpenAPI 스펙으로부터 생성한 axios 클라이언트(`shared/api/`)라, 실제로는 `POST /api/v1/user/login`에 `{ email, password }` JSON 바디를 실어 보냅니다. 이 요청은 `@PublicApi`가 붙어 있어 `LoginCheckInterceptor`가 세션 검사를 건너뜁니다(아직 로그인 전이니 당연히 세션이 없음).

## 3. `UserController.login` → `LoginQueue.submit`

`UserController.java:91`:
```java
public LoginResultDto login(@Valid @RequestBody LoginRequest request, HttpServletRequest httpRequest) {
    return establishSessionIfReady(loginQueue.submit(request), httpRequest);
}
```
- `@Valid @RequestBody LoginRequest request`: JSON 바디가 `LoginRequest(email, password)` record로 역직렬화·검증(`@Email`, `@Size(min=5,max=20)`)됩니다.
- 이 메서드가 하는 일은 딱 두 단계: `loginQueue.submit(request)`로 **"세션을 만들 준비가 됐는지"**를 얻고, 그 결과를 `establishSessionIfReady`에 넘겨 **"세션 만들기"**를 위임하는 것.

`LoginQueue.submit(LoginRequest)` (`LoginQueue.java:129`)이 반환하는 타입은 `LoginQueue.Progress(UUID boormiId, LoginResultDto response)` record입니다. 두 갈래로 나뉩니다.

### 3-A. 한산할 때 (해싱 슬롯 `hashPermits`가 남고 로컬 대기열도 비어 있음)
```java
UUID boormiId = hashTimer.record(() -> userService.login(request));
return new Progress(boormiId, LoginResultDto.success());
```
여기서 `userService.login(request)`가 호출됩니다(`UserService.java:74`):
```java
public UUID login(LoginRequest request) {
    return verify(loadCredential(request.email()), request.password());
}
```
- **`loadCredential(String email)`** (`@Transactional(readOnly = true)`): `boormiRepository.findByEmail(email)`로 DB 조회 → 없으면 `BusinessException(AuthErrorCode.LOGIN_FAILED)` 던짐 → 있으면 `LoginCredential(boormiId, passwordHash, userCd)` record를 반환. **트랜잭션은 여기서 끝나고 커넥션을 바로 반납**합니다.
- **`verify(LoginCredential credential, String rawPassword)`** (트랜잭션 없음, DB 접근 안 함): `PasswordHasher.matches(rawPassword, credential.passwordHash())`로 PBKDF2 21만회 해싱을 재계산해 비교. 틀리면 `LOGIN_FAILED`, 계정이 정지/탈퇴 상태(`UserCd.RESTRICTED/BANNED/DELETED`)면 각각 `SUSPENDED_ACCOUNT`/`WITHDRAWN_ACCOUNT`를 던집니다. 통과하면 `credential.boormiId()`(`UUID`)를 반환합니다.
- 조회와 해싱 검증을 트랜잭션 하나로 안 묶은 이유가 주석에 있습니다: 무거운 해싱이 도는 내내 DB 커넥션을 붙잡고 있으면, 동시 로그인이 커넥션 풀(기본 10개)을 넘는 순간 11번째 요청부터 커넥션 타임아웃 500이 나기 때문입니다.

이렇게 얻은 `boormiId`가 `Progress.boormiId()`에 담깁니다.

### 3-B. 몰릴 때 (세마포어 획득 실패 또는 이미 대기열이 있음)
`enqueue(request)`(`LoginQueue.java:183`) 호출: `redis.execute(loginEnqueueScript, ...)`로 `RedisConfig`가 등록해둔 Lua 스크립트를 실행해 원자적으로 대기열(ZSET)에 순번을 등록하고, 평문 이메일/비밀번호는 **DB나 Redis가 아니라 서버 힙의 `ConcurrentHashMap<String, PendingLogin> pending`**에만 잠깐 보관합니다. 반환값은 `LoginResultDto.queued(ticketId, position, totalWaiting, estimatedWaitSeconds, pollAfterMs)`이고, 이때 `Progress.boormiId()`는 `null`입니다.

이와 별도로, `@PostConstruct`로 미리 띄워둔 `login-hasher-N` 워커 스레드들(`startWorkers()`)이 `localQueue`에서 티켓을 꺼내 `userService.loadCredential(...)` → `userService.verify(...)`를 백그라운드로 실행하고, 끝나면 `loginAdmitScript`로 Redis에 결과(`READY` + boormiId, 또는 `FAILED` + 에러코드)를 기록해둡니다.

## 4. `UserController.establishSessionIfReady` — 세션 생성

```java
private LoginResultDto establishSessionIfReady(LoginQueue.Progress progress, HttpServletRequest httpRequest) {
    UUID boormiId = progress.boormiId();
    if (boormiId == null) {
        return progress.response();          // QUEUED 응답을 그대로 프론트에 반환
    }
    LoginSession newSession = LoginSession.create(httpRequest);
    newSession.login(boormiId);
    ActiveSession previous = activeSessionRegistry.replace(boormiId, newSession);
    if (previous != null) { ...이전 세션 SSE 종료 + invalidate... }
    return progress.response();              // LoginResultDto.success()
}
```
- `boormiId`가 없으면(대기 중) 그대로 `QUEUED` 응답을 반환하고 끝 — 세션은 아직 안 만듭니다.
- 있으면 `LoginSession.create(httpRequest)`(`LoginSession.java`)가 **기존 서블릿 세션이 있으면 무효화하고 새 세션을 발급**(세션 고정 공격 방지) → `newSession.login(boormiId)`로 세션 attribute에 `boormiId`를 저장 → 이 시점에 Set-Cookie 헤더(JSESSIONID)가 응답에 실립니다.
- `activeSessionRegistry.replace(boormiId, newSession)`(`ActiveSessionRegistry.java`)가 "이 계정의 활성 세션"을 방금 만든 세션으로 갈아끼우고 **이전 활성 세션을 반환**합니다. 이전 세션이 있었다면(다른 기기에서 로그인해 있던 경우) 그 SSE 연결을 끊고 세션을 무효화합니다 — "나중에 로그인한 쪽이 이긴다"는 계정당 세션 1개 정책이 여기서 실행됩니다.
- 반환값은 `LoginResultDto`(record: `status, ticketId, position, totalWaiting, estimatedWaitSeconds, pollAfterMs`). 즉시 성공이면 `status=SUCCESS`이고 나머지는 전부 `null`입니다.

이 리턴값이 `CommonResponseAdvice`를 거쳐 `{ isSuccess: true, code: "COM200", message: "...", result: { status: "SUCCESS", ... } }` 형태로 응답 바디가 됩니다. **이 응답에는 사용자 정보가 없습니다** — 오직 세션 쿠키만 발급될 뿐입니다.

## 5. (대기열 경로일 때) 프론트의 폴링 루프

`sessionStore.login`이 받은 `ticket.status`가 `"QUEUED"`이면 `waitInQueue(ticketId, ticket, position, onProgress)`(`sessionStore.ts:113`)가 돌면서 `ticket.pollAfterMs` 간격으로 `api.pollLoginQueue(ticketId)`를 반복 호출합니다. 이건 `POST /api/v1/user/login/queue/{ticketId}` → `UserController.pollLoginQueue(ticketId, httpRequest)` → `loginQueue.poll(ticketId)`로 이어집니다.

`LoginQueue.poll`(`LoginQueue.java:147`)은 `loginClaimScript`로 Redis에서 티켓 상태를 원자적으로 읽습니다.
- `WAITING`이면 순번(`position`)을 담아 `Progress(null, LoginResultDto.waiting(...))`을 반환 → 컨트롤러는 이걸 그대로 다시 프론트에 돌려줌 → 프론트는 모달(`LoginQueueModal`)에 순번을 갱신하고 또 대기.
- `READY`(워커가 해싱을 이미 끝냄)면 `Progress(UUID.fromString(payload), LoginResultDto.success())` 반환 → 컨트롤러의 `establishSessionIfReady`가 이때 비로소 세션을 만듭니다(3번 항목의 세션 생성 로직이 여기서도 똑같이 재사용됨).
- `FAILED`(비밀번호 틀림/정지 등)면 `BusinessException`을 던져 `GlobalExceptionHandler`가 401/403으로 응답 → 프론트의 `waitInQueue` 루프가 예외로 빠져나가 `LoginScreen`의 catch 블록에서 에러 메시지를 띄웁니다.

`waitInQueue`는 응답 `status`가 더 이상 `QUEUED`/`WAITING`이 아닐 때(`SUCCESS`가 되었을 때) 루프를 빠져나옵니다.

## 6. 세션은 생겼지만 아직 "누구인지"는 모름 → `api.me()`

`sessionStore.login`은 `waitInQueue`가 끝나든(또는 즉시 성공이든) 곧바로 `const { result } = await api.me()`를 호출합니다(`sessionStore.ts:203`). 로그인 응답 자체엔 사용자 정보가 없기 때문입니다.

`GET /api/v1/user/me`는 로그인이 필요한 API라 이제부터 **세션 검증 파이프라인**을 거칩니다:
1. `LoginCheckInterceptor.preHandle`이 먼저 실행되어(`@PublicApi` 없음) `LoginSession.current(request)`로 세션을 확인하고, `activeSessionRegistry.isCurrent(userId, sessionId)`로 이 세션이 지금도 계정의 "현재" 활성 세션인지 검사합니다.
2. 통과하면 `LoginUserArgumentResolver.resolveArgument(...)`가 `LoginSession.current(request).flatMap(LoginSession::boormiId)`로 세션에 저장된 `boormiId`를 꺼내 `@LoginUser UUID boormiId` 파라미터에 주입합니다.
3. `UserController.me(boormiId)` (`UserController.java:157`) → `userService.getUserInfo(boormiId)` 호출.

`UserService.getUserInfo(UUID boormiId)`(`UserService.java:113`):
```java
Boormi boormi = boormiRepository.findById(boormiId).orElseThrow(() -> new BusinessException(AuthErrorCode.INVALID_SESSION));
Dreami dreami = dreamiRepository.findById(boormiId).orElse(null);
boolean approved = dreami != null && dreami.getRequestCd() == DreamiCd.APPROVED;
BigDecimal dreamiAvgScore = approved ? dreami.getDreamiAvgScore() : null;
DreamiCd dreamiStatus = dreami != null ? dreami.getRequestCd() : null;
return UserDto.from(boormi, approved, dreamiAvgScore, dreamiStatus, userActivityResolver.resolve(boormiId));
```
- `boormiRepository.findById`로 계정 엔티티를 가져오고, `dreamiRepository.findById`로 드리미 등록 여부/승인 상태를 함께 조회합니다.
- `userActivityResolver.resolve(boormiId)`가 `ActiveContext`(현재 진행 중인 매칭/배달이 있는지, 있다면 어떤 역할·주문 ID·주문 상태인지)를 계산해서 넘겨줍니다 — 이게 나중에 "로그인 직후 어디로 보낼지" 판단의 근거가 됩니다.
- 최종적으로 `UserDto.from(...)`(record 정적 팩토리)이 이 값들을 모두 담은 `UserDto`를 반환합니다.

## 7. 프론트: `UserDto` → 화면 모델 → 홈으로 이동

`sessionStore.ts:85`의 `toAuthUser(dto: UserDto): AuthUser`가 백엔드 DTO를 화면용 `AuthUser` 타입으로 변환합니다(예: `isDreami` 플래그 하나를 `roles: ["부르미", "드리미"]` 배열로 확장). 이 결과로 `set({ user, isAuthenticated: true, hydrated: true })`가 zustand 스토어를 갱신하고, `sessionStore.login`은 이 `user`를 반환합니다.

`LoginScreen.onLogin`이 그 반환값을 받아 `finishLogin(user)`(`LoginScreen.tsx:36`)을 호출합니다:
```ts
setRole(user.activeRole === "DREAMI" ? "드리미" : "부르미");
navigate(resolveLandingRoute(user), { replace: true });
```
`resolveLandingRoute(user)`(`resolveLandingRoute.ts`)는 `user.activeOrderId`/`activeOrderCd`를 보고 진행 중인 배달이 있으면 그 추적 화면으로, 없으면 `ROUTES.home`으로 보낼 경로 문자열을 계산해 반환합니다. `navigate(...)`가 실행되면 React Router가 화면을 전환합니다.

## 8. 홈 화면이 실제로 "그려지는" 시점의 가드

홈을 포함한 대부분의 페이지는 `app/routes.ts`가 자동으로 `<RequireAuth>`로 감싸둡니다(`RequireAuth.tsx`):
```tsx
if (!hydrated) return null
if (!isAuthenticated) return <Navigate to={ROUTES.login} replace />
return <>{children}</>
```
방금 로그인 흐름에서 `hydrated: true`, `isAuthenticated: true`가 이미 설정돼 있으므로, 이 가드를 통과해 홈 화면 컴포넌트가 최종적으로 렌더링됩니다.

```

   → api.login (HTTP)
     → UserController.login
       → LoginQueue.submit
         → UserService.login → UserService.loadCredential (DB) → UserService.verify (PBKDF2) → UUID
       → UserController.establishSessionIfReady
         → LoginSession.create / login
         → ActiveSessionRegistry.replace
   → (QUEUED면) sessionStore.waitInQueue → api.pollLoginQueue (반복) → UserController.pollLoginQueue → LoginQueue.poll
   → api.me (HTTP)
     → UserController.me (@LoginUser로 boormiId 주입받음)
       → UserService.getUserInfo → boormiRepository/dreamiRepository 조회 + UserActivityResolver.resolve → UserDto
   → toAuthUser(UserDto) → zustand set
 → LoginScreen.finishLogin
   → resolveLandingRoute(user) → navigate
   → RequireAuth 통과 → 홈 화면 렌더
```
