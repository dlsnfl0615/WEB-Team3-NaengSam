# 모니터링 스택 — Actuator / Prometheus / Grafana

기본 개념과 언제 쓰는지 정리한 뒤, 이 프로젝트에 실제로 어떤 옵션으로 붙어 있는지 정리.

> 근거: `backend/build.gradle`, `backend/src/main/resources/application.properties`,
> `monitoring/README.md`, `monitoring/prometheus.yml`, `monitoring/docker-compose.yml`,
> `docs/hyeonseo/cicd.md` §5.

---

## 1. 기본 개념 — 언제, 왜 쓰는가

세 도구는 **"관측(observability) 파이프라인" 하나를 셋으로 나눈 것**이다. 역할이 겹치지 않고
줄줄이 이어진다.

```
애플리케이션 내부 상태
      │  ① Actuator가 HTTP로 노출
      ▼
Spring Boot Actuator (/actuator/prometheus)
      │  ② Prometheus가 주기적으로 긁어감(pull, scrape)
      ▼
Prometheus (시계열 DB + 쿼리엔진)
      │  ③ Grafana가 쿼리해서 그래프로 렌더링
      ▼
Grafana (대시보드 시각화)
```

### Spring Boot Actuator

**뭔가**: 애플리케이션이 지금 얼마나 건강한지, 내부에 어떤 수치(요청 수, 응답 시간, JVM 메모리,
커넥션 풀 사용량 등)가 쌓이고 있는지를 **HTTP 엔드포인트로 노출**해주는 스프링 부트 라이브러리.
`/actuator/health`(헬스체크), `/actuator/metrics`(개별 지표 조회), `/actuator/prometheus`(Prometheus가
바로 긁어갈 수 있는 텍스트 포맷) 같은 엔드포인트를 자동으로 만들어준다.

**언제 쓰나**: 로드밸런서/오케스트레이터가 "이 인스턴스가 살아있는지" 확인할 때(헬스체크), 배포 직후
정상 기동 여부를 자동 검증할 때, 그리고 아래 Prometheus가 긁어갈 원천 데이터를 만들 때 쓴다. 이
라이브러리 하나만으로는 "지금 값이 뭔지"만 보여줄 뿐, **과거 추이를 저장하거나 그래프로 보여주지는
않는다** — 그게 Prometheus/Grafana의 역할이다.

### Prometheus

**뭔가**: 여러 애플리케이션의 메트릭 엔드포인트를 주기적으로 **긁어와(pull 방식)** 시계열 DB에
쌓아두고, PromQL이라는 쿼리 언어로 조회할 수 있게 해주는 오픈소스 모니터링 시스템.

**언제 쓰나**: "이 지표가 시간에 따라 어떻게 변했는지"를 알아야 할 때(요청량 추이, 에러율 추이,
메모리 증가 추세 등), 그리고 "이 조건이 되면 알림을 보내라"(Alertmanager와 연동) 같은 조건부 감시가
필요할 때 쓴다. **Push가 아니라 Pull**이라는 게 특징 — 애플리케이션이 Prometheus에 값을 쏘는 게
아니라, Prometheus가 애플리케이션의 메트릭 엔드포인트를 정해진 주기로 찾아가서 긁어간다.

### Grafana

**뭔가**: Prometheus(등 여러 데이터소스)에 쌓인 시계열 데이터를 **대시보드로 시각화**하는 도구.
Prometheus 자체에도 기본 그래프 UI가 있지만 투박해서, 실무에서는 거의 항상 Grafana를 앞에 둔다.

**언제 쓰나**: 여러 지표를 한 화면에 모아서 한눈에 보고 싶을 때, 팀원들이 PromQL을 몰라도 미리 만든
패널을 보고 상태를 판단할 수 있게 하고 싶을 때 쓴다. Prometheus는 "데이터를 갖고 있는 저장소",
Grafana는 "그 데이터를 예쁘게 그려주는 창"이라는 관계다.

## 2. 이 프로젝트에서 어떻게 쓰이고 있나

### 2.1 인스턴스를 분리해서 운영

가장 먼저 알아야 할 구조적 특징: **모니터링 스택(Prometheus+Grafana)이 백엔드와 완전히 다른
EC2 인스턴스**에서 돈다.

```
[백엔드 인스턴스]                          [모니터링 인스턴스]
 backend(8080)  API 서버                   prometheus (호스트에 비공개)
 backend(8081)  액츄에이터                 grafana(3000)  대시보드(호스트에 공개)
       └──── VPC 프라이빗 IP:8081 ◀── 15초마다 스크레이프 ────┘
       (보안그룹: 8081은 모니터링 인스턴스 SG에서만 허용)
```

- 두 스택은 **CI/CD 파이프라인도 분리**돼 있다. 백엔드는 GitHub Actions가 이미지를 빌드해 배포하지만,
  `monitoring/` 폴더는 그대로 모니터링 인스턴스에 복사해서 별도 `docker compose`로 띄운다 —
  `monitoring/` 파일을 고쳐도 백엔드 이미지는 다시 빌드되지 않는다.
- 도커 네트워크는 인스턴스 경계를 못 넘으므로, 두 스택을 잇는 연결점은 **`prometheus.yml`에 적힌
  백엔드의 VPC 프라이빗 IP 하나뿐**이다. 공인 IP가 아니라 프라이빗 IP를 쓰는 이유는, 8081(액츄에이터)
  포트를 인터넷에 노출하지 않고 같은 VPC 안에서만 접근 가능하게 하기 위해서다 — 실제로 백엔드 인스턴스
  보안그룹은 `TCP 8081`을 **모니터링 인스턴스의 보안그룹에서 오는 트래픽만** 허용하도록 제한돼 있다.

### 2.2 Actuator 설정 — `application.properties`의 `management.*`

```properties
management.server.port=${MANAGEMENT_PORT:8081}
management.endpoints.web.exposure.include=health,info,prometheus
management.endpoint.health.show-details=never
management.health.redis.enabled=false
management.metrics.tags.application=${spring.application.name}
management.metrics.distribution.percentiles-histogram.http.server.requests=true
management.metrics.distribution.minimum-expected-value.http.server.requests=1ms
management.metrics.distribution.maximum-expected-value.http.server.requests=10s
management.metrics.distribution.percentiles-histogram.http.server.requests.active=false
management.metrics.distribution.percentiles-histogram.hikaricp.connections.usage=true
```

옵션별 의미:

- **`management.server.port=8081`**: 액츄에이터를 API 서버(8080)와 **별도 포트**로 분리한다. 이
  덕분에 보안그룹에서 "8080은 전체 공개, 8081은 모니터링 인스턴스에서만"처럼 노출 범위를 다르게
  걸 수 있다. `MANAGEMENT_PORT` 환경변수로 로컬에서 바꿀 수도 있다.
- **`management.endpoints.web.exposure.include=health,info,prometheus`**: Actuator가 기본 제공하는
  수십 개 엔드포인트(`env`, `beans`, `threaddump`, `heapdump` 등 민감한 것 포함) 중 **딱 세 개만**
  외부에 열어둔다. 화이트리스트 방식이라 새 Actuator 엔드포인트가 추가돼도 기본적으로 안 열린다.
- **`management.endpoint.health.show-details=never`**: `/actuator/health`가 "UP/DOWN" 한 단어만
  응답하고, 어떤 컴포넌트(DB, Redis 등)가 왜 죽었는지 세부 정보는 노출하지 않는다. 세부 정보를
  노출하면 공격자에게 내부 구성(어떤 DB를 쓰는지 등)을 알려주는 셈이라 운영에서는 보통 끈다.
- **`management.health.redis.enabled=false`**: Redis 장애가 전체 헬스체크를 DOWN으로 끌어내리지
  않게 막는다. 이 프로젝트에서 Redis는 로그인 대기열·카카오 캐시처럼 **없어도 앱이 저부하에서는
  계속 동작하는 보조 기능**이라, Redis 하나 죽었다고 로드밸런서가 멀쩡한 인스턴스를 통째로 빼버리는
  걸 막기 위한 설정이다.
- **`management.metrics.tags.application`**: 모든 메트릭에 `application="quick"` 라벨을 공통으로
  붙인다. 지금은 인스턴스가 하나뿐이지만, 나중에 여러 서비스/인스턴스의 메트릭이 같은 Prometheus에
  쌓이게 되면 이 라벨로 구분할 수 있다.
- **`percentiles-histogram.http.server.requests=true` + `minimum/maximum-expected-value`**: HTTP
  요청 지연시간을 **히스토그램**(버킷별 카운트)으로 노출해, Grafana에서 `histogram_quantile()`로
  p95/p99 같은 백분위수를 계산할 수 있게 한다. 버킷 범위를 1ms~10s로 좁혀 잡은 이유는, 대부분의 API가
  10ms 미만이라 하한을 너무 높게 잡으면 값이 전부 첫 버킷에 뭉쳐 엔드포인트 간 비교가 안 되기
  때문이다(버킷 수를 줄여 카디널리티도 낮춘다).
- **`percentiles-histogram.http.server.requests.active=false`**: "진행 중인 요청" 지표는 히스토그램이
  아니라 개수만 필요해서 껐다. 켜두면 내부 메트릭 이름이 `_active_count`에서 `_gcount`로 바뀌어
  기존 PromQL 쿼리가 깨진다.
- **`percentiles-histogram.hikaricp.connections.usage=true`**: DB 커넥션 풀 점유 시간도 히스토그램으로
  본다. 외부 API 호출을 트랜잭션 밖으로 뺀 효과(초 단위 → ms 단위로 줄었는지)를 p95로 확인하기 위한
  것.

의존성은 `backend/build.gradle`에 이렇게 걸려 있다:

```gradle
implementation 'org.springframework.boot:spring-boot-starter-actuator'
runtimeOnly 'io.micrometer:micrometer-registry-prometheus' // /actuator/prometheus 노출
```

`spring-boot-starter-actuator`만으로는 `/actuator/metrics`(스프링 자체 포맷)까지만 나오고,
Prometheus가 이해하는 텍스트 포맷(`/actuator/prometheus`)을 만들려면 `micrometer-registry-prometheus`가
추가로 필요하다.

### 2.3 Prometheus 설정 — `monitoring/prometheus.yml`

```yaml
global:
  scrape_interval: 15s

scrape_configs:
  - job_name: symboorm-backend
    metrics_path: /actuator/prometheus
    static_configs:
      - targets: ['10.0.1.43:8001']   # 실제로는 백엔드 인스턴스의 VPC 프라이빗 IP:8081
```

- **`scrape_interval: 15s`**: 15초마다 백엔드의 `/actuator/prometheus`를 긁어간다.
- **`static_configs`**: 서비스 디스커버리 없이, 타깃 IP를 파일에 직접 고정해뒀다. 백엔드 인스턴스를
  재생성하면(프라이빗 IP가 바뀌면) 이 값을 수동으로 갱신해야 한다 — `monitoring/README.md`의
  "타깃이 down일 때" 체크리스트 1번 항목이 바로 이거다.
- 저장 기간은 기본 15일(Prometheus 기본값)이고, `docker-compose.yml`의 prometheus 서비스에
  `command: --storage.tsdb.retention.time=30d` 같은 인자를 추가하면 늘릴 수 있다.

### 2.4 커스텀 메트릭 ① — SSE 연결 상태

SSE는 `SseEmitter` 기반 비동기 요청이라 표준 HTTP 메트릭(`http_server_requests_seconds`)에는
**연결이 끊길 때 한 번만** 기록된다. 연결이 유지되는 동안의 실시간 상태는 안 보이므로, `global.sse`
쪽 코드(`SseConnectionManager`)가 Micrometer로 직접 계측한다(코드상 `.` 구분자가 Prometheus로 나갈 때
`_`로 바뀐다):

| Prometheus 이름 | 타입 | 라벨 | 의미 |
|---|---|---|---|
| `sse_connections_active` | Gauge | — | 현재 유지 중인 연결 수 |
| `sse_connections_opened_total` | Counter | — | 누적 연결 수립 수 |
| `sse_connections_closed_total` | Counter | `reason` | 누적 종료 수(사유별) |
| `sse_events_sent_total` | Counter | `event` | 전송 성공한 이벤트 수 |
| `sse_events_dropped_total` | Counter | `reason` | 전송 실패한 이벤트 수 |

**주의점(README에 명시)**: `sse_connections_active`는 실제보다 크게 나올 수 있다 — 클라이언트가
조용히 연결을 끊어도 서버는 다음 전송을 시도할 때에야 그걸 알아챈다(heartbeat 도입 전 기준 문서라,
지금은 25초 heartbeat로 어느 정도 보완됨). `sse_connections_closed_total{reason="send_failed"}`가
계속 오르면 죽은 연결이 쌓이고 있다는 신호로 본다.

### 2.5 커스텀 메트릭 ② — 카카오 응답 캐시

| Prometheus 이름 | 타입 | 라벨 | 의미 |
|---|---|---|---|
| `kakao_cache_total` | Counter | `api`(geocode/route), `result`(hit/miss) | 캐시 조회 결과 |
| `kakao_cache_error_total` | Counter | `api`, `op`(get/put), `reason` | 캐시 실패 원인별 건수 |

- `result="miss"`의 증가량이 **실제로 카카오 API로 나간 호출 수**이고, `hit`은 캐시가 막아준(절감된)
  호출 수다.
- 오류를 `kakao_cache_total`에 라벨로 안 넣고 **별도 메트릭**으로 뺀 이유는, Prometheus가 같은
  메트릭 이름에 라벨 키 집합이 달라지는 걸 허용하지 않기 때문이다(`result`엔 `reason`을 못 붙임).
- `reason="oom"`은 특히 중요한 **조기경보**다 — 카카오 캐시가 로그인 대기열과 같은 Redis 인스턴스
  (`maxmemory 64mb`, `noeviction`)를 쓰기 때문에, 이 메트릭이 뜨면 캐시뿐 아니라 로그인 대기열까지
  같이 막혀 로그인이 503으로 실패하고 있다는 뜻이다. 이 프로젝트는 `redis_exporter`를 안 쓰기 때문에
  Redis 메모리 상태를 직접 볼 방법이 없어서, 이 카운터 하나가 그 대체 신호 역할을 한다.

### 2.6 Grafana 대시보드 구성

`monitoring/docker-compose.yml`이 Grafana 컨테이너를 띄우고, `grafana/provisioning/` 폴더로
데이터소스와 대시보드를 **코드로 미리 구성**해둔다(수동으로 UI에서 설정 안 해도 컨테이너가 뜨면
바로 연결돼 있음). 대시보드는 출처가 다른 세 종류를 섞어 쓴다:

| 대시보드 | 등록 방식 | 이유 |
|---|---|---|
| **SymBoorm — HTTP & SSE** | `grafana/provisioning/dashboards/symboorm-http-sse.json`을 리포에 커밋 | `sse_*`/`kakao_cache_*`는 이 프로젝트가 직접 만든 커스텀 메트릭이라 커뮤니티 대시보드에 없음 — ID로 재생산 불가능하므로 JSON 자체를 코드로 관리 |
| Spring Boot 3.x Statistics (ID 19004) | Grafana UI에서 "Import by ID" | 표준 메트릭이라 ID만 있으면 누구나 동일하게 재현 가능. 수천 줄짜리 자동생성 JSON을 커밋해봐야 리뷰가 불가능해서 커밋하지 않음 |
| JVM (Micrometer) (ID 4701) | 위와 동일 | 위와 같은 이유 |

`allowUiUpdates: false`로 프로비저닝돼 있어서, Grafana UI에서 커스텀 대시보드를 고쳐도 컨테이너를
재기동하면 원래 JSON으로 되돌아간다 — 바꾸려면 JSON 파일 자체를 고쳐서 커밋해야 한다.

### 2.7 로컬 개발 환경 — 배포용과 완전히 분리

`monitoring/docker-compose.local.yml` + `monitoring/prometheus.local.yml`이 로컬 전용 세트다.
배포용과 compose 프로젝트명·컨테이너명·볼륨이 전부 분리돼 있어 서로 간섭하지 않는다. 로컬에서는
백엔드를 도커에 안 넣고 `./gradlew bootRun`으로 호스트에서 띄운 뒤, Prometheus가
`host.docker.internal:8081`로 긁어간다.

```bash
cd monitoring && docker compose -f docker-compose.local.yml up -d
cd backend && ./gradlew bootRun
# http://localhost:3000 (admin/admin)
```

### 2.8 보안 관련 옵션

- **8081(액츄에이터) 포트는 보안그룹으로만 방어한다.** EC2는 공인 IP를 IGW가 NAT하는 구조라
  바인딩 주소 자체로는 외부 접근을 못 막기 때문에, "TCP 8081 ← 모니터링 인스턴스 보안그룹"이라는
  인바운드 규칙이 **유일한 방어선**이다. `monitoring/README.md`는 이 규칙을 반드시 백엔드 기동 전에
  먼저 넣으라고 강조한다 — 규칙이 `0.0.0.0/0`이면 메트릭 엔드포인트가 그대로 인터넷에 노출된다.
- **Grafana(3000)는 기본으로 외부에 노출**되므로(대시보드를 봐야 하니까), `.env`의
  `GF_SECURITY_ADMIN_USER`/`GF_SECURITY_ADMIN_PASSWORD`를 기본값(admin/admin) 그대로 두면 안
  된다는 게 README에 명시돼 있다. 가능하면 보안그룹에서 3000 포트도 팀 IP로만 제한을 권장한다.
- `management.endpoints.web.exposure.include`를 `health,info,prometheus` 세 개로 좁힌 것 자체도
  보안 조치다 — Actuator 전체를 열면 `/actuator/env`(환경변수 노출), `/actuator/heapdump`(힙 덤프
  다운로드) 같은 위험한 엔드포인트까지 같이 열린다.

### 2.9 직접 활용하는 PromQL 예시 (Grafana 패널/트러블슈팅용)

```promql
# 엔드포인트별 p95 응답시간 (SSE 구독 엔드포인트는 연결이 최대 1시간이라 +Inf 버킷을 왜곡하므로 제외)
histogram_quantile(0.95, sum by (le, uri) (
  rate(http_server_requests_seconds_bucket{uri!~".*subscribe.*"}[5m])))

# 5xx 비율
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
  / sum(rate(http_server_requests_seconds_count[5m]))

# 카카오 캐시 히트율
sum by (api) (rate(kakao_cache_total{result="hit"}[5m]))
  / sum by (api) (rate(kakao_cache_total{result=~"hit|miss"}[5m]))

# 로그인 대기열까지 같이 막혔는지 확인하는 트립와이어
rate(kakao_cache_error_total{reason="oom"}[5m]) > 0
```
