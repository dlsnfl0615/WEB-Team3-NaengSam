# address 도메인 — 코드 단위 예상 질문

`upload/코드 단위 예상 질문.md`와 같은 목적·형식. 카테고리: ① 버그/리스크 후보, ② 캐시·동시성 설계,
③ 애노테이션, ④ 대체 가능한 방법이 있는데 왜 지금 방식을 골랐는지.

> 대상 파일: `AddressController`, `AddressApiController`, `AddressService`, `AddressApiService`,
> `Address`, `AddressRepository`, `AddressErrorCode`, `CoordinatesService`/`DirectionsService`(인터페이스),
> `KakaoCoordinatesService`/`KakaoDirectionsService`, `CachedCoordinatesService`/`CachedDirectionsService`,
> `KakaoResponseCache`, `DevCoordinatesService`/`DevDirectionsService`.

## 1. 버그/리스크 후보

**Q1. `AddressService.saveAddress`는 카카오 응답의 `documents`가 비어있으면
`EXTERNAL_SERVICE_ERROR`를 던지는데, `AddressApiController.getCoordinates`는 같은 검사가 없습니다.
문제가 되지 않나요?**

실제로 비대칭입니다.

```java
// AddressService.saveAddress — 빈 응답을 명시적으로 검사
List<CoordinatesResponseDto.Document> documents = coordinates.documents();
if (documents.isEmpty()) {
    throw new BusinessException(GeneralErrorCode.EXTERNAL_SERVICE_ERROR);
}
CoordinatesResponseDto.RoadAddress roadAddress = documents.getFirst().roadAddress();
```

```java
// AddressApiController.getCoordinates — 검사 없이 바로 getFirst()
CoordinatesResponseDto originCoordinates = coordinatesService.getCoordinates(requestDto.origin());
...
new BigDecimal(originCoordinates.documents().getFirst().roadAddress().y())...
```

카카오가 "주소를 못 찾음"(존재하지 않거나 지번만 있는 주소 등)으로 응답하면 `documents`가 빈
리스트로 옵니다. `AddressService`는 이걸 `BusinessException`으로 깔끔하게 처리하지만,
`AddressApiController`는 `List.getFirst()`가 그대로 `NoSuchElementException`을 던지게 됩니다. 이건
`BaseErrorCode`를 안 구현한 일반 예외라 `GlobalExceptionHandler`의 최종 캐치올로 떨어져서, 사용자에게
"주소를 찾을 수 없어요" 대신 그냥 500(내부 오류)이 노출됩니다. 견적 조회(`/address/place`)가 배송지
저장(`AddressController.saveAddress`)보다 먼저 호출되는 화면 흐름을 생각하면, **이상한 주소를
입력했을 때 사용자가 제일 먼저 만나는 API가 오히려 검증이 빠진 쪽**이라는 점이 실무라면 반드시
고쳐야 할 지점입니다.

**Q2. `AddressApiService.findById`가 주문을 못 찾으면 `GeneralErrorCode.EXTERNAL_SERVICE_ERROR`를
던집니다. 이게 맞는 에러코드인가요?**

```java
public Orders findById(UUID orderId) {
    return orderRepository.findById(orderId)
            .orElseThrow(() -> new BusinessException(GeneralErrorCode.EXTERNAL_SERVICE_ERROR));
}
```

의미상 맞지 않습니다. `EXTERNAL_SERVICE_ERROR`(`COMMON_011`, 503)는 "카카오 같은 외부 서비스 호출이
실패했다"는 뜻인데, 여기서 실패한 건 외부 API 호출이 아니라 **우리 DB에서 주문을 못 찾은 것**입니다.
`OrderErrorCode.ORDER_NOT_FOUND`(다른 곳에서 실제로 쓰이는 코드) 같은 404 계열이 맞습니다. 아마 같은
클래스 안에서 카카오 호출 실패 처리에 쓰던 에러코드를 복붙하다가 그대로 남은 것으로 보입니다 — 프론트
입장에서는 "일시적 외부 장애니까 재시도해볼까"로 잘못 해석할 수 있는 코드가, 실제로는 "이 주문 자체가
없다"는 재시도해도 절대 안 풀리는 상황이라는 게 문제입니다.

**Q3. `DreamiCd`처럼, `DreamiCd`가 아니라 `AddressErrorCode`를 보면 카카오 도보 길찾기 상태 코드를
전부 매핑해뒀습니다. 목록에 없는 상태가 오면 어떻게 되나요?**

주석에 이미 명시돼 있습니다 — *"목록에 없는 상태를 카카오가 반환하면 이 enum이 아니라 공통
`EXTERNAL_SERVICE_ERROR`로 처리된다"*. `KakaoDirectionsService`가 카카오의 에러 응답 코드를 이
enum의 상수와 매칭 시도하고, 못 찾으면 폴백으로 일반 외부 서비스 오류로 떨어지는 구조입니다. 카카오가
API를 바꿔서 새로운 에러 코드를 추가해도 앱이 깨지지 않고 "알 수 없는 외부 오류"로 안전하게
degrade된다는 뜻이지만, 반대로 말하면 **그 새 에러의 구체적인 원인(예: "출발지가 섬이라 도보 경로가
없음")은 사용자에게 정확히 전달되지 않고 뭉뚱그려진 메시지로만 보입니다.**

## 2. 캐시·동시성 설계

**Q4. 카카오 응답을 캐싱하는데 왜 Spring의 `@Cacheable`(Spring Cache)을 안 쓰고
`KakaoResponseCache`라는 별도 클래스를 직접 만들었나요?**

`KakaoResponseCache.java` 클래스 javadoc에 이유가 명확히 적혀 있습니다. **`@Cacheable`은 빈
프록시에서 동작합니다** — AOP 프록시가 메서드 호출을 가로채서 캐시를 확인/저장하는 방식이기 때문에,
그 어노테이션은 프록시로 감싸지는 빈(스프링 컨테이너가 관리하는 `Kakao*Service` 인스턴스)에 붙어야
동작합니다. 그런데 이 프로젝트의 테스트 코드는 `Kakao*Service`를 스프링 컨텍스트 없이 **`new`로 직접
생성해서 씁니다.** `new`로 만든 객체는 프록시를 거치지 않으므로, `@Cacheable`을 그 클래스에 붙여봐야
테스트에서는 캐시가 조용히 무효화됩니다(캐시 코드가 있는데 테스트에서는 동작하지 않는 것처럼 보이는
상태). "테스트에서만 동작이 다른 어노테이션"보다는, `CachedCoordinatesService`처럼 **명시적인
데코레이터 클래스**를 만들어 캐시 로직을 뻔히 보이는 자바 코드로 두는 게 낫다고 판단한 것입니다.
부수적으로 부트 4.1 액추에이터에는 캐시 히트율 메트릭 바인더가 없어서, `@Cacheable`을 썼어도 히트율은
어차피 따로 계측해야 했다는 점도 이유로 언급돼 있습니다.

**Q5. `KakaoResponseCache.get()`/`put()`은 Redis 조회 실패, 역직렬화 실패를 전부 예외 없이
`null`/무시로 삼킵니다. 캐시 실패를 왜 호출부에 알리지 않나요?**

**Fail-open 설계**입니다. 캐시는 "카카오 호출 횟수를 줄이는 최적화 장치"일 뿐, **정답을 만드는
필수 경로가 아닙니다.** Redis가 죽어 있어도, 혹은 저장된 JSON이 (배포 후 DTO 모양이 바뀌는 등의
이유로) 깨져 있어도 앱은 그냥 카카오를 직접 호출하는 원래 경로로 흘러가면 됩니다. 이건
`management.health.redis.enabled=false`(Redis 장애를 헬스체크 DOWN으로 안 올리는 설정)와 정확히
같은 철학입니다 — **부가 기능(캐시)의 장애가 핵심 기능(주소 검색)을 막아서는 안 된다**는 원칙을
일관되게 적용한 것입니다. 역직렬화 실패를 미스로 처리하는 것도 같은 맥락 — 다음 `put()`이 새 값으로
덮어쓰므로 별도 마이그레이션 없이 자동 복구됩니다.

**Q6. `CachedCoordinatesService`에 `@Primary`가 왜 필수인가요? 없으면 어떻게 되나요?**

`CoordinatesService` 인터페이스를 구현하는 빈이 `kakao.enabled=true`일 때 **두 개** 동시에 존재하게
됩니다 — `KakaoCoordinatesService`(원본)와 `CachedCoordinatesService`(그걸 감싸는 데코레이터).
`AddressService`나 `AddressApiController`처럼 `CoordinatesService` 인터페이스로 주입받는 곳들은
스프링이 둘 중 어느 걸 넣어줘야 할지 모호해집니다. `@Primary`가 없으면 기동 시점에
`NoUniqueBeanDefinitionException`으로 앱이 아예 안 뜹니다. `@Primary`를 캐시 데코레이터 쪽에 붙여서
"기본으로는 캐시를 거치는 쪽을 써라"라고 명시한 것입니다. `CachedCoordinatesService`가 델리게이트를
**인터페이스가 아니라 구체 타입(`KakaoCoordinatesService`)으로 직접 주입받는** 것도 같은 이유의
연장선입니다 — 만약 `CoordinatesService` 인터페이스로 델리게이트를 받으면, `@Primary`가 걸린
자기 자신이 순환 주입될 위험이 생깁니다.

**Q7. 지오코딩 캐시 TTL은 7일, 경로 캐시 TTL은 1시간으로 다릅니다. 왜 이렇게 차이를 뒀나요?**

두 값의 특성이 다르기 때문입니다.
- **주소→좌표**(`CachedCoordinatesService`)는 **사실상 불변**입니다 — 같은 도로명주소는 언제 물어봐도
  같은 좌표입니다. 그리고 응답 크기도 작습니다(~400바이트). 그래서 길게(7일) 캐싱해도 안전하고
  이득이 큽니다.
- **경로**(`CachedDirectionsService`)는 폴리라인 좌표 배열(`Path.points`)이 들어 있어 지오코딩의
  거의 30배(5~15KB)로 큽니다. 재사용 가치보다 **메모리 상한**이 우선이라, 실제 중복 호출이 벌어지는
  구간(같은 주문 흐름 안, 초~분 단위)만 잡으면 충분한 1시간으로 짧게 잡았습니다.

두 클래스 모두 **TTL을 0 이하로 두면 캐시를 통째로 건너뛰는 킬 스위치**가 되도록 만들어뒀는데, 이건
재배포 없이 환경변수만 바꿔서 캐시를 끌 수 있게 하려는 의도입니다.

**Q8. `CachedDirectionsService`의 캐시 key를 만들 때 좌표를 `stripTrailingZeros()`로 가공합니다.
왜 필요한가요?**

같은 지점이라도 좌표가 유입되는 경로마다 소수점 자릿수(scale)가 다르기 때문입니다. 지오코딩 직후의
좌표는 카카오 응답 문자열을 그대로 파싱한 값(가변 scale)이고, DB에서 다시 읽어온 좌표는 컬럼
정의(`precision=11, scale=8`)대로 항상 8자리로 고정됩니다. `BigDecimal`은 `37.4979`와
`37.49790000`을 값으로는 같다고 보지만 **`equals()`는 scale까지 비교해서 다르다고 판단**합니다.
캐시 key는 문자열이라 이 미묘한 차이가 그대로 다른 key로 갈라져서, 사실상 같은 경로인데도 캐시를
서로 못 쓰는 문제가 생깁니다. `stripTrailingZeros()`(반올림이 아니라 뒤의 0만 제거)로 이걸
정규화해서 같은 지점이면 항상 같은 key가 되도록 맞춘 것입니다.

**Q9. 캐시 key를 만들 때 주소 문자열은 `trim()` + 공백 정규화만 하고 소문자화는 안 합니다. 왜
소문자화는 생략했나요?**

한글 주소이기 때문입니다. 영문 주소라면 대소문자가 섞여 들어와 같은 주소가 다른 key로 갈라질 수
있어 소문자화가 의미 있지만, 한글은 애초에 대소문자 구분이 없는 문자 체계라 그런 처리를 할 이유가
없습니다. 반면 공백은 화면마다 "서울시 강남구"처럼 붙여 쓰거나 "서울시  강남구"처럼 다르게 입력될
수 있어 정규화가 필요했다는 차이입니다.

**Q10. 카카오 캐시와 로그인 대기열이 같은 Redis 인스턴스를 쓴다고 되어 있습니다. 정책이
`maxmemory 64mb` + `noeviction`인데, 캐시 때문에 로그인 대기열이 영향받을 수 있지 않나요?**

**받을 수 있고, 그게 의도된 설계입니다.** `noeviction`은 메모리가 꽉 차면 오래된 캐시를 자동으로
밀어내는 대신(`allkeys-lru` 등) **새 쓰기 자체를 실패시킵니다.** `allkeys-*`/`volatile-*` 정책으로
바꾸면 `login:ticket:*`(로그인 대기열 티켓)도 캐시와 똑같이 evict 대상이 되어, 대기 중이던 사용자의
티켓이 조용히 사라지는 훨씬 심각한 문제가 생깁니다. 그래서 캐시 총량 관리는 evict 정책이 아니라
**TTL로만** 묶어두고, 대신 메모리가 정말 꽉 찼을 때는 캐시 쓰기가 실패하도록(그리고
`kakao.cache.error{reason="oom"}` 카운터로 조기경보) 만든 것 — "캐시가 좀 못 미더워지더라도 로그인
대기열은 절대 건드리지 않는다"는 우선순위가 반영된 트레이드오프입니다.

## 3. 애노테이션 관련 질문

**Q11. `KakaoCoordinatesService.init()`에서 API 키가 없으면 `BusinessException`이 아니라
`IllegalStateException`을 던져서 기동 자체를 실패시킵니다. 왜 그냥 예외를 던지지 않고 앱을 아예 못
띄우게 하나요?**

주석에 이유가 있습니다 — *"키 없이 뜨면 모든 주소 검색이 401로 실패하므로, 차라리 기동을 실패시켜
배포에서 잡는다."* 만약 조용히 기동됐다면, 앱은 정상적으로 떠 있는 것처럼 보이지만 **모든 주소
관련 기능이 개별 요청마다 401로 실패**하는 상태가 됩니다. 이건 배포 파이프라인의 헬스체크는
통과하고, 실제 사용자가 기능을 쓰다가 뒤늦게 알아채는 최악의 실패 모드입니다. 아예 시작 단계에서
죽여버리면, 배포 스크립트나 모니터링이 "기동 실패"로 즉시 잡아낼 수 있습니다. `kakao.enabled=true`인데
`KAKAO_REST_API_KEY`만 빠진 실수(오타, 시크릿 미설정)를 배포 직후 몇 초 안에 드러나게 만드는
안전장치입니다.

**Q12. `kakao.enabled`가 오타로 잘못 설정되거나 아예 빠지면 어떻게 되나요? 이것도 위험하지
않나요?**

이건 `upload.s3-enabled`와 정확히 같은 구조의 위험입니다(`upload/코드 단위 예상 질문.md` Q7 참고).
`Kakao*Service`/`Cached*Service`는 `matchIfMissing = true`(값이 없으면 true로 간주), `DevCoordinatesService`는
`havingValue = "false"`(명시적으로 false여야만)로 조건이 걸려 있어, 오타로 프로퍼티 이름 자체가
바뀌면 두 조건 모두 "값 없음"으로 해석되어 **Kakao/Cached 계열은 기본값(true)으로 켜지고
DevCoordinatesService는 안 켜지는** 결과가 됩니다. 즉 이 경우엔 "빈이 아예 없어서 기동 실패"보다는
"의도와 다르게 실 API 쪽이 켜져버리는" 위험이 더 큽니다 — 로컬에서 자격증명 없이 개발하려 했는데
`KakaoCoordinatesService.init()`이 자격증명 없음으로 기동을 막아버리는 상황을 상상하면 됩니다. 이건
사실 앞서 언급한 `KakaoCoordinatesService.init()`의 기동 실패 안전장치가 **여기서도 그대로
유효하게 작동**하는 지점이라, "설계가 이중으로 안전하게 겹쳐 있다"고 답하면 좋습니다(프로퍼티가
잘못돼 실 API 경로로 잘못 켜져도, 자격증명이 없으면 어차피 기동 실패로 드러남).

## 4. 대체 가능한 방법이 있는데 왜 지금 방식을 골랐는지

**Q13. `AddressController`와 `AddressApiController`가 같은 `/api/v1/address` 경로 프리픽스를
쓰는데, 왜 클래스가 둘로 나뉘어 있나요? 하나로 합칠 수도 있지 않았나요?**

역할이 근본적으로 다릅니다. `AddressApiController.getCoordinates`(`POST /address/place`)는
**DB를 전혀 건드리지 않는 stateless 변환**입니다 — 결제 전 견적 화면에서 주소를 좌표로 바꿔주기만
하고, 그 값은 클라이언트가 들고 있다가 결제 완료 시점에 주문 생성 요청에 실어 보냅니다. 반면
`AddressController.saveAddress`(`POST /address`)는 로그인한 부르미의 배송지를 **실제로 DB에
저장**합니다. 이렇게 나눈 이유는 클래스 javadoc에 명시돼 있습니다 — *"주문이 끝나기 전에는 관련
row를 만들지 않기 위한 의도적 설계"*. 견적만 조회하고 실제로 주문/결제를 안 한 사용자의 흔적을 DB에
남기지 않으려는 것입니다. 하나로 합쳤다면 "이 API가 저장까지 하는지 안 하는지"를 매번 파라미터나
분기로 구분해야 해서, 지금처럼 클래스 이름만 보고 부작용 유무를 바로 알 수 있는 게 더 명확합니다.

**Q14. `AddressRepository`는 `findAllByBoormiId`만 노출합니다. `JpaRepository`가 기본 제공하는
`findAll()`을 그냥 쓰면 안 됐나요?**

`AddressController` javadoc에 이 설계의 실제 배경이 적혀 있습니다 — *"원래는 로그인 없이 열려 있고
전체를 조회하는 IDOR이었다."* 즉 과거에는 인증 없이 호출 가능하고 **모든 사용자의 배송지를 전부
반환하는 취약점(IDOR, Insecure Direct Object Reference)**이 실제로 있었다는 뜻입니다. 지금은
`@LoginUser`로 로그인을 강제하고, 리포지토리 메서드 자체를 `findAllByBoormiId`로만 열어둬서
**컨트롤러가 실수로라도 "전체 조회"를 다시 노출할 방법 자체를 리포지토리 레벨에서 차단**했습니다.
`findAll()`(전체 조회)을 아예 안 만든 게 아니라 `JpaRepository`가 상속으로 제공하긴 하지만,
`AddressService`가 그걸 호출하는 코드가 없으므로 실제로 이 취약점 경로를 쓸 방법이 없습니다 — 다만
정말 엄격하게 막으려면 `findAll()` 자체를 오버라이드해서 `UnsupportedOperationException`을 던지는
방법까지 고려할 수 있다는 점도 언급하면 좋습니다.

**Q15. `AddressService.saveAddress`는 좌표를 `new BigDecimal(roadAddress.y()).setScale(8,
RoundingMode.HALF_UP)`으로 반올림합니다. 그냥 카카오가 준 문자열 그대로 저장하면 안 됐나요?**

DB 컬럼이 `precision = 11, scale = 8`로 고정 소수점 자릿수를 강제하기 때문입니다. 카카오 응답의
좌표 문자열은 소수점 자릿수가 항상 8자리로 고정되어 있다는 보장이 없어서, 그대로 저장하려 들면
컬럼 정의와 안 맞아 예외가 나거나 잘림이 생길 수 있습니다. `setScale(8, HALF_UP)`으로 저장 전에
명시적으로 자릿수를 맞춰서 **DB에는 항상 일관된 형태로만 들어가게** 만든 것입니다. 이게 Q8의
캐시 key 정규화(`stripTrailingZeros`)와 짝을 이루는 이유이기도 합니다 — DB 경유 좌표(8자리 고정)와
지오코딩 직후 좌표(가변 자릿수)가 같은 지점인데 문자열이 달라지는 문제를, 저장 시점(스케일 고정)과
캐시 조회 시점(스케일 제거) 양쪽에서 서로 다른 방식으로 대응하고 있는 것입니다.
