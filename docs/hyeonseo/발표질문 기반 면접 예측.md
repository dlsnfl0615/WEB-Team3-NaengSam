## 관찰 1: 매칭 도메인이 압도적으로 많이 나왔다 — 우연이 아니다

"매칭 설명", "동기화 단일 스레드로 해결한 코드 보여달라", "다중 인스턴스면 못 돌리네요", "챌린지를 위해 계속
고민한 부분" — 전부 매칭으로 수렴한다. **발표에서 매칭을 핵심 챌린지로 강조했기 때문에 면접관들이 "이 팀의
기술적 정체성 = 매칭"으로 인식했다**는 뜻이다. 면접에서는 이 라인이 더 좁고 깊게 파고들 것이다. 실제 코드를
보면 이 우려가 근거 있는 지적이다:

```java
// MatchingEngine.java
public class MatchingEngine implements InMemoryStateProbe {
    private final DelayQueue<QueuedAction> queue = new DelayQueue<>();
    // "모든 매칭 상태 변경을 이 스레드 하나로 직렬화하는 것이 목적이다"
    @PostConstruct
    public void start() {
        worker = Thread.ofVirtual().name("matching-engine").start(this::run);
    }
```

동시성 문제를 "락"이 아니라 **단일 워커 스레드로 모든 매칭 상태 변경을 순차 처리**해서 원천적으로 없앤
설계다. 우아한 해법이지만 **정의상 그 스레드가 도는 JVM 프로세스 하나에서만 유효**하다. 면접관이 "다중
인스턴스면 이걸로 못 돌리네요?"라고 물은 건 정확히 이 한계를 짚은 것이다. 이미 한 번 지적당한 질문이니,
면접에서는 **"그럼 어떻게 다중 인스턴스로 확장할 건가요?"**까지 반드시 나온다. 답을 준비해둘 것(예: 지역/
샤드별로 매칭 엔진을 나누고 리더 선출, 또는 분산 락 + 낙관적 재시도, Kafka 파티션 기반 이벤트 순서 보장
등 — 실제 구현이 없어도 "이런 방향으로 확장하겠다"는 설계 답은 필수).

## 관찰 2: "단일 인스턴스 전제"가 이 프로젝트 전체를 관통하는 아킬레스건

확인된 것만 나열해도:
- 세션 저장 = 톰캣 JVM 힙 (`LoginSession`, `ActiveSessionRegistry`)
- 로그인 대기열 동시 해싱 제어 = `Semaphore` + 로컬 `BlockingQueue`(`LoginQueue`)
- 매칭 상태 직렬화 = 단일 워커 스레드(`MatchingEngine`)

전부 "이 프로세스 하나가 살아있는 동안만 유효한 인메모리 상태"다. 면접관이 셋 중 어느 걸 찔러도 답의
구조는 같다: **"지금은 단일 인스턴스 전제로 설계했고, 그 이유는 [X]다. 다중 인스턴스로 가려면 [Y]가
필요하다"**는 템플릿을 매칭/세션/로그인대기열 세 군데 다 준비해둘 것. "Redis를 왜 핵심 부분에 안 넣고
로그인 대기열에만 넣었는가" 질문도 사실 같은 결이다 — "왜 세션이나 매칭 상태는 Redis로 안 옮겼나?"로
이어질 걸 예상해야 한다.

"이 그래프가 왜 이렇게 생겼는지" 즉흥 판단력 테스트. 실제 부하테스트 보고서(README의 8.12~8.18 링크)에 나온 정상 패턴(p95, 에러율, 커넥션 풀 사용률 등)을 눈에 익혀두고, "이 지표가 튀면 나는 이 순서로 원인을 좁혀간다"는 진단 절차를 말로 정리해둘 것. ## 결론: 우선순위

1. **매칭 도메인 완전 정복** — 특히 "단일 스레드 → 다중 인스턴스 한계"는 이미 한 번 지적당했으니 확장
   설계안까지 필수로 준비.
2. **"지금 구조의 한계 + 다음 단계"를 먼저 인정하는 화법**을 세션/로그인대기열/로깅(로키)/매칭 네
   군데 전부에 적용 — 이 발표에서 나온 질문들의 공통 패턴이 "너네 방식이 이런 상황에서도 되냐"는 한계
   검증이었기 때문에, 방어적으로 숨기기보다 "한계를 안다 + 다음 계획이 있다"는 태도가 제일 잘 먹힌다.
3. **패키지 구조·아키텍처·부하테스트·CI/CD처럼 반복 등장한 설명형 질문**은 이미 `cicd.md`와
   `면접준비.md`에 있으니 구두 설명 리허설만 남았다.
4. **Saga 패턴, 샤딩**은 코드베이스 어디에도 실제 구현이 없다(검색해서 확인). PT 슬라이드나 Notion에
   "향후 계획"으로만 언급됐을 가능성이 크다. 정확히 뭐라고 발표했는지 본인이 기억해내서, 그 맥락에 맞는
   개념 설명 + "왜 아직 못 넣었는지/어디에 넣을지"를 스스로 채워야 한다.
