# 포인트·머니·지갑 시스템

부르미의 포인트(충전·결제)와 드리미의 머니(정산·전환)가 어떻게 동작하는지, 어디서 트랜잭션이
걸리고 차감이 일어나는지, 오류 시 어떻게 롤백/방어되는지를 개념 → 코드 → 흐름 → 동시성/오류처리
순서로 정리.

> 대상 파일: `domain/payment/entity/{Wallet,PointWallet,MoneyWallet,PointTx,MoneyTx,PointLedger,
> MoneyLedger,Payment,Exchange,SettlementDetails}`, `domain/payment/service/{WalletService,
> PaymentService}`, `domain/payment/repository/*`, `domain/payment/exception/PaymentErrorCode`,
> 호출부인 `OrderPlacementService`, `DeliveryService`, `BoormiService`.

---

## 1. 개념 — 포인트 vs 머니, 지갑의 구조

### 포인트와 머니는 서로 다른 "돈"이다

- **포인트(Point)**: 부르미가 **PG로 충전**해서 갖는 재화. 배달 콜(주문)을 등록할 때 요금 결제에
  쓴다. 모든 회원이 하나씩 갖는다.
- **머니(Money)**: 드리미가 **배달을 수행하고 번** 재화. 배달이 완료돼 정산이 확정되면 쌓이고,
  포인트로 전환하거나(1:1, 수수료 없음) 계좌로 출금(`SettlementDetails`)할 수 있다.

한 계정이 부르미와 드리미 역할을 스와이프로 오가는 이 서비스의 특성상, **한 회원이 포인트 지갑과
머니 지갑을 둘 다 가질 수 있다** — 포인트 지갑으로 결제하고, 머니 지갑으로 정산을 받는다.

### 지갑 3분할 — `Wallet` / `PointWallet` / `MoneyWallet`

```java
// Wallet.java — 얇은 "지갑 신원" 테이블
public static Wallet create(UUID boormiId) { ... walletId = UUID.randomUUID(); ... }
```

`Wallet` 한 행이 `walletId`를 발급하고, `PointWallet`과 `MoneyWallet`이 **그 `walletId`를 그대로
자신의 PK로 공유**한다(FK가 아니라 PK 자체를 공유 — 항등 관계). 셋 다 회원가입 시점에
`WalletService.createWallet`이 한 번에 만든다.

```java
@Transactional
public void createWallet(UUID boormiId) {
    Wallet wallet = walletRepository.save(Wallet.create(boormiId));
    pointWalletRepository.save(PointWallet.create(wallet.getWalletId()));
    moneyWalletRepository.save(MoneyWallet.create(wallet.getWalletId()));
}
```

왜 지갑을 3개 테이블로 나눴는가: `Wallet`은 "이 회원이 지갑을 가지고 있다"는 신원만 나타내고,
`PointWallet.amount`/`MoneyWallet.amount`(+`pendingAmount`)처럼 **실제 잔액 컬럼은 각자 다른
테이블에 분리**돼 있다. 포인트와 머니는 갱신 빈도·잠금 대상이 서로 다르므로(결제는 포인트 지갑만
잠그고, 정산은 머니 지갑만 잠그면 됨), 하나의 넓은 지갑 테이블에 다 넣기보다 분리해두는 게 락 범위를
좁히는 데 유리하다.

### "거래(Tx)"와 "원장(Ledger)"을 분리한 이유 — 회계의 더블 엔트리 스타일

이 시스템에서 가장 중요한 설계 포인트다. 잔액이 바뀌는 모든 이벤트마다 **두 종류의 레코드**가
따로 남는다.

| | 역할 | 예시 테이블 |
|---|---|---|
| **Tx (거래)** | 거래 **1건의 현재 상태**를 나타낸다. 상태가 바뀌면(PENDING→PAID→REFUNDED) 같은 행이 전이한다 | `PointTx`, `MoneyTx` |
| **Ledger (원장)** | 그 거래로 인해 잔액이 **얼마나, 어느 방향으로** 움직였고 그 결과 잔액이 얼마가 됐는지를 **불변 로그**로 남긴다 | `PointLedger`, `MoneyLedger` |

`PointTx`의 클래스 주석이 이 관계를 정확히 설명한다:

> *"환불은 새 행을 만들지 않고 원본 결제 행의 status를 REFUNDED_FULL로 전이시키므로, 4000원을
> 결제한 뒤 환불하면 이 테이블에는 net 0인 행 하나만 남는다. 개별 잔액 변동(-4000, +4000)은
> PointLedger가 로그로 남긴다."*

즉 "지금 이 거래가 어떤 상태인가"(멱등 처리·중복 방지에 필요)와 "잔액이 실제로 어떻게 오르내렸나"
(감사 이력·화면의 거래 내역에 필요)를 **서로 다른 테이블의 책임**으로 나눈 것이다. 하나로 합쳤다면
"환불됐다"는 사실과 "잔액이 두 번 바뀌었다"는 로그가 뒤섞여 이력 추적이 어려워진다.

### 상태(status) 정의

```java
public enum PointTxStatusCd { PENDING, PAID, REFUNDED_PARTIAL, REFUNDED_FULL }
public enum PointTxTypeCd   { CHARGE, PAYMENT, REFUND, EXCHANGE_IN }

public enum MoneyTxStatusCd { PENDING, SETTLED, REJECTED }
public enum MoneyTxTypeCd   { SETTLEMENT, REVERSAL, CLAIM_ADJUSTMENT, EXCHANGE_OUT }
```

포인트 결제(`PAYMENT`)만 유일하게 `PENDING`을 거친다 — **결제 시점에 잔액은 바로 빠지지만, 배달이
끝나야 지급이 "확정(PAID)"된다.** 충전(`CHARGE`)·전환(`EXCHANGE_IN`)은 받는 즉시 끝나는 거래라
처음부터 `PAID`로 만들어진다.

## 2. 전체 흐름

```
① 부르미가 포인트 충전 (PG 미연동, 항상 성공 가정)
   WalletService.chargePoint
   → Payment 생성 → PointTx(CHARGE, PAID) 생성 → PointWallet.charge(+금액) → PointLedger 기록

② 부르미가 주문 접수 → 포인트로 즉시 결제
   OrderPlacementService.place (주문 저장 + 결제를 한 트랜잭션으로)
   → PaymentService.payWithPoint
     → PointWallet 비관적 락 조회 → PointTx(PAYMENT, PENDING) 생성
     → PointWallet.deduct(-금액) → PointLedger 기록
   (여기서 잔액이 실제로 "차감"된다 — 단, 거래 상태는 아직 PENDING)

③-A 취소(픽업 단계, 드리미/부르미/관리자 누구든) → 즉시 전액 환불
   DeliveryService.doCancelByDreami/doCancelByBoormi/doCancelByAdmin
   → delivery.cancelBy(...) → orderService.cancel(...)
   → PaymentService.refundByPoint
     → PointTx를 비관적 락으로 조회 → markRefundedFull()
     → PointWallet.refund(+금액) → PointLedger 기록

③-B 배달 완료 → 지급 확정 + 드리미 머니 지갑 정산
   DeliveryService.doFinishDelivery
   → delivery.markDelivered() → orderService.complete(...)
   → PaymentService.settleOrder
     → PointTx.markPaid() (PENDING → PAID로 확정, 부르미 쪽은 이미 차감된 그대로 유지)
     → MoneyWallet 비관적 락 조회 → MoneyWallet.add(+금액)
     → MoneyTx(SETTLEMENT, SETTLED) 생성 → MoneyLedger 기록

④ 드리미가 머니를 포인트로 전환 (1:1, 수수료 없음)
   WalletService.exchangeMoneyToPoint
   → MoneyWallet 락(먼저) → deduct(-금액) → MoneyTx(EXCHANGE_OUT) → MoneyLedger
   → PointWallet 락(다음) → charge(+금액) → PointTx(EXCHANGE_IN) → PointLedger
   → Exchange로 두 거래를 짝지어 기록
```

한 회원 안에서 포인트와 머니가 완전히 독립적으로 움직이다가, **주문 하나를 매개로**
부르미의 포인트 차감(②)과 드리미의 머니 적립(③-B)이 이어지는 구조다. 수수료는 떼지 않아서 부르미가
낸 포인트 금액이 그대로 드리미의 머니로 정산된다(`PaymentService.settleOrder` 주석: *"수수료는 떼지
않으므로 결제 금액이 그대로 드리미 몫이 된다"*).

## 3. 코드 레벨 상세 — 차감·적립이 정확히 어떻게 일어나는가

### 결제(`payWithPoint`) — 트랜잭션 경계와 차감 순서

```java
@Transactional
public void payWithPoint(UUID boormiId, UUID orderId, long amount) {
    PointWallet pointWallet = lockPointWallet(boormiId);                       // ① 지갑을 락으로 잠금

    if (pointTxRepository.findByOrderIdAndType(orderId, PointTxTypeCd.PAYMENT).isPresent()) {
        throw new BusinessException(PaymentErrorCode.ALREADY_PAID);            // ② 중복 결제 사전 검사
    }

    PointTx pointTx = pointTxRepository.save(
            PointTx.createPending(pointWallet.getWalletId(), PointTxTypeCd.PAYMENT, amount, null, orderId)); // ③ 거래 행 먼저 생성(PENDING)

    pointWallet.deduct(amount); // ④ 잔액이 모자라면 여기서 예외 → 트랜잭션 전체 롤백

    pointLedgerRepository.save(PointLedger.create(pointWallet.getWalletId(),
            pointTx.getPointTxId(), -amount, pointWallet.getAmount()));        // ⑤ 원장에 -amount, 변경 후 잔액 기록
}
```

순서가 **거래 기록(POINT_TX) → 지갑 차감 → 원장 기록**인 이유는, 나중에 잔액과 거래 이력을 대조
검증할 때 "이 거래가 만들어진 시점"과 "그로 인해 잔액이 바뀐 시점"을 항상 짝지을 수 있게 하기
위해서다. `PointWallet.deduct`는 엔티티 스스로 잔액 검사를 하고, 모자라면
`BusinessException(INSUFFICIENT_POINT)`를 던진다 — **이 예외가 `@Transactional` 메서드 밖으로
전파되므로, ①~③에서 이미 만든 `PointTx` row까지 포함해 전체가 자동 롤백**된다(방금 저장한
`PointTx`도 커밋 전이라 DB에 남지 않는다).

### 환불(`refundByPoint`) — 이중 환불을 막는 락

```java
@Transactional
public void refundByPoint(UUID orderId) {
    PointTx pointTx = pointTxRepository.findByOrderIdAndTypeForUpdate(orderId, PointTxTypeCd.PAYMENT) // 비관적 락으로 조회
            .orElseThrow(() -> new BusinessException(PaymentErrorCode.PAYMENT_NOT_FOUND));

    if (!pointTx.markRefundedFull()) {   // 이미 REFUNDED_FULL이면 false → 그냥 조용히 종료(멱등)
        return;
    }

    PointWallet pointWallet = pointWalletRepository.findByIdForUpdate(pointTx.getWalletId())
            .orElseThrow(() -> new BusinessException(PaymentErrorCode.WALLET_NOT_FOUND));

    pointWallet.refund(pointTx.getAmount());
    pointLedgerRepository.save(PointLedger.create(...));
}
```

`PointTxRepository.findByOrderIdAndTypeForUpdate`에 `@Lock(PESSIMISTIC_WRITE)`가 걸려 있고, 그
이유가 리포지토리 주석에 아주 구체적으로 남아있다:

> *"락 없이 읽으면 동시 취소 두 건이 같은 PENDING 스냅샷을 보고 둘 다 전이에 성공해 잔액이 두 번
> 복구된다(이중환불). 먼저 락을 잡은 쪽이 커밋할 때까지 나머지는 대기했다가 최신 상태를 다시
> 읽는다."*

**이건 실제로 이 팀이 겪은 트러블슈팅 사례**(팀 위키: "매칭 단계 취소시 포인트 이중 환불 문제")와
직결된다. `markRefundedFull()`이 "상태 확인 → 전이"라는 check-then-act이기 때문에, 락 없이는
동시에 취소 요청이 두 번 들어왔을 때 둘 다 "아직 REFUNDED_FULL이 아니다"라는 같은 스냅샷을 보고
둘 다 환불을 실행해 잔액이 두 배로 복구될 수 있다. 락을 걸어 이 판단과 전이를 직렬화해서 막는다.

### 정산 확정(`settleOrder`) — 부르미의 결제 확정 + 드리미의 머니 적립을 한 트랜잭션으로

```java
@Transactional
public void settleOrder(UUID orderId, UUID dreamiId) {
    PointTx pointTx = pointTxRepository.findByOrderIdAndType(orderId, PointTxTypeCd.PAYMENT)
            .orElseThrow(() -> new BusinessException(PaymentErrorCode.PAYMENT_NOT_FOUND));

    if (!pointTx.markPaid()) {   // 이미 확정됐거나 환불된 거래면 머니를 건드리지 않고 종료(멱등)
        return;
    }

    MoneyWallet moneyWallet = lockMoneyWallet(dreamiId);
    moneyWallet.add(pointTx.getAmount());

    MoneyTx moneyTx = moneyTxRepository.save(MoneyTx.createSettled(...));
    moneyLedgerRepository.save(MoneyLedger.create(...));
}
```

부르미의 `PointTx`를 `PAID`로 확정하는 것과, 드리미의 `MoneyWallet`에 같은 금액을 적립하는 것이
**하나의 트랜잭션**으로 묶여 있다. 만약 이 둘이 별도 트랜잭션이었다면(예: 이벤트로 비동기 처리),
"포인트는 확정됐는데 드리미 머니는 안 쌓이는" 정합성 문제가 생길 수 있다 — 이 서비스는 그런 위험을
감수하지 않고 동기 트랜잭션 하나로 처리한다(매칭 엔진처럼 별도 스레드로 넘기지 않는다).

### 머니→포인트 전환 — 락 순서를 고정해 데드락을 피함

```java
@Transactional
public WalletDto exchangeMoneyToPoint(UUID boormiId, ExchangeRequest request) {
    ...
    MoneyWallet moneyWallet = moneyWalletRepository.findByIdForUpdate(walletId)...  // ① 머니 지갑을 먼저 락
    moneyWallet.deduct(amount);
    ...
    PointWallet pointWallet = lockPointWallet(walletId);                           // ② 포인트 지갑을 그다음 락
    pointWallet.charge(amount);
    ...
    exchangeRepository.save(Exchange.create(...));  // 두 거래를 짝지어 기록
}
```

메서드 주석: *"두 지갑을 모두 잠그므로 락 순서를 항상 머니 → 포인트로 고정해 다른 트랜잭션과
엇갈린 순서로 잡는 일이 없게 한다."* 만약 어떤 코드는 "포인트 먼저, 머니 나중"으로, 어떤 코드는
"머니 먼저, 포인트 나중"으로 락을 잡으면, 두 트랜잭션이 서로 반대 순서로 락을 기다리다 영원히
멈추는 **데드락**이 생길 수 있다. 이 프로젝트는 "지갑을 두 개 이상 잠글 일이 있으면 항상 같은
순서로 잠근다"는 규칙으로 이걸 원천 차단한다.

## 4. 동시성 제어 — 어디에 락을 걸었는가

| 대상 | 락 종류 | 왜 |
|---|---|---|
| `PointWallet.findByIdForUpdate` | 비관적 쓰기 락 | 잔액 check-then-act(확인 후 차감)를 직렬화. 락 없이 동시 결제 두 건이 같은 잔액을 읽으면 둘 다 통과할 수 있음 |
| `MoneyWallet.findByIdForUpdate` | 비관적 쓰기 락 | 위와 같은 이유 |
| `PointTx.findByOrderIdAndTypeForUpdate` | 비관적 쓰기 락 | 환불의 check-then-act(REFUNDED_FULL 여부 확인 후 전이)를 직렬화. 없으면 이중 환불 발생(3절 참고) |
| `UQ_POINT_TX_ORDER_TYPE` (`order_id`, `type` 유니크 제약) | DB 제약(락이 아니라 최종 방어선) | `payWithPoint`의 사전 존재 검사(`findByOrderIdAndType`)가 경합으로 동시에 통과되더라도, 두 번째 INSERT는 이 제약이 막아준다 |

**이중 방어 구조**를 눈여겨볼 만하다 — `payWithPoint`는 애플리케이션 레벨에서 "이미 결제됐는지"를
먼저 확인(`ALREADY_PAID`)하지만, 이 검사 자체는 락이 없는 일반 조회다. 그래서 그 검사와 저장 사이의
아주 짧은 틈에 동시 요청이 둘 다 통과할 가능성이 이론적으로 남는데, 이 마지막 구멍을 **DB 유니크
제약**이 막아준다. 애플리케이션 레벨 검사는 "보통의 경우 빠르게 걸러내는 용도", DB 제약은 "경합이
나더라도 데이터 정합성이 절대 깨지지 않게 하는 최종 안전장치"라는 역할 분담이다.

## 5. 오류 발생 시 롤백 처리

### 5.1 `@Transactional` 하나로 묶인 범위 안에서는 예외 = 전체 롤백

가장 기본적인 메커니즘: 위에서 본 모든 메서드(`payWithPoint`, `refundByPoint`, `settleOrder`,
`chargePoint`, `exchangeMoneyToPoint`)는 전부 `@Transactional`이 걸려 있고, 그 안에서
`BusinessException`이 던져지면 **AOP 프록시가 자동으로 전체 트랜잭션을 롤백**한다
(`spring-tx-interview.md` 5절 참고). 예를 들어 `payWithPoint`에서 `pointWallet.deduct(amount)`가
`INSUFFICIENT_POINT`를 던지면, 그 직전에 저장했던 `PointTx` row까지 전부 커밋되지 않고 사라진다 —
"거래 기록만 남고 실제 차감은 안 된" 반쪽 상태가 생기지 않는다.

### 5.2 더 큰 트랜잭션에 포함되는 경우 — 주문 접수의 예

```java
// OrderPlacementService.place
@Transactional
public UUID place(Orders orders, long amount) {
    orderService.createOrders(orders);
    paymentService.payWithPoint(orders.getBoormiId(), orders.getOrderId(), amount);  // 여기서 실패하면?
    if (matchingService.isActiveGroupExists(orders.getOrderId())) {
        throw new BusinessException(GeneralErrorCode.CONFLICT);
    }
    eventPublisher.publishEvent(new MatchingStartRequestedEvent(orders));
    return orders.getOrderId();
}
```

`place()` 자체가 `@Transactional`이고, 그 안에서 호출되는 `payWithPoint`는 **같은 트랜잭션에
합류**한다(Spring 기본 전파 속성 `REQUIRED`). 그래서 주석 그대로 *"결제가 실패하면 주문 저장까지
함께 롤백된다"* — 포인트가 부족해서 결제가 실패하면, 방금 저장했던 `Orders` row도 함께 사라진다.
"주문은 생겼는데 결제는 실패한" 상태가 나올 수 없다. (참고: 이 클래스가
`BoormiService.subscribeOrder`와 분리된 이유는 외부 카카오 API 호출을 트랜잭션 밖으로 빼기 위해서인데,
`spring-tx-interview.md` 9절에서 다룬 "트랜잭션 안에서 외부 API를 부르면 안 되는 이유"와 정확히
같은 원칙이다.)

### 5.3 멱등성으로 "재시도"에 안전하게 대응 — 예외가 아니라 조용한 무시

환불·정산은 실패(예외)와 별개로, **"이미 처리됐다"는 상황을 예외가 아니라 조용한 종료로
처리**한다.

```java
public boolean markRefundedFull() {
    if (this.status == PointTxStatusCd.REFUNDED_FULL) {
        return false;   // 예외를 던지지 않는다
    }
    ...
    return true;
}
```

`refundByPoint`/`settleOrder`는 이 반환값이 `false`면 **잔액을 건드리지 않고 그대로 메서드를
끝낸다.** 왜 예외가 아니라 이렇게 처리하는가 — 취소/완료 처리는 여러 경로(드리미/부르미/관리자
취소, 배달 완료)에서 호출될 수 있고, 네트워크 재시도나 이벤트 중복 처리로 같은 주문에 대해 같은
호출이 두 번 들어올 가능성이 있다. 이때 두 번째 호출이 예외를 던지면 그 트랜잭션 전체가 실패
처리돼 알림 등 다른 부수 작업까지 막힐 수 있는데, "이미 끝난 일"이라는 걸 조용히 인지하고 넘어가면
**같은 요청이 여러 번 들어와도 결과가 항상 같다**(멱등성)는 안전한 성질을 얻는다.

### 5.4 잔액 부족은 "복구할 게 없는" 단순 실패

`deduct()`가 잔액 부족으로 예외를 던지는 경우는 위 5.1의 트랜잭션 롤백으로 충분하다 — 아직 아무
것도 확정되지 않은 상태(같은 트랜잭션 안)라 "롤백"이라는 개념 자체가 단순하다. 반면 이미 커밋되어
확정된 거래(예: 정산이 끝난 뒤 뭔가 잘못됨)를 되돌리는 건 이 서비스 범위에는 없다 — 그런 경우는
`MoneyTxTypeCd.REVERSAL`(정산 취소)이나 `CLAIM_ADJUSTMENT`(보상 조정) 타입이 enum에 선언돼 있어
"이런 케이스가 있을 수 있다"는 건 설계에 반영돼 있지만, 실제로 그 타입을 생성하는 서비스 코드는
`PaymentService`/`WalletService`에 아직 없다 — 즉 **커밋 후 되돌리기(보상 트랜잭션)는 이 시스템에
아직 구현되지 않은 부분**이라는 것도 정직하게 알아둘 만하다(지난번 "매칭 확정 후 Delivery
미생성" 문제에서 다룬 것과 같은 종류의 한계 — 한 번 커밋된 거래를 되돌리려면 명시적인 보상 로직이
따로 필요한데, 여기선 아직 그 코드 자체가 없다).

## 6. 요약

- **포인트**는 부르미가 충전해서 주문 결제에 쓰고, **머니**는 드리미가 배달을 완료해 정산받는
  완전히 별도의 재화다. 둘 다 1:1로 서로 전환 가능하다.
- 잔액이 바뀌는 모든 사건은 **거래(Tx, 현재 상태)**와 **원장(Ledger, 불변 변동 로그)** 두 곳에
  나눠 기록된다.
- 결제는 "즉시 차감 + PENDING", 배달 완료 시 "PAID 확정 + 드리미 머니 적립"이라는 **두 단계**로
  나뉜다 — 주문이 취소되면 그 PENDING 상태에서 환불로 빠진다.
- 지갑을 다루는 모든 곳은 **비관적 락**(`findByIdForUpdate`)으로 잔액 확인과 변경을 직렬화하고,
  여러 지갑을 동시에 잠글 때는 **항상 같은 순서(머니→포인트)**로 잠가 데드락을 피한다.
- 오류 시 처리는 두 갈래다 — **아직 확정 안 된 실패**(잔액 부족 등)는 `@Transactional`의 자동
  롤백으로, **이미 처리된 요청의 재시도**는 예외 대신 멱등하게 조용히 무시하는 방식으로 대응한다.
  다만 이미 커밋된 거래를 사후에 되돌리는 보상 로직(REVERSAL 등)은 타입만 정의돼 있고 아직 구현은
  없다.
