# `global` 패키지 면접 대비

> 원본: [global-package.md](./global-package.md) (9개 패키지 전체 상세 정리).
> 이 문서는 그중에서 **면접에서 실제로 나올 확률이 높은 것만 추려** 답변 톤으로 다시 정리한 것.
> `global`은 내가 직접 짠 코드가 아니므로, "내용"보다 "어떻게 답할지" 전략이 절반이다.

---

## 0. 답변 전략 — 안 짠 코드를 질문받았을 때

**원칙: 절대 "몰라요"로 끝내지 않는다. 그렇다고 짠 것처럼 말하지도 않는다.**

오프닝 한 문장으로 정직하게 선을 긋고, 곧바로 아는 내용으로 들어간다:

> "이 부분은 제가 직접 구현하지는 않았지만, 로그인/응답 처리처럼 제 도메인 코드가 매번 의존하는 인프라라 코드 리뷰와 PR을 보면서 구조와 이유는 파악해뒀습니다."

이렇게 말하면 되는 이유(`면접준비.md`의 "협업/팀워크" 섹션과 같은 논리):
- 면접관이 진짜 궁금한 건 "네가 이 줄을 타이핑했냐"가 아니라 **"팀 프로젝트 전체 구조를 이해하고 협업할 수 있는 사람이냐"**다.
- **암기보다 "왜"가 먼저 나오면 통과된다.** 세세한 구현(메서드 이름, 필드명)은 몰라도, "이걸 왜 이렇게 설계했는가"를 한 문장으로 말할 수 있으면 충분히 이해하고 있다는 인상을 준다.
- 반대로 모르는 세부까지 아는 척하다가 꼬리 질문에서 막히는 게 제일 위험하다. **큰 그림(무엇을/왜)은 자신 있게, 엣지케이스(정확한 임계값, 특정 예외 처리 분기)는 "그 부분까지 상세히는 못 봤습니다. 다만 원칙은 ~였던 걸로 기억합니다" 정도로 선을 긋는다.**

막히면 쓰는 탈출 문장:
> "정확한 구현 디테일까지는 기억이 안 나지만, 이 계층이 존재하는 이유는 [원칙]이었고, 그래서 [비슷한 원칙이 적용된 제 도메인 코드]에서도 같은 방식을 따랐습니다."
→ 이렇게 **내 도메인 코드로 다시 연결**시키면 "이해도 + 자기 코드에 대한 자신감"을 동시에 보여줄 수 있다.

## 1. 우선순위 — 뭐부터 알아야 하나

| 우선순위 | 대상 | 이유 |
|---|---|---|
| ★★★ 필수 | `commonResponse` + `exception` | 모든 API 응답이 여길 거치므로 "응답 포맷 어떻게 관리했나요?" 류 질문이 거의 확정적으로 나온다(`면접준비.md` 6번에 이미 예상질문 있음) |
| ★★★ 필수 | `session` | 로그인은 모든 팀원 도메인이 걸쳐 있어 "어떻게 로그인 인가를 처리했나요?"는 백엔드 지원자에게 거의 반드시 나온다 |
| ★★☆ 권장 | `sse` | "왜 SSE인가"는 이미 `면접준비.md`에 있는 단골 질문 — `global.sse`가 그 구현체다 |
| ★☆☆ 여유 | `swagger`, `config` | 나오면 한두 문장으로 답변 가능한 수준이면 충분, 깊게 팔 필요 없음 |
| ☆☆☆ 스킵 가능 | `notification`(웹푸시/SMS), `admin` | 니치한 영역. 시간이 부족하면 "이런 게 있다" 정도의 존재만 알아도 됨 |

## 2. `commonResponse` + `exception` — 응답/예외 처리 (★★★)

### 한 줄 요약
모든 API는 `{isSuccess, code, message, result}` 봉투로 응답한다. 컨트롤러는 **DTO만 반환**하고, 성공 응답은 `ResponseBodyAdvice` 구현체(`CommonResponseAdvice`)가, 예외는 `@RestControllerAdvice`(`GlobalExceptionHandler`)가 각각 가로채 자동으로 봉투를 씌운다. 그래서 어떤 도메인 컨트롤러든 응답 모양이 항상 같다.

### 예상 Q&A

**Q. 공통 응답 포맷은 어떻게 관리했나요?**
> 컨트롤러는 순수 DTO나 void만 반환하고, `ResponseBodyAdvice`를 구현한 `CommonResponseAdvice`가 컨트롤러 리턴값이 실제로 직렬화되기 직전에 가로채서 `{isSuccess, code, message, result}` 형태로 감쌉니다. 이 덕분에 응답 조립 코드가 컨트롤러마다 반복되지 않고 한 곳에 모입니다.

**Q. 예외 처리는 어떻게 했나요?**
> 도메인별 에러코드 enum(`AuthErrorCode` 등)이 `BaseErrorCode` 인터페이스를 구현하고, 서비스 로직은 `throw new BusinessException(errorCode)`만 하면 됩니다. `@RestControllerAdvice`인 `GlobalExceptionHandler`가 이걸 잡아서 에러코드가 가진 HTTP 상태·메시지로 공통 포맷 응답을 만듭니다. 컨트롤러/서비스에는 try-catch가 전혀 없습니다.

### 꼬리 질문 대비
- **"ResponseBodyAdvice가 뭔가요?"** → Spring MVC가 컨트롤러 리턴값을 실제 HTTP 바디로 직렬화하기 직전에 가로채는 확장점. `@RestControllerAdvice` + 이 인터페이스 구현으로 등록.
- **"왜 basePackages를 한정해뒀나요?"** → 범위를 안 좁히면 springdoc이 `/v3/api-docs`를 만드는 내부 컨트롤러도 걸려서 Swagger 문서 응답까지 봉투로 감싸버려 Swagger UI가 깨진다(실제 코드 주석에 있는 이유).
- **"4xx와 5xx를 로그에서 다르게 다루던데요?"** → 5xx는 서버 버그니까 스택트레이스 전체를 error로, 4xx(로그인 실패 등)는 의도된 흐름이라 warn 한 줄 + 던진 지점만 남긴다. (이건 `GlobalExceptionHandler` 딥다이브 시 이미 정리해둔 내용 — [로그인 경로.md](./로그인 경로.md) 위 대화 참고)

## 3. `session` — 로그인 인증 인프라 (★★★)

### 한 줄 요약
JWT가 아니라 **서블릿 `HttpSession` + 쿠키(JSESSIONID)** 기반. `LoginCheckInterceptor`가 `/api/**` 요청을 가로채 로그인을 강제하고(`@PublicApi` 붙은 것만 예외), `@LoginUser`라는 커스텀 애노테이션이 `HandlerMethodArgumentResolver`를 통해 컨트롤러 파라미터에 로그인 사용자 UUID를 자동 주입한다. 추가로 `ActiveSessionRegistry`가 **계정당 활성 세션을 1개로 강제**한다(다른 기기에서 로그인하면 이전 세션이 밀려남).

### 예상 Q&A

**Q. 로그인 인가는 어떻게 처리하나요?**
> 세션 기반입니다. `/api/**`는 기본적으로 로그인이 필요하고, `HandlerInterceptor`인 `LoginCheckInterceptor`가 컨트롤러 진입 전에 세션 유무를 검사합니다. 로그인/회원가입처럼 예외적으로 로그인 없이 호출돼야 하는 API에는 `@PublicApi` 애노테이션을 붙여 검사를 건너뛰게 했습니다.

**Q. 컨트롤러에서 로그인 사용자 정보는 어떻게 가져오나요?**
> `@LoginUser UUID boormiId` 처럼 파라미터에 커스텀 애노테이션만 붙이면 됩니다. 내부적으로는 `HandlerMethodArgumentResolver`를 구현한 리졸버가 있어서, Spring이 컨트롤러 메서드를 리플렉션으로 호출하기 직전에 이 애노테이션이 붙은 파라미터를 발견하면 세션에서 사용자 UUID를 꺼내 자동으로 채워줍니다. `@RequestParam`, `@PathVariable`이 동작하는 것과 같은 메커니즘입니다.

**Q. 한 계정으로 여러 기기에서 동시 로그인이 되나요?**
> 안 됩니다. `ActiveSessionRegistry`가 계정당 활성 세션을 하나만 유지하는 단일 진실 공급원 역할을 해서, 다른 기기에서 로그인하면 이전 세션이 자동으로 무효화되고 그 세션이 들고 있던 실시간 연결(SSE)도 함께 끊깁니다. "나중에 로그인한 쪽이 이긴다" 정책입니다.

### 꼬리 질문 대비
- **"세션 정보는 어디 저장되나요? Redis 같은 외부 저장소 안 쓰나요?"** → 기본은 톰캣의 인메모리 `HttpSession`. `ActiveSessionRegistry`(계정당 세션 1개 관리)도 `ConcurrentHashMap` 기반 인메모리다. (Redis는 세션 저장용이 아니라 **로그인 대기열**에만 쓰인다 — 이건 `domain/user` 영역이라 혼동하지 않도록 구분해서 답해야 함.)
- **"세션 vs JWT?"** → 이미 `면접준비.md`에 정리된 답변 그대로: 서버 측 강제 무효화 가능, 토큰 탈취 시 즉시 로그아웃 가능.
- **"HandlerMethodArgumentResolver를 더 설명해달라"** → `supportsParameter()`로 이 리졸버가 처리할 파라미터인지 확인하고, `resolveArgument()`가 실제 값을 만들어 반환한다. `WebConfig`가 `addArgumentResolvers(...)`로 이 리졸버를 등록해뒀기 때문에 Spring이 이 리졸버의 존재를 안다.
- **"관리자 여부는 어떻게 확인하나요?"** → `@LoginUser`와 구조는 같은 `@AdminUser`가 따로 있고, 리졸버 안에서 DB로 `Boormi.isAdmin()`을 한 번 더 확인한다.

## 4. `sse` — 실시간 이벤트 (★★☆)

### 한 줄 요약
계정당 SSE(Server-Sent Events) 연결을 **최대 1개**만 허용. 매칭 오퍼, 배달 위치 갱신 등의 실시간 이벤트를 이 연결로 흘려보낸다. 전송은 단일 가상 스레드로 오프로딩해 **이벤트 발생 순서 = 전송 순서**를 보장한다.

### 예상 Q&A

**Q. 실시간 통신은 어떻게 구현했나요? 왜 WebSocket이 아니라 SSE인가요?**
> (이미 `면접준비.md`에 있는 답변) 서버→클라이언트 단방향 이벤트가 주된 패턴이라 SSE를 썼습니다. HTTP 표준이라 별도 프로토콜이 필요 없고 프록시 친화적입니다. `global.sse` 패키지가 계정당 하나의 연결만 유지하도록 관리하고, 여러 도메인(매칭, 배달)이 이 연결 위로 이벤트를 실어 보냅니다.

**Q. 한 사용자가 여러 탭을 열면 어떻게 되나요?**
> 연결을 거부하지 않고 새 탭이 열릴 때마다 이전 연결을 즉시 새 연결로 교체합니다. 즉 항상 최신 탭 하나만 실시간 이벤트를 받습니다.

### 꼬리 질문 대비
- **"연결이 죽었는지 어떻게 감지하나요?"** → 주기적으로 heartbeat 주석을 보내서, 전송 실패하면 그 연결을 정리하는 방식.
- **"이벤트 순서는 어떻게 보장하나요?"** → 전송을 단일 스레드로만 처리해서 순서가 섞이지 않게 했다.

## 5. 나머지 (`swagger`, `config`, `notification`, `admin`) — ★☆☆ / 스킵 가능

시간이 부족하면 아래 한 줄씩만 기억해도 방어는 된다.

| 패키지 | 한 줄 |
|---|---|
| `swagger` | 에러코드 enum·응답 봉투 모양을 Swagger 문서에 자동 반영해서, 문서와 실제 응답이 어긋나지 않게 했다. |
| `config` | CORS, 인터셉터/리졸버 등록, `Clock` 빈(테스트에서 시간 고정용), Redis Lua 스크립트 빈 등록 같은 전역 설정을 모아둔 곳. |
| `notification` | 도메인이 알림 보낼 때 SSE/웹푸시를 직접 안 부르고 이 파사드 하나만 거치게 해서, 이벤트별로 어떤 채널(인앱/웹푸시)로 보낼지 정책표(`NotificationPolicy`)로 관리한다. |
| `admin` | 매칭/세션 상태가 DB가 아니라 JVM 힙에 있어서, 정리 안 되고 쌓이는 자료구조가 있는지 관리자 API로 스냅샷 조회할 수 있게 한 진단 도구. |

이 넷은 질문이 나와도 "이런 이유로 존재한다"까지만 말하고, 구현 세부는 "직접 짜지 않아 상세히는 모른다"로 정직하게 넘겨도 괜찮은 영역이다(★★★ 두 개만큼 물어볼 확률이 높지 않음).

---

## 6. 요약 카드 (마지막 훑어보기용)

- **commonResponse/exception**: 컨트롤러는 DTO만 반환 → `ResponseBodyAdvice`가 성공 봉투, `@RestControllerAdvice`가 예외 봉투를 자동으로 씌운다. 서비스는 `BusinessException(errorCode)`만 던지면 끝.
- **session**: 세션(쿠키) 기반 인증. `LoginCheckInterceptor`가 로그인 강제, `@LoginUser`가 `HandlerMethodArgumentResolver`로 사용자 UUID 자동 주입, `ActiveSessionRegistry`가 계정당 세션 1개 강제.
- **sse**: 계정당 연결 1개, 단일 스레드 전송으로 순서 보장, 여러 도메인이 공유하는 실시간 알림 통로.
- **나머지**: 존재 이유 한 줄씩만 — 못 짰지만 안다는 티는 낼 수 있는 수준.
