# k6 부하테스트 계획

> 초안. 우선순위/범위는 논의하면서 계속 바뀔 수 있다.

## 기본 원칙

**단독 엔드포인트 테스트 → 시나리오(흐름) 테스트** 순서로 간다. 단독 테스트는 변수가
하나뿐이라 해석이 쉽고 부작용 없는 경우 반복하기 안전하다. 하지만 실제 트래픽은 여러 API가
같은 DB 커넥션풀/CPU를 동시에 나눠 쓰므로, 단독 테스트 결과는 "낙관적인 상한선"에 가깝다.
먼저 단독 테스트로 각 API의 개별 한계·버그를 찾고, 그다음 합친 시나리오로 "동시 사용자가
몇 명까지 버티는지"를 본다.

**선행 API(로그인 등)를 스크립트에 넣을지는 테스트 대상이 신원에 의존하는지로 결정한다.**

- 테스트 대상이 요청자 신원을 안 본다(예: `/dreami/calls/nearby`는 `@LoginUser`가 없어서
  로그인된 세션만 있으면 누구든 같은 결과) → 세션 하나 만들어서 재사용해도 그 API의 처리량
  측정엔 문제 없다. 로그인은 `setup()`에서 한 번만.
- 테스트 대상이 요청자별로 동작이 달라진다(예: 주문 접수는 `boormiId`별
  `MAX_ACTIVE_ORDERS` 체크, 온라인 전환은 `dreamiId`별로 매칭엔진에 등록) → VU마다 독립된
  계정/세션이 필요하고, 로그인도 매 VU(또는 매 iteration)마다 실제로 수행해야 그 API를
  제대로 테스트하는 것이다.

## 진행 순서(초안)

1. **①번(콜 폴링)** — `loadtest/k6/matching-nearby-calls.js`. 카카오 무관, 세션 하나 공유로 충분.
2. **③번(순수 조회)** — 카카오 걱정 없이 데이터량을 안전하게 실험. ①과 병행 가능. `loadtest/k6/boormi-calls-list.js`(GET `/boormi/calls`), `loadtest/k6/dreami-dashboard.js`(GET `/dreami/dashboard`) 작성 완료.
3. **②번(로그인)** — 계정이 12개뿐이라 "동시 로그인 다수"는 흉내내기 어렵지만, 반복 로그인만으로도 PBKDF2 CPU 비용은 측정 가능. `loadtest/k6/login.js` 작성 완료.
4. **④번(주문 접수)** — `loadtest/k6/subscribe-order.js` 작성 완료(카카오 목/실호출 여부와 무관하게 스크립트는 동일 — 생성 직후 취소해서 계정당 활성 주문 5건 캡을 안 넘게 처리, ORDER_009 비율은 `order009Rate`로 서버 성능 지표와 분리). **실제 반복 실행은 카카오 목 전환 후에**.
5. **⑤번(100:100 통합 매칭)** — `loadtest/k6/mass-matching-100x100.js` 작성 완료. 좌표 분산은 스크립트가 온라인 등록/콜 등록 시점에 직접 흩뿌리도록 구현해서 시드 데이터에 좌표를 미리 넣을 필요는 없음. **부르미 100명·승인된 드리미 100명 계정은 `backend/sql/test-seed-accounts.sql` 재작성으로 준비 완료**(`boormi1..100@test.test`/`dreami1..100@test.test`, 비밀번호 `string`) — 이제 남은 선행 조건은 ④의 카카오 비용 문제 해결뿐. 단독 시나리오(①~④)로 개별 병목을 먼저 잡은 뒤 마지막에 진행. `-e BOORMI_COUNT=`/`-e DREAMI_COUNT=`를 작게 주면 계정 몇 개만으로 로직 검증 가능.

## 미해결 사항

- **④·⑤번의 카카오 실호출 비용**: 콜 하나 열 때마다 실제 카카오 API 3회 호출(⑤는 최대 100건이라 300회). 완화 방식 미확정 — `CoordinatesService`/`KakaoDirectionsService`는 `Uploader`/`SmsSender`와 달리 인터페이스가 없어 프로퍼티 스위치로 목 전환이 안 되는 구조. 목 전환 작업 진행 중.
- **시드 데이터 정리 필요**: `backend/sql/test-seed-accounts.sql`을 부르미 100명·드리미 100명(비밀번호 `string`)으로 다시 만들면서 `test-seed-dreami-extra.sql`(구 dreami3~10 보강용)이 이제 중복·충돌 대상이 됨 — 같은 이메일(dreami3~10@test.test)을 다른 UUID로 다시 만들려고 해서 그대로 실행하면 UNIQUE 제약 위반. 삭제하거나 새 계정 규모에 맞게 다시 정리해야 함(아직 미처리).
