# PR 유형별 기술 질문

저녁 회고에서 PR을 놓고 물어볼 질문 모음이다. PR 성격에 맞는 걸 **1~2개만** 고른다.
많이 던지면 심문이 된다.

## 쓰는 법

이 파일의 질문은 그대로 읽으라고 있는 게 아니라 **틀**이다.
반드시 `gh pr diff` 로 본 실제 코드를 넣어서 구체화해라. 그래야 작성자가 답할 수 있다.

- 나쁨: "예외 처리는 어떻게 하셨어요?"
- 좋음: "`UserService.findById`에서 예외를 잡아서 null 리턴하시던데, 호출부에서 '없음'이랑 '조회 실패'를 어떻게 구분해요?"

질문을 던진 뒤에는 **반드시 다른 팀원에게 넘겨라.** "○○님은 어떻게 생각하세요?"
회고의 목적은 답을 찾는 게 아니라 팀원끼리 코드 얘기를 하게 만드는 것이다.

정답을 확인하는 톤이 아니라 궁금해서 묻는 톤을 유지해라. 이 팀은 서로 지적하기 어려워하는 팀이고,
네 질문이 심사처럼 들리면 다음부터 PR을 조용히 올리게 된다.

---

## 어느 PR에나 (하나만 고르기)

- 이 방식 말고 다른 선택지도 있었어요? 왜 이걸로 정하셨어요?
- 짜면서 제일 애매했던 부분이 어디예요?
- 이거 나중에 요구사항 바뀌면 어디부터 손대야 돼요?
- 다시 짠다면 뭘 다르게 할 것 같아요?
- 이 PR에서 리뷰어가 특히 봐줬으면 하는 부분이 있어요?

## 새 기능 (Feat)

- 이 기능 실패하는 경우가 뭐가 있어요? 그때 사용자한테 뭐가 보여요?
- 입력값 검증은 어디서 해요? (프론트 / 백엔드 / 둘 다)
- 동시에 두 명이 이걸 호출하면 어떻게 돼요?
- 데이터가 지금의 100배가 되면 이 부분 괜찮아요?
- 이 로직이 여기 있는 게 맞아요? 다른 계층으로 갈 수도 있었을까요?

## 버그 수정 (Fix)

- 원인이 정확히 뭐였어요?
- 같은 원인으로 터질 수 있는 다른 데는 없어요?
- 이 버그 다시 나면 바로 알 수 있어요? (테스트나 로그가 있는지)
- 증상만 막은 거예요, 원인을 고친 거예요?

## 리팩토링 (Refactor)

- 리팩토링 전후로 동작이 같다는 건 어떻게 확인했어요?
- 이걸 바꾸면서 영향받는 다른 코드는 없어요?
- 왜 지금 이걸 하셨어요? (뭐가 불편했는지)

## API / 백엔드

- 이 엔드포인트 응답 형태가 다른 API랑 일관돼요?
- 에러일 때 상태 코드랑 응답 바디가 어떻게 나가요?
- 쿼리 몇 번 나가요? N+1 날 여지는 없어요?
- 트랜잭션 경계가 어디예요?
- 인증/권한 체크는 어디서 걸려요?

## 프론트엔드

- 이 상태를 여기서 관리하는 게 맞을까요? 더 위로 올려야 할 것 같진 않아요?
- 로딩이랑 에러 상태는 화면에서 어떻게 보여요?
- 이 컴포넌트 다른 데서 재사용할 일이 있을까요?
- API 응답 늦으면 화면이 어떻게 돼요?
- 반응형이나 접근성 쪽에서 놓친 부분 있을까요?

## 테스트가 없는 PR

비난처럼 들리지 않게 조심할 것. "왜 테스트 없어요?"가 아니라 "붙일 만한 데가 있나?"로 접근한다.

- 이 중에 테스트로 잡아두면 좋을 부분이 있을까요?
- 지금은 어떻게 확인하셨어요? (수동 확인이면 그것도 정보다)
- 나중에 누가 이 코드 건드릴 때 뭘 깨뜨릴 수 있을까요?

## 팀 전체에 던지는 질문 (PR 하나에 매이지 않을 때)

- 오늘 코드 보면서 "우리 이건 정해두는 게 좋겠다" 싶은 거 있었어요?
- 반복해서 짜고 있는 코드 없어요? 공통으로 뺄 만한 거
- 서로 짠 코드 중에 아직 못 본 부분 있어요?
- 지금 우리 프로젝트에서 제일 위태로운 부분이 어디라고 생각해요?
