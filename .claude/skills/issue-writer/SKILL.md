# 이슈 작성 & 브랜치 생성

팀 규칙(`docs/git-convention.md`)은 **이슈 → 브랜치 → PR** 순서인데, 첫 단계가 번거로워서
자꾸 건너뛰게 된다. 웹에서 템플릿 고르고 섹션 채우고 번호 확인하고 터미널로 돌아와야 하니까.

**규칙을 지키는 게 안 지키는 것보다 편해야 규칙이 산다.** 이 스킬의 목표는 그거다.
사용자가 "이거 만들자" 한마디 하면 이슈 본문 작성부터 브랜치 생성까지 끝내주는 것.

---

## 1. 무엇을 할 건지 좁히기

사용자 설명이 한 줄이면 그대로 이슈에 넣지 마라. "재료 추가 기능"만 적힌 이슈는 나중에 본인도
무슨 범위였는지 모른다. 짧게 두세 개만 되물어 구체화한다.

**되묻기 전에 코드를 먼저 읽어라.** 관련 파일이 이미 있으면 직접 찾아보고 현재 구조를 파악한 뒤,
"영향 범위" 같은 섹션은 사용자에게 묻지 말고 네가 채워라. 사용자가 웹에서 직접 쓰는 것보다
나은 이슈가 나오는 지점이 바로 여기다. 사용자에게는 **코드를 봐도 알 수 없는 것**만 물어라
— 의도, 우선순위, 어디까지 할지.

**작업 단위가 크면 쪼개자고 제안해라.** "회원 기능 전체" 같은 이슈는 브랜치 하나로 감당이 안 되고,
PR이 거대해져서 팀 규칙인 2인 리뷰가 형식적으로 변한다. 다만 강요하진 말고 이유를 설명하고
사용자가 정하게 해라. 지금 급한 상황일 수도 있다.

---

## 2. 템플릿 고르기

`.github/ISSUE_TEMPLATE/` 를 읽어 현재 어떤 템플릿이 있는지 확인한다. 내용을 기억에 의존하지 말고
매번 읽어라 — 팀이 템플릿을 늘리거나 고칠 수 있다.

현재는 두 종류다.

| 성격         | 파일                 | title prefix  | label         |
| ------------ | -------------------- | ------------- | ------------- |
| 새 기능·개선 | `feature_request.md` | `[FEAT] `     | `enhancement` |
| 리팩터링     | `refactoring.md`     | `[REFACTOR] ` | `refactoring` |

- frontmatter의 `title` prefix와 `labels` 를 그대로 따른다
- 본문 섹션 구조도 템플릿에서 읽어 쓴다
- `<!-- 이렇게 생긴 -->` 작성 가이드 주석은 **지우고** 실제 내용으로 채운다
- 정말 쓸 내용이 없는 섹션은 "해당 없음"이라고 쓴다. 빈칸으로 두면 나중에 안 채운 건지 없는 건지 모른다

**버그 리포트 템플릿은 아직 없다.** 커밋 컨벤션에는 `Fix` 타입이 있는데 짝이 되는 이슈 템플릿이
빠져 있다. 버그 이슈를 만들어야 하면 템플릿 없이 `[FIX] ` 제목 + `bug` 라벨로 만들고,
본문은 **재현 방법 / 기대 동작 / 실제 동작 / 환경** 정도로 구성해라.
그리고 "버그 템플릿도 하나 만들어두면 좋겠다"고 한 번만 언급해라. 매번 말하면 잔소리가 된다.

## 3. 이슈 생성

### 먼저 어느 레포인지 확인한다

이 레포는 `origin` 이 개인 포크(`seoki180/WEB-Team3-NaengSam`)이고 실제 협업은
`softeerbootcamp-8th/WEB-Team3-NaengSam` 에서 이뤄진다. `gh repo set-default` 는 설정돼 있지 않다.

다행히 개인 포크는 issues 기능이 꺼져 있어서 실수로 그쪽에 생성되면 에러가 난다.
조용히 잘못된 곳에 올라갈 위험은 없지만, 에러를 보고 헤매지 않도록 **팀 레포를 `--repo` 로 명시해라.**

```bash
gh repo set-default --view    # 현재 설정 확인
git remote -v                 # 포크 구조인지 확인
```

한 번에 `gh repo set-default softeerbootcamp-8th/WEB-Team3-NaengSam` 로 고정해두라고 권해라.
다음부터 이 확인 자체가 필요 없어진다.

### 보여주고 확인받은 뒤 생성한다

**자동으로 올리지 마라.** 이슈는 팀 전체가 보는 것이고, 한번 올라가면 알림이 나간다.
작성한 제목·라벨·본문을 대화창에 보여주고 "이대로 올릴까요?" 확인을 받아라.

```bash
gh issue create \
  --repo <소유자/레포> \
  --title "[FEAT] 재료 유통기한 알림" \
  --label enhancement \
  --body-file <임시파일>
```

본문은 임시 파일에 쓴 뒤 `--body-file` 로 넘겨라. 여러 줄 마크다운을 셸 인자로 직접 넣으면
따옴표와 백틱이 깨진다.

## 4. 브랜치 생성

생성된 이슈 번호로 `docs/git-convention.md` 규칙에 맞는 브랜치를 만든다.

```
{type}/{이슈번호}      예: Feat/1, Fix/12, Refactor/7
```

type은 커밋 컨벤션과 같은 6종(`Feat`, `Fix`, `Refactor`, `Test`, `Docs`, `Etc`)이고 **대문자로 시작**한다.
이슈 템플릿과 매칭하면 대개 `[FEAT]` → `Feat`, `[REFACTOR]` → `Refactor` 다.

### develop 브랜치 문제

규칙상 **모든 브랜치는 develop에서 분기**해야 하는데, 지금 이 레포에는 develop 브랜치가 없다.
main만 있다.

이 상황을 만나면 **조용히 main에서 따지 마라.** 규칙과 현실이 어긋난 지점이고 팀이 알아야 할
문제다. 사용자에게 알리고 고르게 해라.

- develop을 지금 만들고 거기서 분기 (규칙대로 가는 길)
- 일단 main에서 분기 (지금은 급하니까)

브랜치를 옮기기 전에 `git status` 로 작업 중인 변경이 있는지 확인하고, 있으면 먼저 알려라.
커밋 안 된 변경을 들고 브랜치를 갈아타면 나중에 어느 브랜치 작업이었는지 헷갈린다.

---

## 마무리

이슈 URL과 만든 브랜치명만 짧게 보여주고 끝낸다.

```
✅ 이슈 #7 생성 — https://github.com/.../issues/7
✅ 브랜치 Feat/7 (develop에서 분기)
```

사용자는 이제 바로 작업을 시작하고 싶은 상태다. 요약을 길게 늘어놓지 마라.
